=== Preface

This document describes features available to the area builder for Dragons
Domain MUD.  We endeavour to keep it up to date to reflect stable changes in the
MUD.  It should not be used to document features that are not fully implemented
and tested.



=== Advice to builders

Plan your area on paper or using something like https://virtual-graph-paper.com/.
Check the MUD to make sure there's not already something similar in place. Map
out your area and place mobs and items BEFORE you start writing.  Think before
you write.  If you have questions, read through this document and try and figure
it out.  If you still have questions feel free to ask one of the imms. Let
your imagination run wild, but keep on theme (medieval fantasy hack and slash,
for the most part).



=== Overview of Areas:

An area is one piece of the world.  Each area is defined in a separate file.
All area files have the extension '.are'. Remember the Dragons Domain is a
magical, medieval fantasy-based world, where technology is not particularly
advanced.



=== Sections of an Area

An area file contains the following sections:

    #AREA
    #AREA_SPECIAL
    #HELPS
    #RECALL
    #MOBILES
    #MOBPROGS
    #OBJECTS
    #OBJECT_SETS
    #ROOMS
    #ROOMS_AMBIENT
    #RESETS
    #GAMES
    #SHOPS
    #SPECIALS
    #$

An area is a collection of sections starting with #AREA until the next #AREA.
All of our area files (except 'helpfile.are') contain just one #AREA section,
which is at the top of the file.


=== Data Types

All of the data in an area file (even the section headers) consists of a
series of values.  Each value has a specific type.  The server parses the
file by reading in data values one at a time according to the types it
expects.

Blank characters (spaces, tabs, new lines, carriage returns) at the beginning
of a data value are always ignored (this includes strings).  Thus, you can
format the area files whatever way suits your taste and your needs.

The individual types are: 'letter', 'word', 'string', 'number', and 'to_eol'.

A 'letter' is a single non-blank character.

A 'word' is a sequence of non-blank characters terminated by a blank.

A 'string' is a sequence of non-tilde characters terminated by a tilde.  A
tilde is this character: '~'.  Thus, strings may contain blanks, and may be
multiple lines long.  There is no limit on the length of an individual
string; however, all strings go into a common memory pool whose size is fixed
when the server is compiled.

A 'number' is a decimal number with an optional leading '-' or '+'.  The '|'
character may be used in any number: '1|64|1048576' has the value 1048641.
The individual values separated by '|' are added together, so '5|6' is 11,
not 7. The components need not be powers of 2.  This feature is extremely
useful for defining bit vectors, such as the ACT_* and AFF_* bits for
mobiles, but is not restricted to bit vectors: any number may use the '|'
construction. ie, when putting affects together, all you need to do is the
following (example is a mob who is aggressive and stays in one room) 1|2|32.

A 'to_eol' is all the characters from the current position to the end of the
current input line.  It is used for parsing comments at the ends of lines.

In the syntax description below, <value:type> indicates a value to be read of
the indicated type.  A backslash '\' indicates that the file format itself
has only one line, but several lines are used in this description to fit
within 80 columns.

Braces '{ ... }' are used to enclose elements.  They are NOT literal parts of
the file format, but a way of indicating that the enclosed elements may be
repeated zero or more times.  Braces at the same level of indentation
indicate that the parallel elements may be present in any order.

All other characters in the syntax description are literal characters.

Mobiles, objects, and rooms are identified by vnum (virtual number).  The
range of vnum's is 1 to 65534.  Vnums must be unique (for that particular
kind of vnum).  Vnums do not have to be in increasing order.

Typically an area uses the same range of vnums for mobile vnum', object
vnum', and room vnums, starting with a multiple of 100.  This facilitates
adding the area into an existing set of areas.

At DD4, we typically preassign room vnums.  Let us know the size of your area
to the nearest 100 rooms and we'll give you an available "block" of vnums to use.



=== The #AREA section

The syntax of this section is:

    #AREA <area-writer:string>~ <area-name:string>~
    <lower-level-recommended:number> <upper-level-recommended:number>  \
    <lower-level-hard-limit:number> <upper-level-hard-limit:number>

The 'area-writer' is the name of author of the area.  The 'area-name' is the
name of the area and can be any string.  The next line contains 4 numbers.  The
first two are the recommended level range of the area, and the second two are
the game-enforced limits on character levels who may enter the area.

The 'areas' command uses the first four of the these values.  An example #AREA
section follows:

    #AREA Owl~ Ota'ar Dar Prince's Canton~
    55 60 40 100



=== The #AREA_SPECIAL section

The syntax of this section is:

    #AREA_SPECIAL
    <area-flag:word>
    {
    <flag-modifier:number>
    }
    $

The 'area-flag' is a usually-standalone word put on a line by itself to indicate
a special effect and/or flag that should be applied to the entire area.
Currently one of these, 'exp_mod' also has an associated 'flag-modifier' number
that should follow it.

The current #AREA_SPECIAL flags are:

school                  Area is a MUD SCHOOL (new character beginning area).
no_quest                No mobs in this area may be auto-quest targets.
hidden                  The "areas" command will not show this area, and the
                        mapmaker will not generate maps of it.
safe                    Pkilling cannot happen in this area.
no_teleport             A player cannot teleport into this area.
no_magic                Magic cannot be used in this area.
exp_mod NUMBER          An experience point modifier is applied to all mobs
                        killed in this area. 100 means no change, 50 means
                        halved, 200 means doubled, and so forth.
reset_msg STRING        Reset message that replaces the default area-reset
                        message. Put the message on the following line and
                        terminate it with a tilde (~).
reset_sound FILE        Replaces the default notification sound played when the
                        area-reset message is shown. FILE must be a relative
                        media path containing no spaces, normally beginning with
                        'notify/'. If this setting is omitted, the default reset
                        sound is: notify/area_reset.mp3
reset_sound_vol NUMBER  Sets the source volume of the area-reset notification
                        sound. A value of 0 disables the reset sound. If this
                        setting is omitted, the default volume is 60.
ambient FILE            Default environmental ambience for the area. FILE is a
                        relative media path containing no spaces, normally
                        beginning with "ambient/".
ambient_vol NUMBER      Default area ambience volume. 0 disables the area
                        ambience; values from 1 to 100 are valid.
music FILE              Default looping music for the area. FILE is a relative
                        media path containing no spaces, normally beginning with
                        "music/".
music_vol NUMBER        Default area music volume. 0 disables the area music;
                        values from 1 to 100 are valid.

An example #AREA_SPECIAL section follows:

#AREA_SPECIAL
no_teleport
no_quest
ambient ambient/area/forest_insects.mp3
ambient_vol 30
music music/area/forest_theme.mp3
music_vol 20
reset_msg
A fell wind blows through the forest.
~
reset_sound notify/area/forest_reset.mp3
reset_sound_vol 55
$



=== The #HELPS section

Help sections are usually placed in their own file (helpfile.are) but may be
included in individual area files, too.  It will be included in the pool of all
entries accessible via the 'help' command. Conflicting helps are resolved by
displaying only the first instance of a help entry.

One quite good use of the #HELPS section in an area file is to give imms private
information about the area and how it works by restricting the help to
characters of level 101 or higher.

The syntax of a help entry is as follows:

    #HELPS
    {
	<level:number> <keywords:string>~
	<help-text:string>~
    }
    0 $~

The 'level' number is the minimum level necessary to read the help for the
given topic.  For example:

100 IMMTALK :~

would mean that only characters of level 100 or higher could read the helps
for the 'immtalk' command.

The 'keywords' are the text strings that must be matched in order to see
this particular help entry.  Case is unimportant, though typically the
keywords are capitalized.  For two-word entries, single quotes must be
placed around each phrase.  For example:

0 'CURE POISON'~

The 'help-text' of the help is completely at the discretion of the builder.
Spells usually give a syntax example, followed by a summary:

0 'CURE POISON'~
Syntax: cast 'cure poison' <victim>

This spell will remove the effects of poison from the victim's body.
~

Normally when a player uses 'help', both the keywords and the help-text are
shown.  If the 'level' is negative, however, the keywords are suppressed.  This
allows the help file mechanism to be used for certain other commands, such as
the initial 'greetings' text.

If a 'help-text' begins with a leading '.', the leading '.' is stripped off.
This provides for an escape mechanism from the usual leading-blank stripping of
strings, so that entries with complex ASCII art etc may be used.



=== The #RECALL section

The syntax of this section is:

    #RECALL <recall-point:number>

The 'recall-point' gives the vnum of the room to which a player will
recall if they attempt to do so anywhere within the area.  If this section is
omitted, the recall point will be the standard ROOM_VNUM_TEMPLE defined in
merc.h (currently vnum 3001), or your clan headquarters if your character is
clanned.  If the 'recall-point' is invalid, the player is unable to recall
within the area.



=== The #MOBILES section

Mobs are where a lot of the character of your area comes out.  This will be the
most important section for players who walk around with 'brief' on.
The syntax of this section is:

    #MOBILES
    {
     #<vnum:number>
     <keywords:string>
     <short-description:string>
     <long-description:string>
     <description:string>
     <act-flags:number> <affected-flags:number> <alignment:number> S
     <level:number> <hitroll:number> <armor:number>			\
     <hitnodice:number> d <hitsizedice:number> + <hitplus:number>	\
     <damnodice:number> d <damsizedice:number> + <damroll:number>
     <body_form:number> <exp:number>
     <position:number> <position:number> <sex:number>
     {
        {mob_foley_type_1} " " {mob_foley_key_1} "~"
            .   .   .
        {mob_foley_type_last} " " {mob_foley_key_last} "~"
     }
     {
        ">" {mobprog_trigger_type} " " {argument_list} "~"
        {program_command_1}
        {program_command_2}
        {program_command_3}
            .   .   .
        {program_command_N}
        "~" NL
        "|"
     }
     {
        < <archetype:word>~ <rank:word>~
     }
    }
    #0


The 'vnum' is the virtual number of the mobile.

The 'keywords' are words which can be used in commands to identify the
mobile.

The 'short-description' is the description used by the 'act' function and
other functions (notably in combat) to identify the mobile.

The 'long-description' is the description seen when a character walks into a
room in which the mobile is visible.

The 'description' is the longest description.  It is used when a character
explicitly looks at the mobile.

The 'act-flags' define how the mobile acts.  See 'HELP BITZ' in game to see what

==Mindlessness

AFF_MINDLESS uses BIT_49, decimal 562949953421312.
Scribe supplies it through the existing affect field:

    aff mindless

This is an explicit trait, independent of undead classification, anatomy,
intelligence scores and physiology. No existing archetype is automatically
assigned it by this chunk.

The ordinary AFF XOR rules apply. An individual bit adds mindlessness when
it is absent from the template, or cancels it when already inherited.
Omission or zero preserves an inherited bit.

Implemented mind-dependent consumers:

    Synaptic Blast, Inflict Pain, Mind Thrust, Psionic Blast,
    Psychic Crush, and each otherwise eligible Ultrablast target.

    Charm Person, Awe, Ego Whip, Feeblemind, Psychic Drain,
    Fear, Confusion, and Possession.

    Combat Mind, which requires a mind to enhance.

    Transfix, and the defensive Aura of Fear check against its attacker.

The target checks occur before the effect is applied. They do not roll a
saving throw or modify the resistance masks.

Mindlessness does not automatically grant RES_PSYCHIC immunity. Physical
psionic effects such as Ballistic Attack and Project Force retain their
existing handling. The list above defines this chunk's implemented consumers;
it is not a blanket rule for all psionic or psychologically named abilities.

Existing casting costs, lag, target restrictions and surrounding retaliation
remain in place. Rejecting the effect is not a ceasefire or a mana refund.
Domination's existing disabled implementation is not re-enabled.

mstat's existing AFF layers display the named flag. Live editing uses:

    mset <mobile> mindless on
    mset <mobile> mindless off

These NPC-only commands set or clear only this live bit. They do not change
the prototype, other flags, other instances or future spawns. Repeating the
same setting is idempotent. Invalid settings change nothing.

Adding the trait does not retroactively remove existing effects or follower
relationships. No generic rejection is added to affect_to_char() or
add_follower(): necromantic servants may still use the existing AFF_CHARM
and follower machinery.

Mindlessness does not itself grant poison, sleep, paralysis or drain immunity,
remove body parts, change INT/WIS, disable special functions or prevent speech.
The skeleton's physiology and resistance package remain separate work.


The 'alignment' of the mobile ranges from -1000 to +1000.  Keep in mind that
certain spells give characters fighting oppositely-aligned monsters an
advantage, and that experience gained is influenced by the relative alignments
of a character and their victims.

The literal letter 'S' must be present after the alignment.  In the original
Diku mob format, 'S' stands for simple.  DD4 supports only 'simple' mobs, so
the 'S' is actually redundant, but is retained for compatibility.

The 'level' is a number from 1 to (probably?) 2147483647.  Mobs power scale up
to INT_MAX, but it's unlikely you'd make mobs much higher level than 120 or so,
given that a player maxes at 100--assuming you actually want them to be killed
by players (which you may not).

The 'body-form' is a value that describes the morphology of mobiles, to improve
corpse and carnage production upon death, and prevent some rather silly
player/mobile interactions (tripping up snakes, for example). It contains flags
that describe the physical characteristics of mobiles that are checked by
many functions during the game.

A body_form value of 0 specifies a normal-sized humanoid capable of speech.

The following bit values are used to specify mob form:

        Flag              Bit   Description
        --------------    ---   --------------------------------
        BODY_NO_HEAD        1   No head
        BODY_NO_EYES        2   No eyes
        BODY_NO_ARMS        4   No arms
        BODY_NO_LEGS        8   No legs
        BODY_NO_HEART      16   No heart
        BODY_NO_SPEECH     32   Cannot speak the common language
        BODY_NO_CORPSE     64   Won't leave a corpse when killed
        BODY_HUGE         128   Massive size
        BODY_INORGANIC    256   Not made of living tissue
        BODY_HAS_TAIL     512   Has a tail

Example:
        #101
        wild dog^
        a wild dog^
        A half starved, wild dog wanders the abandoned street.
        ~
        This wild-eyed and starving mongrel patrols the piles of rubbish.
        ~
        1|32|128 0 0 S
        1 0 0 0d0+0 0d0+0
Here -> 4|32 0
        8 8 1

In this example, the mob 'wild dog' has a body_form value of 36 (no arms
and no speech).  Pipes can be used for easy calculation.

Mobs with 'BODY_NO_CORPSE' set do not form corpses or produce carnage; they
wither and disappear. Any coins or equipment that would normally be in a corpse
falls to the floor of the room.  If equipment or money falls a message is printed
when the mob is killed.

Corpse forming mobiles may produce body parts when killed or spray blood.
Random death-generated parts use the creature's resolved BODY/PART anatomy
and declared natural parts. Legacy default head, heart and limb checks remain.
A successful part-drop roll creates at most one eligible kind. Quantity flags
do not create several objects, and BODY_NO_CORPSE suppresses all such drops.

Generated parts decay, carry ITEM_BODY_PART, and retain undead provenance.
Inorganic parts are inedible trash. See the Scribe manual for supported
part keywords and examples. mstat lists the current death-part candidates.

Body parts from mobiles with 'BODY_INORGANIC' set are made type
'trash' and are inedible (but still have a timer set to prevent clutter).

The "mob_foley_type" and  "mob_foley_key" values are what allow you to
optionally override default mobile foley sounds.  Currently footstep foley is
implemented by terrain type.  The default footstep sounds are those of a
medium-sized humanoid moving through SECT_CITY, SECT_SWAMP, etc.  To override
them you can use types and keys per below, where "3060" in the list below is the
mob's vnum.  Any sounds not overridden will use the defaults.

    FStepInside sfx.foley.mob.3060.inside~
    FStepCity sfx.foley.mob.3060.city~
    FStepField sfx.foley.mob.3060.field~
    FStepForest sfx.foley.mob.3060.forest~
    FStepHills sfx.foley.mob.3060.hills~
    FStepMountain sfx.foley.mob.3060.mountain~
    FStepDesert sfx.foley.mob.3060.desert~
    FStepSwamp sfx.foley.mob.3060.swamp~
    FStepWater sfx.foley.mob.3060.water~
    FStepUnderwater sfx.foley.mob.3060.underwater~
    FStepUnderwaterGround sfx.foley.mob.3060.underwater_ground~
    FStepAir sfx.foley.mob.3060.air~

You will need to add entries to the sound_const.c file for these overrides, and
upload the sounds in the appropriate server directories for Mudlet to pull them,
e.g.

{ "sfx.foley.mob.3060.city",
    { "sfx/foley/mob/3060/city.1.mp3",
      "sfx/foley/mob/3060/city.2.mp3", NULL }, { 0 }, 45, "foley", 1 },

{ "sfx.foley.mob.3060.inside",
    { "sfx/foley/mob/3060/inside.1.mp3",
      "sfx/foley/mob/3060/inside.2.mp3", NULL }, { 0 }, 45, "foley", 1 },

The "mobprog_trigger_type" and associated information describe the format of
mobprogs, simple mobile-specific programs written in the MUD's pseudo-scripting
Mobprog language.  Their description is out of scope of this document, but read
mobprogs.txt for full details.

The optional mobile selection line names an archetype and rank:

    < skeleton~ common~

Scribe supplies these independently through archetype and rnk. The selected
archetype determines the body species and inherited defaults.

ACT, AFF, body-form, attack-part and resistance inputs are individual XOR
masks. Scalar values replace or inherit defaults. Special names resolve per
slot, with one complete selection-probability vector.

Export the original individual inputs, not an expanded inherited state.
Use mstat to inspect template, individual, prototype and live values.

Consult mob.c or the Scribe manual for individual archetypes.

The wight archetype is an intelligent corporeal undead humanoid:

    < wight~ common~

It inherits ordinary humanoid anatomy and adds ACT_UNDEAD.

Wights are not mindless and retain speech. The archetype does not add
BODY_INORGANIC, BODY_NO_CORPSE, BODY_NO_SPEECH or ghost phase.

Passive combat defaults are:

    resistance:     RES_DARK
    vulnerability:  RES_HOLY
    immunity:       RES_POISON | RES_SLEEP | RES_DRAIN

Wights do not inherit RES_NONMAGIC, silver vulnerability, cold-iron
vulnerability, charm immunity or paralysis immunity.

The template supplies spec_wight as its active behaviour. It does not use
the broad legacy spec_cast_undead spellcaster.

While fighting and able to act, spec_wight has a 20 percent chance at each
special-function opportunity to attempt Energy Drain against the current
opponent.

The existing Energy Drain implementation remains authoritative. Its
RES_DRAIN | RES_MAGIC resistance categories, save behaviour, edrain cooldown
and existing resource/XP effects are reused rather than duplicated.

A victim with an active edrain timer is not drained again. spec_wight also
does not use the living-target drain against an IS_UNDEAD() opponent.

The archetype XP adjustment remains zero. spec_wight receives the normal
+10 percentage-point special-function XP weighting.

A normally killed wight retains the ordinary corporeal death path. Its
corpse is marked by the existing undead-provenance machinery.

Scribe selects the archetype with "archetype wight". Individual ACT,
resistance, vulnerability and immunity values remain XOR overrides.

Do not convert existing world wights merely by name. Conversion should be
performed explicitly after the archetype and spec_wight have been tested.

The wraith archetype is an intelligent supernatural undead spirit:

    < wraith~ common~

It uses the humanoid body species but has no ordinary biological interior.

Its body-form XOR adds:

    BODY_NO_HEART
    BODY_NO_CORPSE
    BODY_INORGANIC

and cancels inherited:

    PART_HEART
    PART_BRAINS
    PART_GUTS

Humanoid limbs and sensory capability remain inherited. The wraith is not
mindless and retains speech.

Passive combat defaults are:

    resistance:     RES_DARK
    vulnerability:  RES_HOLY
    immunity:       RES_POISON | RES_SLEEP | RES_DRAIN | RES_NONMAGIC

The wraith starts with ghostphase semi_material.

RES_NONMAGIC supplies the mundane-contact barrier. The existing supported
phase-aware weapon/shield rules therefore apply: ordinary mundane weapons are
blocked, mundane silver receives the established semi-material exception, and
magical weapons use normal resistance handling.

The template does not assign AFF_NON_CORPOREAL. Live NPC phase remains the
separate ghost_phase state.

The wraith archetype supplies spec_wraith.

When not fighting and otherwise able to act, a semi-material wraith changes
to ghostphase ethereal on its next special-function opportunity.

When an ethereal wraith enters combat, its next eligible special-function
opportunity changes it to semi_material. That materialisation uses the
opportunity; it does not also attempt life drain.

While fighting in semi_material, spec_wraith reuses the existing spec_wight
Energy Drain behaviour, including its 20 percent attempt chance,
RES_DRAIN | RES_MAGIC handling, save behaviour and edrain cooldown.

An explicit ghostphase none disables the automatic phase transitions without
disabling life drain or removing RES_NONMAGIC.

After combat ends, a semi-material wraith returns to ethereal at its next
eligible special opportunity.

    < dracolich~ common~

It is intelligent and undead, and it keeps the dragon's wings, tail, scales

Ghost phase: initial defaults and live state
------------------------------------------

Initial phase resolves through body species, creature archetype,
individual mobile definition and prototype, then is copied into
each newly created NPC.

Phase is a scalar selection, not a bitmask. A later explicit value
replaces the earlier value; do not OR or XOR phases together.

The C-table initial_ghost_phase fields accept MOB_TEMPLATE_UNSET
for inheritance or one of GHOST_PHASE_NONE, GHOST_PHASE_ETHEREAL
and GHOST_PHASE_SEMI_MATERIAL. Both raw tables are validated at boot.

All current body species supply none. The ghost archetype supplies
semi_material for development testing; other archetypes inherit.
No name, vnum, undead flag or special function independently selects
a phase in create_mobile().

The optional Scribe mobile field is:

    ghostphase inherit
    ghostphase none
    ghostphase ethereal
    ghostphase semi_material

Use the appropriate single setting. Omission or inherit emits no
override. Explicit none is preserved.

The corresponding optional #MOBILES tail field is:

    MobGhostPhase <inherit|none|ethereal|semi_material>

This field has no trailing tilde. Place it after any mob programs,
archetype/rank selection and teacher entries, with the other optional
metadata before the next # record. Invalid phase tokens stop loading
with a diagnostic identifying the mobile.

MOB_INDEX_DATA preserves the original setting in area_ghost_phase
and the resolved initial value in initial_ghost_phase.
CHAR_DATA.ghost_phase remains the independent live value.

clear_char() still clears the live value to none. create_mobile()
then copies the validated prototype initial value once. PCs keep
the neutral value. Recreating an NPC restores its prototype's initial
phase; a normal reset does not overwrite an existing living instance.

Authorised live controls remain:

    mset <mobile> ghostphase none
    mset <mobile> ghostphase ethereal
    mset <mobile> ghostphase semi_material

Live mset does not accept inherit and does not edit the prototype.
mstat separates body-species, archetype, template, individual,
prototype-initial and current-live values.

Phase remains independent of ACT_UNDEAD, anatomy and resistance masks.
Explicit none does not remove undead classification or restore organs.
Cancelling ACT_UNDEAD does not automatically clear the selected phase.

The live phase now affects the explicitly supported weapon/shield
contacts and their pre-success contact checks.

A fully ethereal NPC and an unphased character cannot reach one another
through those physical contacts, even with a magical weapon.
Semi-material and ethereal NPCs share an ethereal side for this contact
policy; other matching immunities still apply.

Against a default semi-material ghost from the unphased side, mundane
weapons are blocked by RES_NONMAGIC. Mundane silver is admitted at half
damage. Magical weapons, including magical silver, receive normal
treatment unless another configured response applies.

A material vulnerability can also overcome RES_NONMAGIC. For example, a
cold-iron-vulnerable creature can be struck by a mundane cold-iron weapon.
Cold iron does not otherwise bypass the semi-material barrier.

These exceptions do not modify stored masks or make silver magical.
Any other matching immunity still wins. The conditional silver
resistance is combined once with other responses; a matching
vulnerability cancels it under the existing non-stacking rule.

Cancelling RES_NONMAGIC through an individual XOR override removes that
barrier and its conditional silver penalty. Selecting ghostphase none
alone does not remove the separately inherited immunity.

Stun rejects inorganic NPCs. Decapitate rejects NPCs that are both
inorganic and no-corpse, avoiding fabricated ghost heads. Player
profiles are unchanged. The material-only finishing/status chance
rules otherwise retain their existing scope after the contact gate.

Generic damage callers, spell-phase rules, unconverted projectiles,
Target/trauma and other bespoke effects are not automatically covered.
Existing mask-based effects still use their declared categories.
The ghost is not yet ready for conversion of production world mobs
or Animate Dead servants.

There is no automatic transition, timer, new special or player phasing.
Visibility, movement, normal death and reward handling remain separate.

See the Scribe manual's "Ghost phase: weapon and shield contact" section
for the exact supported paths, contact matrix and tests.

See the Scribe manual's "Ghost phase: initial defaults and live state"
section.

==Individual mobile flag overrides

For a mobile with a mob-spec archetype, its ordinary ACT, AFF and body-form
fields are XOR masks applied over the resolved body-species/archetype
defaults.

A bit absent from the inherited template is added when present in the
individual field. A bit already present in the inherited template is removed
when present in the individual field.

An individual mask of zero inherits the template unchanged. Mobiles without
a mob-spec retain the ordinary meaning of these fields.

The server preserves the original individual masks separately from the
resolved prototype flags. Runtime changes affect the live mobile and are
not repeatedly XORed against the template.

ACT_IS_NPC is always enabled on NPC prototypes. AFF_CHARM is always removed
from the initial prototype; charm remains a runtime relationship.

Scribe's act, aff and bf fields continue to emit the individual masks.
Do not expand inherited defaults into those fields during export.

When converting an existing mobile to inheritance, remove duplicated flags
from its individual mask unless cancellation is intended.

mstat shows Template, #MOBILES, XOR removed, Prototype and Live values for
each of these three flag groups.

==Individual resistance overrides

Optional #MOBILES tail fields:

    MobResists <mask>
    MobVulnerabilities <mask>
    MobImmunes <mask>

Place these after the ordinary mobile data, mob programs, optional
archetype/rank entry, and teacher entries. They can accompany the optional
footstep fields. No tilde terminator is used.

The corresponding Scribe fields are:

    res     resistance XOR mask
    vuln    vulnerability XOR mask
    imm     immunity XOR mask

Scribe accepts resistance keywords separated by spaces, or a combined decimal
mask. The .are fields accept decimal masks or decimal values joined by '|'
without spaces.

Omitted fields and zero masks inherit the corresponding template unchanged.
A repeated inherited bit is removed; a previously absent bit is added.

Values within a single mask are ORed together. XOR applies between the
template and individual layers, not between repeated words in one field.

If a tail field is declared more than once, the last declaration replaces
that individual input mask; repeated declarations do not toggle it again.

Raw resistance, vulnerability and immunity masks may overlap legitimately.
For example, converting inherited fire immunity to fire vulnerability
requires fire in both the individual immunity and vulnerability masks.

The resolved prototype must not contain contradictory categories. Invalid
effective combinations produce boot diagnostics. Existing runtime precedence
remains immunity first, with resistance and vulnerability cancelling.

Each spawned NPC receives its own copy of the effective prototype masks.
mstat displays Template, #MOBILES, XOR removed, Prototype and Live values.

The immortal commands:

    mset <mobile> resists <mask>
    mset <mobile> vulnerabilities <mask>
    mset <mobile> immunes <mask>

replace a complete live mask. They are not XOR operations and do not change
the prototype, area file, other existing instances, or future spawns.

These generic live resistance fields currently apply to NPCs only.

Cold iron is RES_COLD_IRON, BIT_22, decimal 4194304. It is available through
the normal res, vuln and imm fields and follows their existing inheritance,
validation and combat-resolution rules.

ITEM_COLD_IRON, BIT_32, decimal 4294967296, explicitly tags an object.
Ordinary primary/secondary melee strikes with a tagged weapon add
RES_COLD_IRON to the attack's existing physical and magic/nonmagic categories.
The combined mask is resolved once. Names do not determine material.

Cold iron is distinct from freezing damage. Other damage paths do not acquire
the category merely because the attacker carries a tagged weapon. See the
Scribe manual for supported attack paths and examples.

Silver uses ITEM_SILVER (BIT_33, decimal 8589934592) for object tagging
and RES_SILVER (BIT_23, decimal 8388608) for resistance classification.

Scribe accepts object "ex silver" and mobile "res silver",
"vuln silver" or "imm silver". Existing inheritance and validation apply.

Ordinary primary/secondary strikes with the actual tagged weapon add
RES_SILVER to their existing damage and magic/nonmagic categories.
The combined mask is resolved once. Silver does not grant magic or
automatically bypass RES_NONMAGIC immunity.

Names and descriptions do not set the material flag. This change does
not alter the ghost archetype or classify unrelated attacks as silver.

The combined valid resistance mask is 16777215, covering bits 0 to 23.

Named object-contact attacks now use the selected weapon or shield's
ITEM_MAGIC, ITEM_SILVER and ITEM_COLD_IRON properties.

Supported weapon paths are backstab/double backstab, circle/second circle,
thrust, joust, riposte, counterbalance strikes, armed whirlwind, weapon
Hurl and Decapitate. Smash uses the actual shield. Shield Hurl uses the
selected equipped shield.

Damage resolves its combined categories once. Decapitate, Assassinate's
level-based proc and shield Hurl additionally adjust their percentage
chance using material responses: immunity prevents success, resistance
halves the chance, vulnerability adds half, and conflicting resistance
and vulnerability cancel. Existing upper thresholds are retained.

Matching contact immunity blocks finishing/status effects before their
success side effects. Smash does not impose victim lag through immunity.

Natural/body-part variants do not borrow material from unrelated items.
A huge NPC's shieldless Smash has no item-material categories.
Existing NPC-only resistance handling and XOR authoring remain unchanged.

See the Scribe manual's "Named weapon and shield contacts" section for
source selection, chance conventions and exclusions.

==Innate player resistances and vulnerabilities

The shared resistance resolver also handles selected innate PC traits:

    Elf, Drow, Wild-Elf: resist sleep and charm.
    Illithid: resist psychic.
    Duergar: resist paralysis.

    Fae: vulnerable to cold iron and silver.
    Tiefling: vulnerable to cold iron.
    Troll: vulnerable to fire and acid.
    Werewolf and Vampire subclasses: vulnerable to silver in every form.
    Shapeshifter class in demon form: vulnerable to silver while in that form.

These are derived from current race, subclass and form, not stored in
NPC resistance fields or removable affects. Racial traits persist through
form changes. Repeated weaknesses combine once, not through XOR or
stacked multipliers. No innate player immunity is supplied.

The existing damage and resistance-aware save rules apply.

Transfix and targeted Howl consult their full skill masks for both PC
and NPC targets. Resistance halves the winning outcomes of the existing
success roll; vulnerability adds half, subject to the existing upper
threshold. Matching immunity prevents success, while matching resistance
and vulnerability cancel. Multiple matching categories do not stack.

Transfix retains charm, nonmagical and psychic categories. Howl retains
nonmagical, psychic and sonic categories. They do not borrow materials
or magical status from equipment. AFF_HOLD does not classify them as
paralysis. Targeted Howl now rejects mindless targets; its no-target
cosmetic action is unchanged.

Confusion uses the resistance-aware save for both PC and NPC targets.
Its existing player behaviour is preserved. No additional saving throw
is introduced, and a successful effect keeps its existing penalties
and duration.

Fireshield retaliation applies innate fire vulnerability to PC
recipients once. No new player immunity is supplied.

See the Scribe manual's "Transfix, Howl and Confusion" section.

Player mstat displays these derived masks and their category names.
Existing learned, equipment and spell defences remain separate.

NPC templates, individual XOR overrides, live masks and immunity rules
remain unchanged. A mobile with a player-race value does not receive
the PC profile automatically. There are no new Scribe fields.

See the Scribe manual's "Innate player resistances and vulnerabilities"
section for scope, examples and diagnostic values.

==Weapon Stun resistance and material handling

Weapon Stun selects a qualifying non-deleted primary blunt weapon,
or the off-hand blunt weapon when the primary does not qualify.

The selected weapon supplies its magical/nonmagical source and any
silver or cold-iron material categories. Stun retains its existing
blunt and paralysis categories. Qualifying body-part objects retain
the skill defaults without item-material or item-magic additions.

The complete contact mask produces one resistance result for the
existing success roll. Resistance halves the winning percentage
outcomes; vulnerability adds half, subject to the existing upper
threshold. Matching resistance and vulnerability cancel. Immunity
or NPC invulnerability prevents the knockout and its victim lag.

There is no additional save, damage event or duration adjustment.
The existing NPC-caller rejection and other target restrictions remain.

Duergar paralysis resistance applies. Elven sleep resistance alone
does not: AFF_SLEEP is the resulting state, not Stun's effect category.

Decapitate, Assassinate and shield Hurl retain their material-only
chance scaling. They share threshold arithmetic with Stun, not its
choice of resistance categories.

See the Scribe manual's "Weapon Stun: materials and resistance" section.

==Tenketsu post-hit paralysis

Tenketsu retains its blunt, nonmagical and paralysis categories.
It does not acquire silver, cold iron or magical properties from
unrelated equipment.

The existing skill/combo damage calculation runs through the normal
damage pipeline once. Its paralysis is applied only afterward, when
positive damage has been applied and both combatants remain present,
alive and above zero HP.

The already-resolved response for that hit controls paralysis:
normal or vulnerable means automatic application; resistant means
a 50 percent chance; immune means no application. A vulnerable
follow-up cannot exceed the existing automatic chance.

Damage scaling and paralysis chance affect separate components.
Damage is not scaled twice. No additional spell save or learned-skill
check is introduced. Misses, zero-damage outcomes, lethal impacts
and already held targets do not receive a new hold/no-recall pair.

Successful paralysis retains the existing duration and penalties.
Duergar paralysis resistance applies. Elven sleep/charm resistance
alone does not. NPCs retain their existing live resistance masks.

Both direct Tenketsu and combo use share this handling.
No new player immunity, flag, Scribe keyword or save field is added.

See the Scribe manual's "Tenketsu: post-hit paralysis" section.


==Individual attack-part overrides

Optional #MOBILES tail field:

    MobAttackParts <mask>

The corresponding Scribe field is:

    atk <attack-part keywords or combined decimal mask>

This field uses the existing combat PART_* bits from PART_CLAWS through
PART_HUSK_SHELL. It does not use RES_* values or general BODY_* flags.
See the Scribe manual for the complete keyword and numeric-value table.

Place MobAttackParts after ordinary mobile data, mob programs, the optional
archetype/rank entry and teacher entries. It may accompany the optional
footstep and resistance fields. No tilde terminator is used.

An omitted field or zero inherits the template unchanged. A repeated
inherited bit is cancelled; a previously absent bit is added. Values within
one mask are ORed together. Repeated field declarations use the last value.

The effective prototype mask is copied into each live NPC. mstat shows
Template, #MOBILES, XOR removed, Prototype and Live values.

    mset <mobile> attack_parts <mask>

replaces the complete live mask. Zero clears that live mask. This does not
change the prototype, other live instances, or future spawns.

Step 4C3a supplies the data, inheritance, live storage and diagnostics.
Step 4C3b uses the live mask when selecting the type of an ordinary NPC
attack with an empty attacking weapon slot.

An equipped weapon, including an existing body-part weapon object, retains
its own type and magical classification. Explicit primary attack identifiers
and player attacks/forms remain unchanged.

Natural mappings:

    claws                        claw       slashing
    fangs                        bite       piercing
    horns, tusks, beak           pierce     piercing
    tail, hooves, paws, forelegs pound      blunt
    sharp_scales                 rake       slashing
    haunch                       crush      blunt

Feathers and husk_shell remain stored features without an ordinary offensive
mapping. They do not automatically grant armour or reflected damage.

Each eligible part is one selection candidate. Only the chosen attack's
resistance category applies. Objectless natural attacks are nonmagical.
No attacks per round, new damage formula, equipment or skill permissions
are added.

Head-based attacks require a head. Hooves, haunches and forelegs require
usable legs. Claws and paws require usable arms or usable legs. Arm/leg
trauma excludes the corresponding limb group. Tail attacks require an
existing tail without tail trauma.

The filter uses the existing HAS_* anatomy macros and does not alter the
stored mask. mstat adds Eligible and Inactive rows. Equipped weapons can
still take precedence over eligible natural parts.

If no offensive part is eligible, the previous generic hit remains
available. An empty attack-part mask is not a no-combat flag.

Body form and attack parts remain separate masks. An attack-part flag does
not automatically add or repair the corresponding general anatomy.

==Individual HP modifier overrides

Optional #MOBILES tail field:

    MobHPMod <signed integer or inherit>

The corresponding Scribe field is:

    hpmod <signed integer or inherit>

This is a percentage adjustment to ordinary generated HP after the existing
level and rank calculation:

    spawn HP = normal level/rank HP * (100 + effective hp_mod) / 100

Integer division rounds down. Final generated HP is bounded to at least 1
and at most MOB_SPAWN_HP_LIMIT (INT_MAX / 100).

Examples:
    0       no adjustment
    25      increase by 25 percent
    -25     decrease by 25 percent
    100     double normal HP

The allowed numeric adjustment is -99 through INT_MAX. Scribe currently
uses the corresponding signed 32-bit upper limit, 2147483647.

This is a scalar replacement, not an XOR mask. Omission or inherit uses the
resolved body-species/archetype value. Explicit zero suppresses an inherited
bonus or penalty. A specified number replaces the inherited number; the
layers are not added together.

Place MobHPMod in the optional mobile tail with the resistance and attack-part
fields, after any mob programs, archetype/rank entry and teachers. There is
no tilde terminator. Repeated declarations use the last value.

The original individual value and resolved prototype value remain separate.
The adjustment is applied once during ordinary mobile creation, before
subsequent equipment or scripted changes.

mstat shows the template, individual and prototype adjustments, plus recorded
spawn base HP, applied adjustment, initial adjusted HP and current HP/maximum.
Inspection does not recalculate or reapply the adjustment.

Later code which explicitly replaces a summoned mobile's HP continues to do
so. Existing live mset hp behaviour is unchanged. There is no mset hpmod
command in this chunk.

This does not change xp_mod, damage/critical/swiftness modifiers, dimensions,
language, or special-function execution.

==Individual attack damage modifier overrides

Optional #MOBILES tail field:

    MobDamMod <signed integer or inherit>

The corresponding Scribe field is:

    dammod <signed integer or inherit>

This is a percentage adjustment to NPC attacks resolved through one_hit().
It includes ordinary weapon/natural/unarmed attacks and manoeuvres which
use that function. It is not a universal modifier for every spell or skill.

The existing attacker-side calculation runs first. Apply the live adjustment
once before target resistance and defense processing:

    adjusted attack = calculated attack * (100 + live dam_mod) / 100

Integer division rounds down. A positive input remains at least one at this
stage; later immunity or defenses can still prevent damage.

The helper uses a 64-bit intermediate and bounds its output to
MOB_ATTACK_DAMAGE_LIMIT (INT_MAX / 1000). The existing final MAX_DAMAGE
rule remains separate.

Examples:
    0       no adjustment
    25      increase by 25 percent
    -25     decrease by 25 percent
    100     double calculated attack damage

Allowed numeric adjustments are -99 through INT_MAX. Scribe uses the
corresponding signed 32-bit upper limit, 2147483647.

Omission or inherit preserves the resolved template adjustment. An explicit
number replaces it, including zero. The inheritance layers are not XORed,
added together, or applied as separate multipliers.

Place MobDamMod in the optional mobile tail with MobHPMod, resistance and
attack-part fields. No tilde terminator is used. Repeated declarations use
the last value.

The prototype value is copied into each live NPC. Combat reads that live
value without changing it. mstat shows template, individual, prototype and
live adjustments, plus an illustrative scaling sample before defenses.

    mset <mobile> dammod <number>

replaces the live adjustment only. It does not accept inherit, alter the
prototype, or affect other instances or future spawns. Existing damroll
editing remains a separate flat bonus.

Player attacks and independent damage paths outside one_hit() are not newly
scaled. Effects already derived from a triggering hit can still reflect its
adjusted amount; do not apply another multiplier to them.

HP, XP, critical/swiftness defaults, dimensions, language and inherited
special execution are unchanged.

==Individual critical and swiftness modifier overrides

Optional #MOBILES tail fields:

    MobCritMod <signed integer or inherit>
    MobSwiftMod <signed integer or inherit>

Corresponding Scribe fields:

    critmod <signed integer or inherit>
    swiftmod <signed integer or inherit>

These are additions to the existing NPC scores, not percentage multipliers:

    initial critical score = 5 + resolved crit_mod
    initial swiftness score = 5 + resolved haste_mod

The existing table member haste_mod supplies the swiftness adjustment.
It does not cast Haste or apply a Haste/Quicken affect.

Allowed adjustments are -100 through 100. Omission or inherit preserves the
resolved template adjustment. An explicit number replaces it, including zero.
The inheritance layers are not XORed, summed or independently multiplied.

An adjustment of 20 produces an initial score of 25. An adjustment of -5
produces zero. Negative initial scores are retained so that subsequent
equipment bonuses do not erase part of a configured penalty.

Place both fields in the optional mobile tail with HP, damage, resistance
and attack-part declarations. No tilde terminator is used. Repeated fields
use the last value. Explicit zero must not disappear during export.

The resolved adjustments initialise the existing live crit and swiftness
fields once during creation, before later equipment or scripted changes.
mstat records the template/individual/prototype values, creation adjustments,
initial scores and current live scores.

The existing critical and swiftness roll comparisons remain unchanged.
These are scores, not promises of exact percentage chances. No new critical
roll or independent attack scheduler is added. Raising swiftness affects the
existing bonus-attack check; it does not grant an additional Haste spell.

Existing live commands remain absolute assignments:

    mset <mobile> crit <score>
    mset <mobile> swiftness <score>

They do not modify prototype values or creation snapshots. There are no new
live critmod/swiftmod commands. The legacy mset crit range is 0 through 99;
the legacy mset swiftness range is 0 through 100.

HP, attack damage, XP, dimensions, language and inherited special execution
remain separate. Player initialisation and combat formulas are unchanged.

==Individual dimension data overrides

Optional #MOBILES tail fields:

    MobHeight <non-negative integer or inherit>
    MobWeight <non-negative integer or inherit>
    MobSize <non-negative integer or inherit>

Corresponding Scribe fields:

    height <non-negative integer or inherit>
    weight <non-negative integer or inherit>
    size <non-negative integer or inherit>

These are absolute raw metadata values, not modifiers or bitmasks.
Omission or inherit uses the resolved template value. A supplied number
replaces that value. Explicit zero means the dimension is unspecified;
it does not describe a physically massless or zero-sized creature.

Each field resolves independently. The layers are not added, multiplied
or XORed. Values range from zero through INT_MAX; Scribe uses the current
signed 32-bit upper limit, 2147483647.

The existing table values are preserved without assigning measurement units
or a categorical size scale. For example, goat's raw dimensions are 1/30/100
and fire_elemental's are 2/20/3. Do not interpret these as a newly defined
physical unit system or size enumeration.

Place the fields in the optional mobile tail with the other scalar,
resistance and attack-part declarations. No tilde terminator is used.
Repeated declarations use the last value. Explicit zero must be exported.

Raw template values and individual inputs are validated before creation.
Each live NPC receives an independent copy of its effective prototype values.

mstat shows Template, #MOBILES, Prototype and Live values for each dimension.

    mset <mobile> height <number>
    mset <mobile> weight <number>
    mset <mobile> size <number>

replace one live value. These commands are NPC-only and do not accept
inherit. They do not modify prototypes, other instances or future spawns.

This data layer does not change combat, carrying, mounting, corpse weight,
equipment fit, room access, movement, body-form flags or natural-attack
eligibility. BODY_HUGE remains independent. APPLY_HEIGHT and APPLY_WEIGHT
remain inactive. Player initialisation and persistence are unchanged.

Language and inherited special-function execution remain separate work.

The accompanying Scribe update also restores the MobDamMod export statement
accidentally removed in PR #714. Verify all existing scalar exports when
testing the new fields.

=== The #OBJECTS section

These are the items the people who journey through your area will keep and use,
so it's a good idea to provide detailed, quality descriptions for them.
Remember to balance them with/against that already exist in the game;
https://fromagefraser.com/dd4-query/items is an excellent tool to research
currently-existing items and their properties to see how yours might slot in.

The syntax of this section is:

    #OBJECTS
    {

The 'vnum' is the virtual number of the object.

The 'keywords' are words which can be used in commands to identify the
object.

description should be lower case, because this description is used in the
middle of sentences.

The 'long-description' is the description used when a character walks in the
room and the object is visible.

The 'action-description' is not used, which why you just put a ~ there.

The 'item-type' is the type of the item.

Blessed weapons and undead
--------------------------

ITEM_BLESS has a specific combat effect when present on the actual
ITEM_WEAPON making an attack against a target satisfying IS_UNDEAD().

A blessed, non-cursed weapon receives +2 effective hitroll on ordinary
one_hit() weapon rolls and +10 percent positive weapon damage, with a
minimum damage bonus of one point.

Blessing does not make a weapon magical, does not add RES_HOLY, and
does not bypass RES_NONMAGIC. ITEM_MAGIC, silver, cold iron and ghost
phase remain independent properties.

An object carrying both ITEM_BLESS and ITEM_CURSED receives no blessing
combat bonus. Cursed weapons receive no new beneficial undead mechanic.

The bonus follows the actual attacking weapon. Inventory items, the
other hand, shields and ITEM_BODY_PART objects do not transfer it.
Named weapon-object damage routed through damage_from_object() uses
its actual source weapon. Chance-based finishing/status rolls do not
receive extra success percentage from blessing.

Vampire PCs satisfy IS_UNDEAD() and are therefore valid undead targets,
subject to the ordinary PvP and safety rules.

--- Notes on use of trapped items

Example of a trapped object:

nice chest~
a nice chest~
A nice chest is here.  It is nice.~
~
15 2097152 1|512 5 20 0
150~ 13~ 27207~ 0~
105 0 0


The 2097152 (BIT_21) is the 'this is a trap' flag.  Any item can be trapped,
just by sticking this flag on it.

The 1|512 flags are TRAP_EFFs, which are basically "what does the trap trigger
on?"  They reference the following, and may be stacked. They will overwrite the
take/wear bits (meaning you can't take/wear a trap).

TRAP_EFF_MOVE           BIT_0 (1)    /* trigger on movement */
TRAP_EFF_OBJECT         BIT_1 (2)    /* trigger on get or put */
TRAP_EFF_ROOM           BIT_2 (4)    /* affect all in room */
TRAP_EFF_NORTH          BIT_3 (8)    /* movement in this direction */
TRAP_EFF_EAST           BIT_4 (16)
TRAP_EFF_SOUTH          BIT_5 (32)
TRAP_EFF_WEST           BIT_6 (64)
TRAP_EFF_UP             BIT_7 (128)
TRAP_EFF_DOWN           BIT_8 (256)
TRAP_EFF_OPEN           BIT_9 (512)  /* trigger on open */


5 is the damage type.  Options are:

TRAP_DAM_SLEEP          -1
TRAP_DAM_TELEPORT        0
TRAP_DAM_FIRE            1
TRAP_DAM_COLD            2
TRAP_DAM_ACID            3
TRAP_DAM_ENERGY          4
TRAP_DAM_BLUNT           5
TRAP_DAM_PIERCE          6
TRAP_DAM_SLASH           7
TRAP_DAM_POISON          8
TRAP_DAM_SNARE           9
TRAP_DAM_CURSE           10
TRAP_DAM_HEX             11
TRAP_DAM_SPIRIT          12


20 in the example item is the number of charges the trap has before it is
exhausted.  The '0' is probably important.

150~ 13~ 27207~ 0~ are capacity, pickable etc flags, and key vnum for the
container here, but could be anything depending on what you trap. The '13' must
be the combined value of bit value flags on containers--because it is consumed
as a string, 1|4|8 will not work.

Imm commands trapstat, trapremove, traplist, and trapset are in wizhelp and have
helpfile entries with more detail. They do what they sound like they should.


--- Meaning of Value Numbers by Item Type

As mentioned earlier, the 'value' fields are entered by the builder as TEXT
strings, even though they will be converted to and stored as integer values.
This is so that spell names, rather than slot numbers, could be used for items
that can have spells placed on them.  For these types of items, the text string
containing the spell name (for example, cure critical) is translated to an
internal skill/spell number or 'sn'.  For the other item types, the strings are
converted directly to integer values.  If an item only has one spell, the other
strings must still be terminated by a ~, but need not have any content.  A
complete list of spells at the time of the last update of this document is given
at the end of this file.

NOTE:  Because these are read in as strings, the '|' pipe format cannot be used
for the flags; i.e. 1|4|8~ is an invalid entry, but 13~ is valid. (cf.
ITEM_CONTAINER, value[1]).  If you try to add a piped value the server will grab
the first value and discard the rest.

Holy water
----------

Holy water is liquid number 16 (LIQ_HOLY_WATER). It uses ordinary water-like
condition values for thirst/fullness and has a separate undead interaction.

When a character satisfying IS_UNDEAD() actually drinks holy water, the base
damage is one quarter of maximum hit points, with a minimum of 10. The damage
uses RES_HOLY and passes through the normal DD4 resistance and death machinery.

Holy resistance, vulnerability and immunity therefore apply normally and only
once. Holy water is not classified as generic RES_MAGIC merely because it is
consecrated.

Living drinkers receive only the ordinary liquid effects.

Sahuagin and grung use the drink command to bathe/cover themselves rather than
drink. Their contact with holy water is not handled by this drinking stage;
that belongs to the later splash/contact mechanic.

Drink containers consume their normal rolled number of draughts. Fountains are
not consumed.

Scribe keyword:

    v2 holy_water

This exports liquid number 16. Existing liquid numbers remain unchanged.

Splashing liquids
-----------------

The general player command is:

    splash <container> <target>

The source must be a carried ITEM_DRINK_CON containing at least one unit
of any valid liquid.

A valid splash consumes up to five liquid units, retains the container,
and costs one combat pulse of wait state. Messages identify the actual
liquid used.

The command itself is liquid-neutral. Individual liquid effects are
resolved separately so that new liquids can gain splash behaviour without
duplicating container and command handling.

At present, ordinary liquids have no mechanical splash effect. Water,
alcohol, blood, salt water and all other current non-holy liquids simply
produce the splash action.

The only current special case is holy water splashed on an undead target.
That combination is hostile and checks is_safe() before liquid is consumed.

Holy-water splash base damage is the smaller of one eighth of the target's
maximum HP and four times the attacker's level, with a minimum of 10.
The result is RES_HOLY and uses the normal damage/death/resistance pipeline.

Holy water splashed on a living target currently has no special effect.

Holy resistance, vulnerability and immunity apply once. This is not a
weapon/material attack and gains no RES_MAGIC, RES_SILVER or RES_COLD_IRON.
Ghost phase does not block the holy effect.

A non-zero drink-container value[3] also makes a splashed liquid poisonous.

Poison can affect suitable living, organic targets. Inorganic creatures and
object-like NPCs cannot be poisoned by liquid contact. Existing RES_POISON
immunity, resistance and vulnerability apply normally, as do player Resist
Toxin and Bonus Exotic protections.

Splash poison is RES_POISON only; it is not automatically RES_MAGIC.

Poison is independent of the liquid's own special effect. Poisoned holy water
can therefore poison an eligible organic undead target and also inflict its
holy-water effect.

Fountains cannot be splashed directly; fill a portable drink container
first.

Future liquid-specific splash effects should be implemented in the shared
liquid splash resolver rather than adding separate splash commands.

=== The #OBJECT_SETS section

DD4 supports having "sets" of 2-5 objects, such that bonuses can be applied
to a player when varying combinations/quantities of them are worn.

To add such a set, the items can be created as usual in an #OBJECTS section, but
the set must be described/detailed in a separate "#OBJECT_SETS" section of the
area file. Currently the set objects and set descriptions are in the "sets.are"
area file for ease of centralisation, but this is only a convention.

The syntax of this section is:

    #OBJECT_SETS
    {
     #<vnum:number>
     <keywords:string>~
     <set-description:string>~
     <set-member0:number> <set-member1:number> <set-member2:number> \
     <set-member3:number> <set-member4:number>
     <bonus-tier0:number> <bonus-tier1:number> <bonus-tier2:number> \
     <bonus-tier3:number> <bonus-tier4:number>
     {
         A
         <apply-type:number> <apply-value:number>
     }
    }
    #0

The "set-member" values are the vnums of the items that belong to the set. A 0
indicates there is no set member in that slot.

Sets are considered to belong to the categories "uncommon" (2 items), "rare"
(3 items), "epic" (4 items), and "legendary" (5 items).

The "bonus-tier" values indicate how many items need to be worn to trigger the
various set bonuses available.

For example, values 5 5 5 5 5 would mean all 5 would need to be worn to get the
bonus, whereas 2 2 4 4 5 would mean 2 items would need to be worn for the first
bonus, 4 items for next bonus, and all 5 for the third.

Note that you cannot, for example, wear 2 items and get 3 bonuses--each increase
in number represents only 1 bonus. Bonuses are also applied in reverse order, so
put your best bonus first!

An example #OBJECT_SETS entry that applies a "fly" bonus when 2 items are worn:

#2702
uncommon crow~
The Smithy's Set of the Crow.
Crow were the pseudo-pets of the smiths, often seen perching across a smithy's
forge in winter months basking in its heat and scavenging any food scraps that
were present. An ancient forging process imbues the essence of crow into this
armour set, allowing its wearer to manifest properties of the black-feathered
avians.
~
2704 2705 0 0 0
2 2 0 0 0
A 27 -1



=== The #ROOMS section

The rooms in your area are what really make it, setting the atmosphere and tone.
Try to make an effort with their descriptions.

The syntax of this section is:

    #ROOMS
    {
     #<vnum:number>
     <name:string>
     <description:string>
     <area:number> <room-flags:number> <sector-type:number>
     {
         D <door:number>
         <description:string>
         <keywords:string>
         <locks:number> <key:number> <to_room:number>
     }
     {
         E
         <keywords:string>
         <description:string>
     }
     S
    }
    #0

The 'vnum' is the virtual number of the room.

The 'name' is the name of the room.

The 'description' is the long multi-line description of the room.

The 'area' is obsolete and unused.  Rooms belong to whatever area was most
recently defined with #AREA.

The 'room-flags' describe more attributes of the room.
ROOM_ flags:
    ROOM_DARK               BIT_0       Room is dark
    ROOM_NO_MOB             BIT_2       Mobiles will not wander into
    ROOM_INDOORS            BIT_3       Is indoors
    ROOM_VAULT              BIT_4       Player vault may be interacted with here
    ROOM_CRAFT              BIT_7       Room gives physical crafting bonus
    ROOM_SPELLCRAFT         BIT_8       Room gives magical crafting bonus
    ROOM_PRIVATE            BIT_9       Room only fits two characters
    ROOM_SAFE               BIT_10      No pkilling in room
    ROOM_SOLITARY           BIT_11      Room only fits one character
    ROOM_PET_SHOP           BIT_12      Room stores pets to be sold at pet store
    ROOM_NO_RECALL          BIT_13      Cannot recall from room
    ROOM_CONE_OF_SILENCE    BIT_14      No magic in room
    ROOM_PLAYER_KILLER      BIT_15      Can recall from here despite other flags
    ROOM_HEALING            BIT_16      Healing rate accelerated here
    ROOM_FREEZING           BIT_17      Room does freezing damage
    ROOM_BURNING            BIT_18      Room does burning damage
    ROOM_NO_MOUNT           BIT_19      Mounts cannot access room
    ROOM_TOXIC              BIT_20      Healing slowed, chance of being poisoned
    ROOM_NO_WEATHER         BIT_21      No weather in room
    ROOM_NO_DROP            BIT_63      Cannot drop items in room


The 'sector-type' identifies the type of terrain.  This primarily affects
movement cost through the room, but may have various other effects--for example,
water races don't have to drink in "wet" terrain types, and rangers get a small
healing bonus when they sleep in HILL and FOREST terrain types.

SECT_ types:
    SECT_INSIDE             0
    SECT_CITY               1
    SECT_FIELD              2
    SECT_FOREST             3
    SECT_HILLS              4
    SECT_MOUNTAIN           5
    SECT_WATER_SWIM         6
    SECT_WATER_NOSWIM       7
    SECT_UNDERWATER         8
    SECT_AIR                9
    SECT_DESERT             10
    SECT_SWAMP              11
    SECT_UNDERWATER_GROUND  12
    SECT_MAX                13

Unlike mobiles and objects, rooms don't have any keywords associated with
them. One may not manipulate a room in the same way one manipulates a mobile
or object.

The optional 'D' sections and 'E' sections come after the main data.  A 'D'
section contains a 'door' in the range from 0 to 5:

     0    north
     1    east
     2    south
     3    west
     4    up
     5    down

A 'D' command also contains a 'description' for that direction, and
'keywords' for manipulating the door.  'Doors' include not just a real door,
but any kind of exit from the room.  The 'locks' value specifies special
features about a door, and there are multiple combinations.  Doors can be
not-doors, bashproof, pickproof, passproof, walls (can be climbed), or secret
(cannot be seen on "exits" information).  The following table gives the 'locks'
value and how the door will be set for each acceptable value:

      value    door    pickproof  bashproof  passproof   wall    secret
        1      yes        no         no         no        no       no
        2      yes       yes         no         no        no       no
        3      yes        no        yes         no        no       no
        4      yes       yes        yes         no        no       no
        5      yes        no         no        yes        no       no
        6      yes       yes         no        yes        no       no
        7      yes        no        yes        yes        no       no
        8      yes       yes        yes        yes        no       no
        9       no        no         no         no       yes       no
        10     yes        no         no         no        no      yes
        11     yes       yes        yes        yes        no      yes
        12      no        no         no         no        no      yes


The 'key' value is the vnum of an object which locks and unlocks the door.

Lastly, 'to_room' is the vnum of the room to which this door leads.

You must specify two 'D' sections, one for each side of the door.  If you
specify just one then you'll get a one-way exit.  As well as one-way exits,
doors can open into the same room they exit from, providing some interesting
creative opportunities.

An 'E' section (extended description) contains a 'keywords' string and a
'description' string.  Looking at one of the words in 'keywords' yields the
'description' string.

The 'S' at the end marks the end of the room.  It is not optional.

=== The #ROOMS_AMBIENT section

The section for adding any environmental sounds to rooms.  These instructions
will override any area-wide (in #AREA_SPECIAL) or terrain-based environmental
sounds/loops.

The syntax of this section is:

    #ROOMS_AMBIENT
    {
     <vnum:number>
     <relative_filepath:string>
     <volume:number>
    }
    #0

The 'vnum' is the virtual number of the room.

The 'relative_filepath' is the relative path to the room sound file.

The 'volume' is the volume the file should be platyed at (0->100, 0 is muted).
If volume is omitted, the default of 25 is used (server-configurable).

The '$' at the end marks the end of this section.  It is not optional.

This section must be declared after #ROOMS.

=== The #RESETS section

The most important section of the area, and the easiest to mess up.  It is
here that you place your mobs and equip them, and place any ground objects that
might exist.  Make sure you use the proper location flags.

The syntax of this section is:

    #RESETS
    {
     * <comment:to_eol>
    }
    {
     M 0 <mob-vnum:number> <limit:number> <room-vnum:number> \
    <comment:to_eol>
    }
    {
     O 0 <obj-vnum:number> <:number> <room-vnum:number>      \
     <comment:to_eol>
    }
    {
     I <obj-vnum:number> <obj-level:number> <room-vnum:number>  \
     <limit:number> <comment:to_eol>
    }
    {
     P 0 <obj-vnum:number> <:number> <obj-vnum:number>       \
     <comment:to_eol>
    }
    {
     G 0 <obj-vnum:number> 0  <comment:to_eol>
    }
    {
     E 0 <obj-vnum:number> 0 <wear_loc:number> <comment:to_eol>
    }
    {
     D 0 <room-vnum:number> <door:number> <state:number>     \
     <comment:to_eol>
    }
    {
     R 0 <room-vnum:number> <last-door:number> <comment:to_eol>
    }
    S

The 'resets' section contains a series of single lines.  The backslashes and
line splitting above are for readability; they are not part of the file
format. Because of the end-of-line comments, this section is not as free-
format as other sections.

The reset commands are:
    *     comment
    M     read a mobile
    O     read an object
    I     place object on ground and set level
    P     put object in object
    G     give object to mobile
    E     equip object to mobile
    D     set state of door
    R     randomize room exits
    S     stop (end of list)

The '*' lines contain comments.  The 'S' line is the last line of the
section.

Every command aside from 'G' is followed by four numbers (three for the 'G'
command). The first number is ignored except in the case of 'I'.

For the 'M' command, the second number is the vnum of a mobile to load.  The
third number is the limit of how many of this mobile may be present in the
world.  NOTE: WORLD (not room). The fourth number is the vnum of the room
where the mobile is loaded.

For the 'I' command, the first number is the vnum of the object to load.  The
second is the level to set the item to.  The third is the vnum of the location
to place it.  The last number is meant to be the object load limit, but is
currently unimplemented and thus ignored.

For the 'O', 'P', 'G', and 'E' commands, the second number is the vnum of an
object to load.  The third number is ignored.

For the 'O' command, the fourth number is the vnum of the room where the
object is loaded.  The object is not loaded if the target room already
contains any objects with this vnum.  The object is also not loaded if any
players are present in the area.  The object's level will be related to that of
the mob most recently loaded in the area before it.

For the 'P' command, the fourth number is the vnum of a container object
where the object will be loaded.  The actual container used is the most
recently loaded object with the right vnum; for best results, there should be
only one such container in the world.  The object is not loaded if no
container object exists, or if someone is carrying it, or if it already
contains one of the to-be-loaded object.

For the 'G' command, there is no fourth number.  If the most recent 'M'
command succeeded (e.g. the mobile limit wasn't exceeded), the object is
given to that mobile.  If the most recent 'M' command failed (due to hitting
mobile limit), then the object is not loaded.

For the 'E' command, the fourth number is an equipment wear location (see
following).  Be careful where you equip the mobile or you might end up with a
breast plate used as a weapon--the server will not prevent you from doing this.

If the most recent 'M' command succeeded, that mobile is equipped with the
object.  If the most recent 'M' command failed, then the object is not loaded.

Equipment wear locations:
    WEAR_NONE               -1
    WEAR_LIGHT               0
    WEAR_FINGER_L            1
    WEAR_FINGER_R            2
    WEAR_NECK_1              3
    WEAR_NECK_2              4
    WEAR_BODY                5
    WEAR_HEAD                6
    WEAR_LEGS                7
    WEAR_FEET                8
    WEAR_HANDS               9
    WEAR_ARMS               10
    WEAR_SHIELD             11
    WEAR_ABOUT              12
    WEAR_WAIST              13
    WEAR_WRIST_L            14
    WEAR_WRIST_R            15
    WEAR_WIELD              16
    WEAR_HOLD               17
    WEAR_DUAL               18
    WEAR_FLOAT              19
    WEAR_POUCH              20
    WEAR_RANGED_WEAPON      21


All objects have a level limit, which is computed by inheritance from the
most recently read 'M' command (whether it succeeded or not) in 'area_update'
in 'db.c'.  A worn/equipped object's level equals the carrying mobile's level
minus a few levels, clipped to the range 0 to 100.  There is also a bit of fuzz
on the mobile's loaded level based on their set level in their #MOBILES entry,
with the consequence that it should be possible (if unlikely) to obtain an item
up to 4 levels lower than the set-level of the mobile who carries it.

For the 'D' command, the second number is the vnum of a room.  The third
number is a door number from 0 to 5.  The fourth number indicates how to set
the door: 0 for open and unlocked; 1 for closed and unlocked; 2 for closed
and locked.

Room exits should be coherent: if room 1 has an exit to room 2, and room 2
has an exit in the reverse direction, that exit should go back to room 1.
This doesn't prevent one-way exits; room 2 doesn't HAVE to have an exit in
the reverse direction.

For the 'R' command, the second number is the vnum of a room.  The third
number is a door number.  When this command, the doors from 0 to the
indicated door number are shuffled.  The room will still have the same exits
leading to the same other rooms as before, but the directions will be
different.  Thus, a door number of 4 makes a two-dimensional maze room; a
door number of 6 makes a three-dimensional maze room.

Use of both the 'D' and 'R' commands on the same room will yield
unpredictable results.

Any line (except an 'S' line) may have a comment at the end.



=== The #GAMES section

#GAMES section in area files

To allow mobs to host gambling games.

The syntax is:

 #GAMES
    {
     * <comment_to_eol>
    }
    {
     M <mob-vnum:number> <game-fun:string> <bankroll:number>
       <max_wait:number> <cheat:number>
       <comment:to_eol>
    }
    S

The #GAMES section has one command per line.

The 'M' command assigns game-fun to all mobiles with mob-vnum.

bankroll is the amount of gold that the croupier (the mob running the game) has
when it is loaded.  When the bankroll goes below zero, the mob shuts down its
game.  Currently games can only be conducted with gold pieces, though it is
planned that this will be changed eventually to allow all denominations.

The max_wait value is the number of PULSE_MOBILEs the croupier will wait for
each person to make a decision for interactive games (currently unimplemented).
PULSE_MOBILE is defined in merc.h.  The wait between rounds should depend upon
the number of players playing.

If cheat is non-zero ("true") this mobile will cheat at the given game (assuming
cheat code is implemented in the game).

An 'M' line may have a comment at the end.

The following simple games are currently available for mobiles:

game_u_l_t                Upper-Lower-Triple, a dice game
game_high_dice            High dice, a dice game
game_seven                Seven, a dice game

An example of a #GAMES section:
*
M  3160 game_u_l_t            100000    4    1    /* Croupier, cheats    */
M  3161 game_blackjack        1000000   8    0    /* Dealer, doesn't cheat */
*
S



=== The #SHOPS section

The syntax of this section is:

    #SHOPS
    {
     <keeper:number>                                        \
     <trade-0:number> <trade-1:number> <trade-2:number>     \
     <trade-3:number> <trade-4:number>                      \
     <profit-buy:number> <profit-sell:number>               \
     <open-hour:number> <close-hour:number>                 \
     <comment:to_eol>
    }
    0

Like the #RESETS section, the #SHOPS section has one command per line.

The 'keeper' is the vnum of the mobile who is the shopkeeper.  All mobiles
with that vnum will be shopkeepers.

The 'trade-0' through 'trade-4' numbers are item types which the shopkeeper
will buy.  Unused slots should have a '0' in them; for instance, a shopkeeper
who doesn't buy anything would have five zeroes.

The 'profit-buy' number is a markup for players buying items from the keeper, in
percentage points.  50 is 50% markup, 100 would be double the item raw "value"
and so on.  The 'profit-sell' number is a markdown for players selling the
keeper items, in percentage points. 100 is nominal price; 75 is a 25% markdown,
and so on. The buying markup should be at least 100, and the selling markdown
should be at most 100.

The 'open-hour' and 'close-hour' numbers define the hours when the shopkeeper
will do business.  For a 24-hour shop, these numbers would be 0 and 23.
Everything beyond 'close-hour' to the end of the line is taken to be a
comment.

Note that there is no room number for a shop.  Just load the shopkeeper
mobile into the room of your choice, and make it ACT_SENTINEL.  Or, for a
roving shopkeeper, leave it as non-sentinel.

The objects a shopkeeper sells are exactly those loaded by 'G' reset commands
for that shopkeeper.  These items replenish automatically.  If a player sells
an object to a shopkeeper, the shopkeeper will keep it for resale if he, she,
or it doesn't already have an identical object.  These items do not
replenish.

See the #SHOPS section in midgaard.are or sahuagin_market.are for good examples.



=== The #SPECIALS section

Use this section to give mobs more personality and capability via spec_funs.
There's literally no limit to what you can accomplish using them, but they're
typically used to have e.g. cleric mobs fight like clerics, warrior mobs fight
like warriors, etc.

The syntax of this section is:

#SPECIALS
    {
     * <comment_to_eol>
    }
    {
     M <mob-vnum:number> <spec-fun:word> <comment:to_eol>
     N <mob-vnum:number> <slot:1..3> <name:word> <comment:to_eol>
     P <mob-vnum:number> <p1:number> <p2:number> <p3:number>
     P <mob-vnum:number> <auto-or-inherit:word>
    }
    S

Like the #RESETS section, the #SPECIALS section has one command per line.

The legacy M record replaces the whole special set with a single named
function at 100%, or with complete none/inherit selection.

N overrides one numbered slot name. P overrides the complete probability
vector. All function names must be registered. Normal trailing comments
are allowed.

==Three weighted special functions

A mobile supports up to three configured specials. At each existing special
opportunity, at most one routine is selected. Percentages are integers from
0 through 100. A set containing functions must total exactly 100.

A zero-percent function is configured but disabled. An empty slot must have
zero probability. Only an entirely empty set may use 0/0/0.

Selection does not bypass a routine's own conditions or random checks.
If the selected routine returns FALSE, another slot is not tried.

Scribe fields:

    sp <name, none or inherit>
    sp2 <name, none or inherit>
    sp3 <name, none or inherit>
    spchance <p1 p2 p3, auto or inherit>

Standalone sp preserves legacy singleton M output. Using sp2, sp3 or spchance
selects extended N/P output, where sp addresses only slot 1.

Name inheritance is independent per slot. C-table NULL inherits, an empty
string clears, and a non-empty name replaces. The existing spec_fun1,
spec_fun2 and spec_boss fields map to slots 1, 2 and 3. Slot 3 has no new
rank restriction.

The final C-table spec_chance member inherits or replaces as one vector.
MOB_SPECIAL_CHANCES_INHERIT inherits; MOB_SPECIAL_CHANCES_AUTO requests
automatic allocation. A literal vector supplies explicit percentages.
Do not mix sentinel markers and ordinary percentages.

Auto divides 100 over occupied slots: 100, 50/50, or 34/33/33. Remainders
go to earlier occupied slots. Invalid explicit totals are not normalised.

Repeating a name in multiple slots is permitted. Its selection probabilities
add, but the dispatcher still invokes only one selected slot per opportunity.
A zero-percent occurrence does not enable a function by itself.

The effective set is resolved after all area sections load and before resets.
Each live NPC receives its own copy. Capability checks inspect every enabled
slot, not only slot 1.

The special-XP contribution is the rounded weighted mean of the existing
per-function bonuses:

    floor((p1*bonus1 + p2*bonus2 + p3*bonus3 + 50) / 100)

This contribution enters the existing area-reset XP calculation once.
Archetype xp_mod remains a separate additive adjustment. Live edits do not
recalculate an already assigned exp_modifier.

Immortal commands:

    mset <mob> specials <name1> <p1> <name2> <p2> <name3> <p3>
    mset <mob> specials none
    mset <mob> specials inherit
    mset <mob> spec <name>

Use none 0 for an empty slot in the full tuple. The complete replacement
is validated before any change. The live inherit command restores the
effective prototype, including individual overrides. The legacy spec command
installs a singleton at 100% and also accepts whole-set none/inherit.

mstat shows template and individual name/policy inputs, prototype/live slots,
percentages, invocation counters and the prototype special-XP contribution.
Counters measure calls, including routines returning FALSE, not successful
effects. Live replacement resets them. The older one-name summary shows
only the first enabled slot.

No new update schedule, skill-table entries or automatic multi-cast loop
is introduced.

Certain special functions make mobiles much more challenging to fight, and an
experience bonus is added to reflect this. They currently range from no bonus
(not a combat special) to +20% for the really tough specials like
spec_evil_evil_gezhp (!) and spec_sahuagin_prince.

=== Colour

This MUD supports 8-bit (256) terminal colours.  You will see 8-bit colour used
throughout the MUD's text and may use it yourself in your areas, with virtually
any text string.

The format for a colour tag is <NUMBER>.  Similar to using standard colours, you
add 8-bit colour to text by enclosing it in tags.

To print a literal '<' character, just type it twice: '<<'.

Close your tags with <0> to stop your colours from bleeding.

Example: <196>This text would be turned bright red.<0>

For a list of all the colours available and their corresponding tag numbers, see
the table at: https://tinyurl.com/dd4colours or type 'HELP COLOURCODES' while
online.

The numbers for foreground colours run from 1-255; you can also colour the
background--just add 300 to the foreground colour number, so that e.g. to colour
the background BrightCyan (14) you would use the tag <314>, producing this effect.

The following tags are available for text decoration:

<556> Bold ON                   <557> Bold OFF
<558> Italics ON                <559> Italics OFF
<560> Underline ON              <561> Underline OFF
<562> Strikethrough ON          <563> Strikethrough OFF
<564> Default foreground ON     <565> Default background ON

=== Booting and Testing Areas

When the DD4 server starts, it reads a file named 'area.lst' in the current
directory.  This file contains a list of all the area files to read in.  To add
or delete areas, simply edit area.lst.

The server reads all of the area files into memory once at load time and then
closes them.  Thus you can edit area files while the server is running.
Changes will take effect the next time the server boots.  Because the server is
completely memory-based, zone resets are fast.

You can test areas by running a local install of the MUD, which can be obtained
from https://github.com/fromage-fraser/dd4

Instructions on how to do this can be obtained from that location.

The server reports syntax errors, including the area file name and a line
number.  Take the line number with a grain of salt; some kinds of errors cause
the server to run on for quite a few lines before ultimately detecting the
error.

The server also reports semantic errors, such as references to non-existent
mobiles, objects, or rooms.

The server exits after reporting any error.  DD4 takes only a few seconds
to load, however, so it's quite practical to use the whole server as a syntax
checker.



=== Compressing the Area Files

It is possible to run DD4 with a single combined, compressed area file. I mean,
don't?  But you COULD.

Here's how to do this on a *nix system:

(1) In 'area.lst', remove the last line (the '$' line).

(2) Execute the command:

	cat `cat area.lst` | compress > all_area.Z

(3) Edit 'area.lst' again.  Insert a '-' at the beginning of every line.
    Do not put any spaces between the '-' and the file name.  Put the last
    '$' line back at the end of the file.

(4) Edit 'start_dd4'.  Change the line:

	../src/dd4 $port >&! $logfile

    to:

	zcat all_area.Z | ../src/dd4 $port >&! $logfile

(5) Test the changes so far.  DD4 should start up normally, although it
    may take a few seconds longer to zcat everything.

Now you can remove all the original *.are files.

Notice that all of the compression and decompression takes place outside of the
DD4 server.  Thus, you can substitute any archiving program of your choice, as
long as it can write its output to standard output.

You can recover the original areas simply by running 'uncompress all_area.Z'
and dissecting them out of all_area.

From the server's point of view, when an area file name starts with '-', it
simply reads standard input for the area, terminating at '#$' as usual (but
without closing standard input).  Diagnostic messages are given with the full
name (e.g. '-arachnos.are'), but the line number will be reported as zero.

You can freely mix areas from standard input with ordinary area files.  Thus,
you could compress all the DD4 standard zones into a file such as dd4_area.Z,
prefixing them with '-' in 'area.lst'.  Then you could add your own areas
anywhere in the file (beginning, middle, end, wherever your areas need to go),
and omit the '-' on the lines for your areas.

The server will take a little longer to load with compressed area files,
because 'zcat' needs time to run.  This is offset by a reduction in time spent
opening disk files.  After loading, the server has all of the area database in
memory and never rereads the files.  Thus, there is zero performance impact
on server operation after loading.



=== Memory Usage

In order to simplify the code, the EnvyMud server has a fixed maximum size on
strings in the area database.  This size is defined at the beginning of 'db.c'
'db.c' with a '#define' statement.  As of the last update of this document, the
size is:

    #define  MAX_STRING 6000000

Right now we're using about 5400000 bytes, so you couldadd a few more areas
without touching the server at all.  The server will tell you when the string
table overflows, and you can simply increase the maximum limit and recompile.
The immortal 'memory' command will show you memory usage from within the game.

There is no other limit on area sizes or memory usage.

We decided to use a fixed size because it simplifies our job.  It also allows
significant performance improvements.

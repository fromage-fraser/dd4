=== 1. Introduction [[scribe-introduction]]

_DD Area Scribe_ or _Scribe_ is a tool for producing formatted area files for the Dragons Domain Envy-style MUD. DD area files retain the Envy MUD format, with changes to the `#AREA` header information and the addition of new variables and flag values to other sections.

Scribe is a script that reads a simplified text source file containing all area information, validates the information, and if no serious errors are found, outputs a formatted area file. Scribe is written in Perl and is run from the command line (see Section 2).

Scribe was written as an alternative to writing area files by hand or by using the existing Windows tool _MZF_. The advantages and disadvantages of each of these systems might be summarised:

==== Writing areas by hand

Laborious; lots of redundant variables to include. Unsafe; no error or format checking.

==== Using the MZF tool

Easy to use; convenient and simple user interface. Format and variable checking provides some safety. Buggy; contains known bugs and bizarre behaviours. Incompatible with DD; MZF does not contain DD's special flags and values; output requires hand-editing. Win16/32 executable only.

==== Using the Scribe tool

Fairly laborious; all data hand written, although in a friendly, human-readable format. Safe; variable checking and correct formatting. Compatible; contains all DD special variables and flags. Requires Perl 5 for compilation.

Scribe meets writing areas by hand and using MZF midway, providing full DD-server compatibility and error checking, but not including a simple to use graphical interface.

=== 2. Usage [[scribe-usage]]

Producing an area file with Scribe involves the following steps:

==== 1. Source file is written

The area source file contains all of the relevant information to be included in the final, correctly formatted area file. It is a text file with a simple, human-readable format that is easy to edit. Information can be added to the source file in any order.

==== 2. Scribe is used to check the source file and write the area

Scribe is used to process the area source file. It reads through the source file checking for obvious formatting errors and then validates this information, filling in any missing variables where it can. If there are serious errors then Scribe will indicate where they occur in the source file and then exit. If there are no serious errors, then the area is formatted and written to file.

Scribe is a Perl script that is run from the command:

`scribe.pl` _<source file> <destination file>_

For example,

[source, text]
----
scribe.pl kahsis.src kahsis.are
----

Area files traditionally have the `.are` extension. Both source and destination files must be indicated for the script to run. Scribe will create a backup copy of any existing destination file.

=== 3. What's Perl? [[scribe-perl]]

If you are not able to run Perl but would like to use this script to produce your areas, you can write your source files and send them to one of the DD Immortals, who will test the file and inform you of any errors.

=== 4. Producing source files [[scribe-source-files]]

The area source file consists of discrete blocks of data that each define area information (area name, author, etc), one mob (mobile, creature), one room, one object, one mobile reset, one object reset, one shop or one help file entry. Some reset information (e.g. shutting doors and mob special functions) are included in the above blocks. Blocks may occur in any order within the source file.

A *block* consists of a *header* indicating the type of data it defines, followed by a list of *field* and *value* pairs. Fields are short keywords representing room, object, mobile or area variables. A block is terminated by the start of another block or the end of the source file.

*Headers* are single words preceded by a dollar sign `$` and occupy one line. Field keywords and values are separated at least one space or tab (one tab is nice). Field/value pairs occupy one line unless they define multiple-line text blocks, in which case they are terminated by a line containing a single tilde `~`. You should not terminate single line strings of text with a tilde: these will be automatically added by Scribe.

Blocks have the following format:

[source, text]
----
$header
field1          value1
multiple_line_field
<lines of text>
~
field2          value2
...
fieldN          valueN
----

For example, the following block defines the name, short name, long name, description, sex, affect flags, vnum, level and act flags variables for a mobile:

[source, text]
----
$mob
nm  octopus
sh  an octopus
lo  An octopus crawls along the coral.
de
The octopus' slimy body is purple with bright red blotches.
It crawls over the coral, its tentacles writhing horribly.
~
sx  female
aff hide sneak
vn  1
lv  5
act scavenger wimpy stay_area
----

(Field/value pairs for each type of block are discussed in detail in Section 5 onwards.)

Field/value pairs can be arranged in any order within the block. Multiple definition of the same field can be made, although only the last instance will be used. The dollar sign `$` at the beginning of a line indicates the beginning of a new block, so should be avoided.

Your source file will consist of a series of blocks of any type in any order. Use your favourite text editor to produce the source file. All text before the first block header is ignored, so you can add comments if you wish. Your source file must contain an *$area* block in order to be compiled without error.

Source file format:

[source, text]
----
Any number of comments at the start of the file.
$area   <area header information>
$...    <mobile, room, object, etc blocks as desired>
----

You may add comments at any point in your area file by prefixing them with a non-alphanumeric symbol that is not a dollar sign `$`, e.g. `#`, `;` or whatever symbol you prefer.

[source, text]
----
. This is a comment
# So is this
; The line below is a header
$mob
. This is a comment within a $mob block
----

==== Note

Make sure that you hard-wrap lines of text in multi-line text blocks to under 80 columns, i.e. supply a carriage-return at the end of every line. Make sure your text editor isn't soft-wrapping your text!

=== 5. Area header and base vnum definition [[scribe-area-header]]

The *area header* block defines the `#AREA` section of the final area file. It describes the name and author of the area, and character access information. One definition is required, or your source file will produce errors.

==== Note on Vnums

_Vnums_, or _virtual numbers_, are the unique identification numbers for the mobiles, rooms and objects in your area. No blocks of the same type (mobs versus rooms versus objects) may share the same vnum; blocks of different types may share a particular vnum. Vnums are indicated as relative numbers in the area source file (usually beginning at zero).

Scribe uses _relative vnums_: the vnums used in the source file are numbered from 0 upwards. A base vnum is defined in the area header block and is used to calculate absolute vnums from the relative values:

[.text-center]
`Final vnum in area file = base vnum + relative vnum`

If you have been allocated a range of vnums from the DD Immortals for use in your area (e.g. 2600-2799), use the lowest vnum as your base (2600), and number your mobs, rooms and objects from zero upwards. If you haven't been given a range of vnums, you should still number mobs, rooms and objects from zero up, and just use any value for your base value. The use of a base value allows you to easily renumber your area if necessary, e.g. when you are finally given some to use by those lazy Imms.

If you need to use vnums for rooms, mobiles or objects that are not defined in the same source file (i.e. are defined in other areas), you need to use temporary holding values and manually edit the formatted area file produced by Scribe.

*Header:* `$area`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `au`
| author
| text
| `ti`
| title
| text
| `ls`
| lower level suggested
| number
| `us`
| upper level suggested
| number
| `le`
| lower level enforced
| number
| `ue`
| upper level enforced
| number
| `bv`
| base vnum
| number
|===

*`au` — Author*

_Line of text_

The person or people responsible for writing the area.

*`ti` — Title*

_Line of text_

The name of the area. Don't make it too long (25 characters maximum).

*`ls us` — Suggested level range*

_Number: 0 or higher_

The suggested level range for travelling to your area, as shown in the online _AREAS_ command. Use these values to indicate what level of character would profit from visiting your area; don't use them to indicate the lowest and highest level mobs (1, 100 is fairly unhelpful).

*`le ue` — Enforced level range*

_Number: 0 or higher_

The level range for permitted entry to your area. Characters outside this range may not access the area and get the ‘God prevents you from entering there’ message when they try.

Note: only the lower level limit is currently enforced.

*`bv` — Base vnum*

_Number: 0 or higher_

The base value used to calculate absolute vnums from relative vnums. Note that if your area links to other areas in the MUD and you want to be able to have these links active while you build, it may be best to set this to 0 and use absolute vnums in your .src file, for convenience’s sake.

*Example*

[source, text]
----
$area
ti  The Planet Vulcan
au  Mr Spock
ls  75
us  90
le  0
ue  100
bv  2600
----

=== 6. Recall header [[scribe-recall-header]]

The *recall header* block defines the `#RECALL` section of the final area file. It provides the author with an opportunity to override the default recall room location for a player who is adventuring in the area.

*Header:* `$recall`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `rl`
| recall location
| number
|===

*`rl` — Recall location*

_Number: vnum of a room in the MUD_

The vnum of a room a character in this area should recall to by default. Does not have to be in the current area. If the character has multiple recalls available and is using a non-default one, they will recall there, and not to the #RECALL location.

*Example*

[source, text]
----
$recall
rl  27347
----

=== 7. Area special header [[scribe-area-special]]

The area special block defines the #AREA_SPECIAL section of the area file. This section can be used to add supported area-wide features.

*Header:* `$special`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `af`
| area flags
| keyword list
| `xp`
| experience modifier
| number
| `rm`
| reset message
| text
| `rs`
| reset sound file path
| text
| `rv`
| reset sound volume
| number, 0–100
| `am`
| area ambient sound file path
| text
| `av`
| area ambient sound volume
| number, 0–100
| `mu`
| area music file path
| text
| `mv`
| area music volume
| number, 0–100

*`af` — area flags*

_Line of text_

Flags that produce area-wide effects. They include:

[source, text]
----
school  area is a MUD SCHOOL (new character
    beginning area)
no_quest    no mobs in this area may be auto-quest
    targets
hidden  the “areas” command will not show this area,
    and DD’s mapmaker will not generate maps
    for it
safe    pkilling cannot happen in this area
no_teleport a player cannot teleport into this area
no_magic    magic cannot be used in this area
----

[source, text]
----
E.g.    af  hidden no_teleport safe
----

*`xp` — experience modifier*

_Number: 0 or higher_

An area-wide contribution to the mobile XP percentage. `100` is the neutral
area value, `50` is half and `200` is double at this percentage stage when no
other contributions alter the total. Normal resets also include the existing
special-function and equipment adjustments; the creature archetype's
`xp_mod` is added to that same percentage rather than multiplied separately.
See <<scribe-template-xp,Archetype XP bonuses and penalties>> for the combined
calculation and the existing minimum-reward qualification.

[source, text]
----
E.g.    xp  125
----

*`rm` — reset message*

_Line of text_

A custom reset message for the area (seen by players and imms in an area when it resets, or by an imm using the ‘reset’ command).

[source, text]
----
E.g.    rm  Water swirls through the ruins.
----

*`rs` — area reset sound file path*

_Line of text_

An optional replacement for the default one-shot notification sound played when the area reset message is shown. The path is relative to the MUD audio directory, must contain no spaces, and should normally begin with notify/.

If this field is omitted, the default reset sound is: notify/area_reset.mp3

[source, text]
----
E.g.    rs notify/area/swamp_reset.mp3
----

*`rv` — area reset sound volume*

_Number: 0 to 100_

Source volume for the area reset notification sound. A value of 0 disables the reset sound for this area. Values from 1 to 100 override the default source volume. If this field is omitted, the default volume of 60 is used. The rv field may be used without rs to change the volume of the default reset sound. The final volume is scaled by the player's master and notification volume settings.

[source, text]
----
E.g.    rv 55
----

*`am` — area ambient sound file path*

_Line of text_

Relative path to an ambient sound file to use for atmospheric sound for the area. This will play throughout the area on loop unless a room sound file exists.

[source, text]
----
E.g.    am ambient/area/crypt.mp3

----

*`av` — area ambient volume*

_Number: 0 to 100_

Volume setting for ambient loop. Will be scaled by player master volume level.

[source, text]
----
E.g.    av 25
----

*`mu` — area music sound file path*

_Line of text_

Relative path to a music sound file to use for background music for the area. This will play throughout the area on loop unless a room music file exists, and independently of the ambient sound layer.

[source, text]
----
E.g.    mu music/area/crypt.mp3

----

*`mv` — area music volume*

_Number: 0 to 100_

Volume setting for the area music loop. It is scaled by the player's master and music volume settings.

[source, text]
----
E.g.    mv 25
----

*Example*

[source, text]
----
$special
af hidden no_teleport
xp 125
rm Water swirls through the ruins.
rs notify/area/ruins_reset.mp3
rv 55
am ambient/area/crypt.mp3
av 25
mu music/area/crypt.mp3
mv 20
----

[[scribe-mobile-inheritance]]
==== Body species, creature archetypes and individual mobile flags

A *body species* describes a broad physical form, such as `humanoid`,
`elemental` or `farm_mammal`. A *creature archetype* is a more specific entry
in the server's `mob_table`, such as `goat` or `fire_elemental`, which refers
to one body species. A particular `#MOBILES` entry supplies the individual
mobile's descriptions, level, flags and other area-authored values.

For the ACT, AFF and body-form flags already supported by Scribe, the server
resolves the layers in this order:

[source,text]
----
body-species defaults XOR creature-archetype masks
    = inherited template

inherited template XOR original individual #MOBILES mask
    = effective prototype flags

copy prototype flags when an NPC is created
    = initial live flags
----

Runtime spells, equipment, resets and immortal commands can subsequently
change the live instance. They do not repeatedly reapply XOR to that instance.
The original individual masks are retained separately from the prototype's
effective values.

===== Adding and removing inherited flags

For one flag, the individual mask has the following meaning:

[cols="<1,<1,<1,<3",options="header"]
|===
| Inherited bit | Individual bit | Effective bit | Result
| Off | Off | Off | Leave the flag absent.
| Off | On | On | Add the flag.
| On | Off | On | Keep the inherited flag.
| On | On | Off | Cancel the inherited flag.
|===

`none`, `zero`, `0`, or omission of an existing flag field means an empty
*individual* mask. On a templated mobile, that inherits the corresponding
template unchanged; it does not clear all inherited flags. On an untemplated
mobile, the inherited mask is zero, so the existing ordinary flag behaviour
is preserved.

Example: suppose an archetype supplies `ACT_UNDEAD`. Its individual Scribe
field `act undead` cancels that classification. The same field gives an
untemplated mobile the undead classification. The meaning depends on the
selected template, not on the flag word alone.

[source,text]
----
# Keep an inherited undead flag and add sentinel:
act sentinel

# Cancel an inherited undead flag and add sentinel:
act undead sentinel
----

These lines illustrate the individual mask only. The archetype must also be
selected in the generated area entry as described below. They do not define
or select a skeleton archetype by themselves.

Within a single field, flags form one mask. Repeating a word within the field
is not another inheritance layer. Repeating the same source field replaces
its earlier definition; it is not an additional XOR operation. The server
logs bits cancelled at the template-to-individual boundary, rather than
requiring builders to discover those cancellations through combat.

===== Protected engine flags

`ACT_IS_NPC` is always enabled on an NPC prototype. It cannot be cancelled
through inheritance. `AFF_CHARM` is always removed from the initial prototype:
charm is a runtime relationship, not a safe way to create a pre-charmed mobile
by listing `aff charmed`. Scribe can recognise the word, but recognising it
does not override this server restriction.

===== Body-form masks and migration

The body-form mask contains both `BODY_*` restrictions and positive `PART_*`
flags. They are independent bits. To remove an inherited heart represented by
`PART_HEART`, cancel that bit and add `BODY_NO_HEART` where the intended
anatomy requires it. Adding a negative flag does not automatically remove a
positive part flag, and removing a positive part flag does not necessarily
satisfy the engine's negative-flag anatomy tests.

The Scribe `bf` keyword list remains the list documented below; template
support does not automatically add every `PART_*` C constant as a Scribe
keyword. A combined non-negative decimal mask can be used for supported bits
whose textual names are not in Scribe. Consult `merc.h` for their values.

When moving an existing mobile onto a template, inspect its old individual
flags before regenerating the area. Duplicated defaults now mean cancellation.
For example, the elemental template supplies `BODY_NO_ARMS` and
`BODY_NO_LEGS`. An old individual body mask of `12` (4 + 8) cancels both;
changing that individual mask to `0` retains the inherited restrictions.

Do not put the final expanded flags back into `act`, `aff`, or `bf` on export.
Doing so can cancel the very defaults the editor intended to preserve.

[[scribe-template-selection]]
===== Selecting a creature archetype


*`archetype` — Creature archetype*

_One registered name; optional_

This chooses an entry from `mob_table` in `server/src/mob.c`. That entry
selects its broad body species and supplies the inherited creature defaults.
It is independent of `rnk` and of the `sp` / `sp2` / `sp3` special overrides.
It does not define a new template or select a body species directly.

Accepted archetype names are:

[cols="<2,<4",options="header"]
|===
| Name | Meaning
| `reserved` | Existing neutral placeholder archetype; no meaningful creature defaults.
| `goat` | Existing goat archetype, based on `farm_mammal`.
| `fire_elemental` | Existing fire-elemental test archetype, based on `elemental`.
| `skeleton` | Skeletal humanoid archetype.
| `zombie` | Mindless undead humanoid retaining flesh, organs and limbs.
| `ghoul` | Corporeal undead with claws, fangs, a long tongue, sleep/charm immunity and contact paralysis.
| `ghast` | Corporeal undead with carrion stench and stronger contact paralysis that also affects elves.
| `ghost` | Development-stage intelligent, inorganic undead with no physical heart, brain, guts or corpse. Starts semi-material and inherits nonmagical immunity; supported weapon/shield contacts use the phase exceptions below. Spell-phase rules and active abilities remain unfinished.
| `wight` | Intelligent corporeal undead humanoid with dark resistance, holy vulnerability, poison/sleep/drain immunity and dedicated `spec_wight` life drain.
| `wraith` | Intelligent supernatural undead spirit with no biological corpse or internal organs, dark resistance, holy vulnerability, poison/sleep/drain/nonmagical immunity and active life-drain/phasing behaviour.
| `spectre` | Stronger supernatural undead spirit using the wraith passive spirit physiology, with stronger life drain and the same ethereal/semi-material phasing model.
| `mummy` | Intelligent corporeal undead humanoid with dark resistance, holy and fire vulnerability, poison/sleep/drain immunity, and `spec_mummy` fear plus contact mummy rot.
| `banshee` | Intelligent undead spirit with dark resistance, holy vulnerability, poison/sleep/drain/nonmagical immunity, a semi-material starting phase and `spec_banshee` wail.
| `death_knight` | Intelligent corporeal undead warrior with dark resistance, holy vulnerability, poison/sleep/drain immunity and `spec_death_knight` martial/spell combat behaviour.
|===

The script normalises an explicit name to lowercase and validates it against
`%mob_archetype`. Empty, unknown and multiple-word values are errors. Do not
use `none`, `inherit`, a numeric index or a body-species name such as
`humanoid` in this field. To retain the old no-selection behaviour, omit it.
An explicit `reserved` selects the existing neutral placeholder.

The Scribe registry is a companion list of C-table names, not a second source
of creature traits. Consult `server/src/mob.c` for the authoritative definitions.
Scribe validates the selected name; it does not expand template traits into
individual source fields.

[source,text]
----
archetype fire_elemental
rnk elite
----

The above source fields produce:

[source,text]
----
< fire_elemental~ elite~
----

Omitting `rnk`, or writing `rnk common`, produces:

[source,text]
----
< fire_elemental~ common~
----

The output line is emitted whenever an archetype is explicitly supplied,
even with the default rank. Its placement remains after any mobile programs
and before teacher declarations and the optional foley/override fields.
Do not put the literal `< ...~ ...~` line in a Scribe source block.

[cols="<2,<2,<4",options="header"]
|===
| Archetype input | Rank input | Generated selection line

====== Anatomy is a resolved XOR result

The skeleton's body-form input is an XOR mask over `humanoid`, not its final
body mask. It contains the five existing positive organ bits in order to
cancel them, and four previously absent BODY flags in order to add them.
Do not add retained head, arm, leg, hand, foot or finger bits to that XOR
mask: doing so would remove the inherited bits.

In particular, the current `HAS_HEART` and `HAS_EYES` macros allow their
positive PART flags to establish presence despite the negative BODY flags.
The skeleton therefore removes `PART_HEART` and `PART_EYE` as well as setting
`BODY_NO_HEART` and `BODY_NO_EYES`. This prevents contradictory effective
anatomy. `PART_BRAINS`, `PART_GUTS` and `PART_EAR` are also removed.

The current `can_see` and `can_see_obj` routines do not treat `BODY_NO_EYES`
as `AFF_BLIND`. This archetype adds no blindness effect and can use existing
visibility rules. It gains no infrared, invisible-detection or universal
perception ability. Darkness and other existing visibility restrictions
remain relevant. Eye-targeting routines which consult `HAS_EYES` reject it.

`BODY_NO_SPEECH` makes `CAN_SPEAK` false in routines that use that check.
`BODY_INORGANIC` invokes DD4's non-living physiology rules; it does not
make the creature an `ACT_OBJECT`.

====== Corpses and generated body parts

The skeleton is not `ACT_OBJECT`, so normal corpse creation uses
`ITEM_CORPSE_NPC`, not `ITEM_REMAINS`. Its undead provenance adds
`ITEM_UNDEAD`. It does not have `BODY_NO_CORPSE`; normal loot handling is
preserved. Inorganic physiology changes applicable death descriptions and
makes random death-generated parts `ITEM_TRASH` and inedible. Such parts
retain undead provenance. Their appearance is random, not guaranteed on
every kill. The no-heart result excludes a heart from the death-part candidate list.
Hands, feet and fingers are eligible through the retained PART flags.

Identification and immortal inspection reveal undead provenance. Random
death drops are separate from combat dismemberment and corpse harvesting.

====== Individual exceptions

An ordinary skeleton should not repeat its inherited `undead` or `mindless`
flags in source. Omission, `none`, or zero preserves those inherited bits.
Repeating either keyword is an intentional XOR cancellation.

An individual knight can add sentinel and a warrior special without changing
the archetype:

[source,text]
----
archetype skeleton
rnk elite
act sentinel
sp spec_warrior
----

The special gives access through the existing enabled-special checks. It does
not create equipment, guarantee a particular skill action, or alter anatomy.
Equip weapons through the normal area resets when the routine needs them.

An aware skeleton can cancel only mindlessness:

[source,text]
----
archetype skeleton
aff mindless
----

It remains undead and retains its physiological immunity masks. The live
`mset <mobile> mindless off` command is a temporary instance-only equivalent.

To cancel only undead classification:

[source,text]
----
archetype skeleton
act undead
----

This is an explicit authoring exception, not a rule that having a soul removes
undead status. Such an individual still has skeletal anatomy and mindlessness
unless those are separately changed. Generated corpse provenance follows the
resulting classification, not its name.

An obsidian variant changes blunt vulnerability into blunt resistance:

[source,text]
----
archetype skeleton
res blunt
vuln blunt
----

These emit `MobResists 16` and `MobVulnerabilities 16`. The first adds blunt
resistance and the second removes inherited blunt vulnerability. Both are
needed; adding only resistance leaves contradictory effective categories.
The resulting resistance mask is `262256`, with holy-only vulnerability
`131072`. Piercing, slashing and dark resistance remain inherited.

====== Feeding and contact paralysis

`spec_ghoul` enables idle corpse feeding and a separate natural-contact
effect. It does not itself assign undead classification or anatomy.

For feeding, the routine requires an awake NPC in a room, with a head,
not fighting, waiting, charmed, held or dazed. It uses the existing
`spec_fido` NPC-corpse handling: corpse contents fall into the room and the
corpse is removed. This supplies no healing. Player corpses, remains and
loose body parts are not selected. An undead-tagged NPC corpse is still
eligible under that feeding rule.

Contact paralysis is checked only after an unarmed claw or bite produces
positive damage through the ordinary attack path. A weapon, spell, ordinary
miss, successful defense or zero-damage outcome does not trigger it. The
corresponding natural part must still be usable, and both characters must
remain alive in the same room.

When the set contains `spec_ghoul` but no `spec_ghast`, the combined live
weights of its `spec_ghoul` slots give the contact-effect activation chance.
At the default 100%, every qualifying hit proceeds to the target checks
and saving throw. There is no additional 25% roll. At zero weight that
contact effect is disabled. If both contact specials are configured, one
weighted choice selects the ghoul or ghast effect, or no contact effect;
see <<scribe-ghast-archetype,Ghast archetype>>. Other special routines are
not called by this check. Normal weighted scheduling still governs idle
feeding. Necromantic control does not suppress contact effects on qualifying
attacks; charm still suppresses scheduled feeding.

Characters whose actual race field is elf, wild elf or drow are exempt from
`spec_ghoul` contact paralysis. They are not exempt from `spec_ghast` contact
paralysis. The exemption does not come from names or descriptions. Other DD4 targets
use their existing `RES_PARALYSIS` defense and saving throw; there is no
blanket mindless, undead or inorganic exemption and no `RES_MAGIC` tag on
this contact effect.

On failure to save, the victim receives the existing paralysis affect type
with `AFF_HOLD | AFF_DAZED`, lasting 3 to 8 combat-pulse intervals. This
prevents movement and ordinary actions through the existing flags. There
is no added Dexterity, movement-maximum or no-recall modifier. Duration is
counted globally on combat pulses, including when the victim is no longer
fighting; the hourly affect update skips this particular form of paralysis.
A held, dazed or already-paralysed target is not refreshed by more touches.

`mstat` and `affects` display this duration in combat rounds. The existing
Freedom spell removes it by stripping the paralysis affect. The regular
cast Paralysis spell retains its original behavior and duration rules.

Special invocation counters count scheduled calls, not contact saves or
successful paralysis effects. Disabling a contact special prevents new
applications of its effect, but does not remove an existing paralysis or
recalculate stored live XP. Another configured contact special remains
independently eligible.

Disable both feeding and contact effects with:

[source,text]
----
archetype ghoul
sp none
----

Remove the inherited claw and fang declarations with:

[source,text]
----
archetype ghoul
atk claws fangs
----

These are XOR cancellations. Feeding can still occur, but those parts no
longer qualify for ordinary natural attacks or contact paralysis.

The implementation uses DD4's normal level-scaled damage and attack count;
it does not enforce a tabletop two-claw/one-bite sequence. Ordinary kills
do not automatically create new ghouls, and this archetype does not create
a protection-circle ward. Ghast-specific stench and cold-iron rules are not
granted to an ordinary ghoul.

Naming a mobile a ghoul does not select this archetype. Animate Dead uses
its separately configured servant prototypes.

====== Mixing contact effects

With only `spec_ghast` configured at 100%, every qualifying contact makes
at most one save check for its 5-to-10-round effect. Setting its weight to
zero disables it. Duplicate slots contribute their combined weight.

When both ghoul-family specials are configured, their weights are mutually
exclusive alternatives. For example:

[source,text]
----
archetype ghast
sp spec_ghast
sp2 spec_ghoul
sp3 spec_fido
spchance 20 30 50
----

A qualifying contact has a 20% chance to select ghast paralysis, a 30%
chance to select ghoul paralysis, and a 50% chance to produce no contact
effect. Selection is followed by the relevant racial check and one save.
The remaining weight never executes the other special from within combat.
If an elf is selected for the ghoul version, that result has no paralysis;
the code does not retry the ghast version. A resisted selection also ends
the attempt. Normal weighted scheduling still invokes configured specials
under each routine's own conditions.

Replace the default with weaker ghoul behaviour using `sp spec_ghoul`, or
clear the whole set using `sp none`. These changes do not alter the creature's
archetype, anatomy or resistance masks. Live `mset` special edits have the
same separation and do not recalculate stored XP.
Neither form of special replacement removes the inherited `AFF_STENCH` trait.

rolls. Cancel it independently with `aff stench` in an individual ghast's
source. `sp none` disables feeding and contact paralysis, but leaves stench
in place.

Ordinary strikes from weapons tagged `ex cold_iron` add `RES_COLD_IRON`
to their existing attack mask. The ghast's vulnerability therefore uses
the standard resistance rules, not a separate double-damage multiplier.
See <<scribe-cold-iron,Cold iron>> for supported attacks and overrides.

automatically convert victims into undead or change Animate Dead's servant
prototypes.

The wraith uses the same distinction between permanent physiology and live
ghost phase established for ghosts. `BODY_INORGANIC` and the removed organs
describe the creature's body; `ghost_phase` determines supported physical
contact accessibility.

The template does not assign `AFF_NON_CORPOREAL`. That existing affect retains
its separate meaning and is not the NPC wraith-state mechanism.

`RES_NONMAGIC` supplies the ordinary mundane-contact barrier. Because the
default live phase is `semi_material`, the existing phase-aware contact
resolver applies the established rules: ordinary mundane weapons are blocked,
mundane silver is admitted with its conditional half-damage response, and
magical weapons are handled normally unless another resistance applies.

The archetype supplies `spec_wraith` as its active behaviour.

While outside combat and able to act, a wraith whose live phase is
`semi_material` automatically changes to `ethereal`. This transition uses
`set_ghost_phase()` only; it does not alter ACT, AFF, anatomy or resistance
masks.

When an ethereal wraith is fighting a valid opponent, its next eligible
special-function opportunity changes it to `semi_material`. That
materialisation consumes that special opportunity, so life drain is not also
attempted on the same invocation.

While fighting in `semi_material`, `spec_wraith` reuses `spec_wight` for its
life-drain behaviour. The drain therefore retains the existing 20 percent
attempt chance and DD4 Energy Drain's `RES_DRAIN | RES_MAGIC` resistance,
saving, `edrain` cooldown and resource/XP behaviour.

An explicit live or inherited `ghostphase none` disables automatic wraith
phase transitions. It does not disable `spec_wraith` life drain and does not
remove the independently inherited `RES_NONMAGIC` immunity.

After combat ends, an eligible semi-material wraith returns to `ethereal` on
its next special-function opportunity.

Charm, hold, daze, wait state, unconsciousness and death prevent both automatic
phase transitions and life-drain attempts.

A fully ethereal wraith cannot participate in the currently supported ordinary
weapon/shield physical contacts with an unphased character, even when the
weapon is magical. Once semi-material, the established mundane, silver and
magical contact rules apply.

These phase transitions currently affect the supported physical-contact rules
only. They do not by themselves make the wraith invisible, change room
movement, assign `AFF_NON_CORPOREAL`, or make unrelated spell/effect paths
phase-aware.

The wraith remains vulnerable to holy effects and resistant to dark effects.
Poison, sleep and drain immunity use the ordinary resistance machinery.

A default wraith leaves no biological corpse. Existing equipment and coin
handling continue through the normal no-corpse death machinery.

The archetype does not use the broad legacy `spec_cast_undead`.

Individual `#MOBILES` ACT, AFF, body, resistance, vulnerability, immunity,
special and phase inputs retain their normal override semantics. Cancelling
`RES_NONMAGIC` remains separate from changing `ghostphase`.

Existing world wraiths are not automatically converted merely because this
archetype exists.

| Retained morphology | Humanoid limbs and sensory capabilities remain available.
| Natural attacks | No additional attack-part mask.
| Resistance | `RES_DARK`.
| Vulnerability | `RES_HOLY`.
| Immunities | `RES_POISON`, `RES_SLEEP`, `RES_DRAIN`, `RES_NONMAGIC`.
| Initial phase | `semi_material`.
| Special functions | `spec_spectre`: stronger life drain plus automatic ethereal/semi-material phasing.
| Archetype XP adjustment | Zero. `spec_spectre` contributes +15 percentage points through the special-function XP weighting.
|===

The implementation plan groups wraiths and spectres together for active
life-drain/incorporeal behaviour but does not prescribe a numeric difference
between them. DD4 therefore keeps the same passive spirit physiology and phase
model, while `spec_spectre` supplies the stronger active progression.

`BODY_INORGANIC`, `BODY_NO_HEART` and `BODY_NO_CORPSE` describe permanent
physiology. The inherited physical heart, brain and guts are cancelled.
Removing the physical brain does not imply `AFF_MINDLESS`.

The template does not assign `AFF_NON_CORPOREAL`. Supported physical
accessibility continues to use the separate live `ghost_phase` state.

`RES_NONMAGIC` supplies the mundane-contact barrier. In `semi_material`,
ordinary mundane weapons are blocked, mundane silver uses the established
conditional half-damage exception, and magical weapons are handled normally
unless another configured response applies.

`spec_spectre` uses the same automatic phase transitions as `spec_wraith`.
Outside combat an eligible semi-material spectre becomes `ethereal`; when an
ethereal spectre enters combat, its next eligible special opportunity changes
it to `semi_material` and that materialisation consumes the opportunity.

While fighting in `semi_material`, or while explicitly configured with
`ghostphase none`, a spectre has a 30 percent chance at each eligible special
opportunity to attempt Energy Drain. This is stronger than the wraith's
20 percent chance but reuses exactly the same Energy Drain implementation:
`RES_DRAIN | RES_MAGIC`, saving behaviour, the `edrain` cooldown and the
existing resource/XP consequences remain authoritative.

A target already carrying a positive `edrain` timer is not drained again.
`IS_UNDEAD()` targets are not subjected to this living-target drain.

An explicit live or inherited `ghostphase none` disables automatic phase
transitions without disabling the spectre's life drain or removing its
separate `RES_NONMAGIC` immunity.

Charm, hold, daze, wait state, unconsciousness and death suppress both phase
transitions and life-drain attempts.

The spectre is resistant to dark effects and vulnerable to holy effects.
Poison, sleep and drain immunity use the normal resistance machinery.

A default spectre leaves no biological corpse. Existing no-corpse equipment
and coin handling remain authoritative.

The archetype does not use the broad legacy `spec_cast_undead`. The existing
`spec_spectral_minion` is a Bastion-specific teleporting special and is not the
spectre archetype behaviour.

Individual `#MOBILES` ACT, AFF, body, resistance, vulnerability, immunity,
special and phase inputs retain their normal override semantics.

Existing world spectres are not automatically converted merely because this
archetype exists.

The implementation plan identifies mummy rot and fear as active mummy behaviour
and specifically notes that a mummy may be vulnerable to fire. The passive
profile therefore retains the established corporeal-undead package: dark
resistance, holy vulnerability, and poison, sleep and drain immunity, with
`RES_FIRE` added to the vulnerability mask for the mummy-specific weakness.

The template does not add `AFF_MINDLESS`. Skeletons and zombies are the normal
mindless examples; mummies retain a mind unless an individual mobile overrides
that through the ordinary AFF XOR layer.

The mummy remains corporeal. It does not inherit `RES_NONMAGIC`, ghost phase,
`AFF_NON_CORPOREAL`, silver/cold-iron interaction or spirit contact rules. No
body restriction is inferred merely from mummification: ordinary humanoid
anatomy remains inherited.

====== `spec_mummy`: fear

While fighting, awake and otherwise able to act, `spec_mummy` has a 20 percent
chance on each selected special-function opportunity to attempt the existing
Fear spell against its current opponent. The existing Fear implementation
remains authoritative: mindless and object-like targets are ineligible, and
`RES_MAGIC | RES_PSYCHIC` plus the normal saving-throw machinery determine
whether the victim is forced to flee.

A failed or resisted Fear attempt still consumes that selected special-function
opportunity. `spec_mummy` does not use the broad legacy `spec_cast_undead`
spell list.

====== Mummy-rot contact

Mummy rot is a separate contact effect associated with `spec_mummy`; it is not
an alias for the player `fleshrot` spell.

Only a successful damaging ordinary NPC attack made without a wielded weapon is
a qualifying mummy-rot contact. Weapon attacks do not transmit the disease.
The shared natural-contact marker now covers all weaponless NPC natural attacks;
existing ghoul/ghast paralysis remains restricted to its claw and bite attack
types.

The live `spec_mummy` slot weight gates the contact capability. With the default
single special at 100 percent, each qualifying damaging contact then has a
25 percent chance to attempt mummy rot. Lower builder-configured `spec_mummy`
weights reduce that contact opportunity proportionally.

Objects, inorganic targets and victims already carrying mummy rot are not
eligible. A contact attempt uses `RES_POISON | RES_CURSE | RES_DARK`, with no
`RES_MAGIC` category because this is a physical supernatural disease rather
than a cast spell. Player Resist Toxin and Bonus Exotic defenses are also
honoured.

On failure to resist, the victim receives `mummy rot` for 6 to 10 normal affect
ticks and suffers a -2 Constitution modifier. Once per character update while
the effect remains, the rot also inflicts level-scaled damage between
`max(2, level/10)` and `max(low, level/5)`. The effect does not stack or refresh
while already present.

`mummy rot` has its own skill-table identity and wear-off message. `cure poison`
removes it. The Cure Poison eligibility check also now recognises standalone
`fleshrot`, correcting the previous case where Fleshrot could be stripped only
when another poison/nausea condition was present at the same time.

A normally killed mummy follows the ordinary corporeal death path and may leave
a corpse. The existing undead-provenance machinery marks that corpse as
originating from an undead creature.

Individual `#MOBILES` ACT, AFF, body, resistance, vulnerability, immunity,
special and special-weight inputs retain their normal override semantics.
Disabling `spec_mummy` removes both its scheduled Fear behaviour and new
mummy-rot contact attempts; it does not remove a mummy-rot affect already on a
victim.

Existing world mummies are not automatically converted merely because this
archetype exists.

====== Anatomy and XOR inheritance

The ghost body-form entry is an XOR mask against the humanoid body species.

`PART_HEART`, `PART_BRAINS` and `PART_GUTS` are already inherited from
humanoid, so repeating them in the archetype cancels those physical parts.
The three added BODY flags are absent from the humanoid defaults.

Both heart changes are required: adding `BODY_NO_HEART` without cancelling
`PART_HEART` would still satisfy the current `HAS_HEART()` macro.

The retained head, limb and sensory properties preserve existing capability
checks. They do not establish whether the ghost is physically material.
The live phase and supported contact rules determine that interaction;
retaining a head does not authorise every biological finishing effect.

`PART_BRAINS` describes a physical body part. Its absence does not imply
mindlessness. Supported mental effects continue to use their existing
mindless-target checks and resistance rules.

====== Death and existing physiology checks

`BODY_NO_CORPSE` uses the existing no-corpse death handling. The default
ghost produces neither a corpse nor death-generated body parts. Equipment
and coins follow the existing no-corpse handling; do not add a separate
ghost extraction or death path.

`BODY_INORGANIC` and the absence of a heart participate in existing
physiology checks where those checks are already used. This stage does
not claim that every biological spell has been normalised, and it adds
no blanket resistance or immunity.

====== Individual overrides and development limits

The existing individual XOR rules apply. An ordinary test definition
should not repeat inherited flags unless cancellation is intended.
In particular, `act undead` cancels the inherited undead classification.

Undead classification and body properties remain independent. Cancelling
`ACT_UNDEAD` does not automatically restore organs, make the creature
organic or enable corpse generation.

Names and descriptions do not select this archetype. It must be selected
explicitly with `archetype ghost`.

The existing `AFF_NON_CORPOREAL` flag retains its current player-form
behaviour. This stage neither assigns it to ghosts nor changes its users.

The sections below provide inherited initial settings, immortal live
control and supported weapon/shield defences. No player materialisation
command, fear, aging, possession or compulsory special is introduced.
Existing world mobiles and Animate Dead prototypes remain unchanged.

[[scribe-ghost-phase]]
===== Ghost phase: initial defaults and live state

WARNING: Phase configuration now affects the explicitly supported
weapon/shield contacts. It does not yet govern every spell, projectile,
status effect or direct resource change. The development ghost template
must not replace production ghosts or Animate Dead servants yet.
Phase alone does not change visibility or permit passage through walls.

`CHAR_DATA.ghost_phase` remains a per-instance enumeration. It is not an
ACT/AFF/RES bitfield or an affect record. This stage adds a separately
stored initial value to the template/prototype layers, then copies that
value into each new NPC. Later changes to the live value do not rewrite
its prototype or the values of other NPC instances.

[cols="<2,<1,<4",options="header"]
|===
| Phase | Numeric diagnostic | Meaning in this development stage
| `none` | 0 | No ghost phase selected. This is not an assertion that a creature is physically material.
| `ethereal` | 1 | Supported physical contact cannot cross to/from an unphased character.
| `semi_material` | 2 | Supported contacts can interact with both sides; weapon-barrier exceptions apply as described below.
|===

====== Initial-value inheritance

The order is body species, creature archetype, individual #MOBILES setting,
resolved prototype, then the newly created live NPC. Phase is a scalar
selection: a later explicit value replaces an earlier one. Never combine
phase values through OR or XOR. The existing flag fields retain their
independent XOR rules.

In C, both raw template layers accept `MOB_TEMPLATE_UNSET` for inheritance
or one of the three `GHOST_PHASE_*` constants. If neither layer specifies
a value, the existing scalar resolver produces `none`. The individual
area setting has the same distinction between inherit and explicit zero.

All four current body species explicitly supply `GHOST_PHASE_NONE`.
The ghost archetype supplies `GHOST_PHASE_SEMI_MATERIAL`; the other seven
archetypes inherit. This semi-material starting value is a DD4 development
choice for controlled contact testing, now read by the supported contact paths.
There is no archetype-name, vnum, ACT_UNDEAD or special-function check in
mobile creation that independently assigns a phase.

[cols="<3,<4",options="header"]
|===
| Stored member | Role
| `species_type.initial_ghost_phase` | Raw body-species default, or `MOB_TEMPLATE_UNSET`.
| `mob_type.initial_ghost_phase` | Raw archetype replacement, or `MOB_TEMPLATE_UNSET`.
| `MOB_TEMPLATE_DATA.initial_ghost_phase` | Resolved template initial phase.
| `MOB_INDEX_DATA.area_ghost_phase` | Original individual setting; omission is `MOB_TEMPLATE_UNSET`.
| `MOB_INDEX_DATA.initial_ghost_phase` | Effective prototype initial phase after individual replacement.
| `CHAR_DATA.ghost_phase` | Current live value, initially copied from the prototype for an NPC.
|===

`validate_mob_ghost_phases()` checks both raw C tables, including values
hidden by an override or belonging to an unused entry. Invalid table
values stop boot at this validation step rather than silently becoming
an ordinary default. Existing unrelated validators are not changed.

====== Scribe field and area-file representation

An optional mobile source field selects the starting phase:

[source,text]
----
archetype ghost
ghostphase ethereal
----

Accepted values are `inherit`, `none`, `ethereal` and `semi_material`.
Scribe normalises valid names to lowercase. Numbers, bit expressions,
abbreviations and multiple phase names are not accepted as phase values.
An omitted field or explicit `inherit` emits no override; the server
resolves the template. Explicit `none` is preserved, not treated as
omission.

[cols="<2,<3",options="header"]
|===
| Source field | Exported optional mobile tail
| Omitted, or `ghostphase inherit` | No `MobGhostPhase` field.
| `ghostphase none` | `MobGhostPhase none`
| `ghostphase ethereal` | `MobGhostPhase ethereal`
| `ghostphase semi_material` | `MobGhostPhase semi_material`
|===

A hand-authored area file may also contain `MobGhostPhase inherit`.
The loader reads one named value and rejects invalid phase tokens with
the mobile's vnum in its error. These lines have no trailing tilde.
Place the field in the ordinary optional mobile tail, after any mob
programs, archetype/rank selection and teacher entries, alongside the
other metadata fields and before the next `#` record.

[source,text]
----
< ghost~ common~
MobGhostPhase none
----

This example retains the ghost anatomy and classification while explicitly
clearing its initial phase. Conversely, cancelling ACT_UNDEAD through the
existing XOR input does not automatically clear the independently selected
phase or restore physical organs. A non-ghost prototype can explicitly
select a phase for a development test without changing its classification.
Scribe does not pre-expand any server template defaults into the file.
Selecting `none` does not remove the ghost's separately inherited
`RES_NONMAGIC` immunity. Cancelling that immunity is a separate XOR edit.

====== Initialisation and lifetime

`clear_char()` continues to initialise the live field to `GHOST_PHASE_NONE`
for fresh and recycled character structures. Player loading retains this
neutral value. `create_mobile()` subsequently copies the validated
prototype initial value once, after assigning the prototype metadata.
This direct initial assignment does not use the live setter, because
creation is not yet a fully initialised live-state transition.

A new unoverridden ghost therefore starts at `semi_material`; an ordinary
unconfigured NPC starts at `none`. Recreating a destroyed NPC restores its
prototype initial phase, not the previous instance's last live phase.
An ordinary area reset that leaves an existing NPC alive does not reset
its phase. There is still no timer, expiry or automatic phase transition.

The runtime value is not written back to an area record or player file.
The new persistent area field describes only the initial value. Existing
area files require no conversion, and no existing world or summoned-mob
prototype is converted by this stage.

====== Live editing and diagnostics

The existing authorised live commands are unchanged:

[source,text]
----
mset <mobile> ghostphase none
mset <mobile> ghostphase ethereal
mset <mobile> ghostphase semi_material
----

Live `mset` does not accept `inherit`: choose the desired live state.
Names remain case-insensitive and must match a complete listed value.
Invalid input leaves the state unchanged. The live setter still rejects
PCs, deleted characters and characters at POS_DEAD. It does not require
ACT_UNDEAD or a particular archetype.

`mstat` separates the body-species setting, archetype setting, resolved
template, individual #MOBILES override, effective prototype initial phase
and current live phase. Raw settings can display `inherit`; resolved and
live values display their phase names and expose invalid values rather
than concealing them. The report identifies weapon/shield contact
coverage and warns that other effect paths are not phase-aware yet.
No player mstat profile is changed.

Use `set_ghost_phase()` for later live transitions, not the initial-value
fields. Neither initial phase selection nor a live phase change edits
ACT, AFF, body or resistance masks, grants player immunity, toggles
AFF_NON_CORPOREAL, changes followers, stops combat or invokes a special.
Silver does not become magical. Supported contact checks read the live
phase at the attempt; the setter does not rewrite resistance masks.
Unconverted spells, death/reward processing and movement remain separate.

Use disposable prototypes with no unrelated individual overrides. Compare
a ghost with the field omitted, a ghost with `ghostphase inherit`, a ghost
with `ghostphase none`, a ghost with `ghostphase ethereal`, and an ordinary
unconfigured non-ghost. Their initial values should be semi-material,
semi-material, none, ethereal and none respectively.

export. Snapshot the ACT/AFF/body/RES values before and after; the phase
selection must not change them. Then use the contact tests below;
passing them does not establish coverage of every spell or status rider.

[[scribe-ghost-contact]]
===== Ghost phase: weapon and shield contact

WARNING: This is an incremental physical-contact integration, not a complete
AD&D ghost or a general planar system. Keep production world ghosts and
Animate Dead servants unchanged until the remaining effect paths are covered.
The contact matrix and its combination rules below are explicit DD4 rules.

====== Scope and source identity

Supported damage paths are ordinary TYPE_HIT-based weapon and natural strikes,
weapon Backstab/double Backstab, Circle/second Circle, Thrust, Joust, Riposte,
Counterbalance strikes, armed Whirlwind, Smash, weapon Hurl and Decapitate.
Existing body-part/objectless variants in that named dispatch remain physical
contacts with their existing skill categories, not equipment-derived silver.

The selected weapon or shield continues to supply material and magic flags.
Joust uses its selected lance; Hurl uses its selected object; Smash uses the
shield. No inventory scan or primary-weapon guess is introduced. The object
helpers now receive the attacker as well as the victim so a fully ethereal
attacker cannot use a covered contact against an unphased target.

Assassinate, Decapitate, shield Hurl, Stun and Smash use the same contact gate
before their success side effects. Stun's full response still adjusts one
success roll. Decapitate, Assassinate and shield Hurl retain their material-only
chance scaling after the full contact gate; the conditional half-damage silver
exception is not an additional material-only chance multiplier.

Inorganic NPCs cannot receive Stun's biological knockout. Decapitate rejects
an NPC that is both inorganic and no-corpse. The default ghost therefore cannot
produce a severed head even from an otherwise admitted magical/silver impact.
Assassinate's existing inorganic exclusion remains. These changes grant no
new PC immunity or trait and do not prohibit all attacks on inorganic NPCs.

====== Contact matrix

Only an NPC's ghost_phase participates; PC phase storage is ignored here.
Existing AFF_NON_CORPOREAL behaviour is neither repurposed nor changed.
The matrix governs reachability before the ordinary masks are resolved.

[cols="<2,<2,<4",options="header"]
|===
| Attacker | Target | Supported physical contact
| none | none | Existing resistance handling.
| none | ethereal | Cannot reach, regardless of silver or magical weapon.
| ethereal | none | Cannot reach; materialising is required first.
| none | semi_material | Resolve the actual source, including the silver exception below.
| semi_material | none | Existing resistance handling against the unphased target.
| ethereal or semi_material | ethereal or semi_material | Shared ethereal-side contact; the target's nonmagical barrier does not block this contact. Other matching immunities still apply.
|===

This does not grant all ethereal attackers a magical attack against every
creature. The shared-side exception is restricted to a phased target. No
phase is inferred from name, vnum, ACT_UNDEAD, special function or equipped
item. The stored phase can be assigned to a test NPC independently of its
archetype, using the existing authoring or live controls.

====== Mundane barrier and silver exception

The ghost archetype now inherits RES_NONMAGIC immunity through the ordinary
mask machinery. It does not acquire a permanent RES_SILVER resistance.
For a default semi-material ghost struck from the unphased side:

[cols="<3,<3",options="header"]
|===
| Actual contact source | Response at the resistance stage
| Mundane, not silver | Immune.
| Mundane cold iron only | Immune; cold iron is not a bypass.
| Mundane silver (including silver plus cold iron) | Resistant: half positive damage, minimum one at this stage.
| Magical weapon, including magical silver | Normal unless another explicit resistance/immunity applies.
|===

get_contact_resistance_result() implements this without modifying a character,
prototype, object or stored mask. When the relevant RES_NONMAGIC immunity is
present, a shared-side contact or eligible silver contact omits RES_NONMAGIC
from that one local lookup. Silver is not marked magical. Other categories,
such as slash, silver and cold iron, remain in the lookup; an immunity to any
of those still wins.

Admitted mundane silver contributes one conditional resistance, not an extra
multiplier. Any matching vulnerability cancels it under DD4's existing
non-stacking convention, even when another resistance also matches. Several
matching resistances never quarter the hit. Magical silver does not receive
this conditional resistance. Removing RES_NONMAGIC through an individual
XOR override removes both that barrier and its conditional silver penalty;
any separately configured material response still applies normally.

Explicit ghostphase none does not remove RES_NONMAGIC. With that phase, the
special ghost contact exceptions are inactive and ordinary masks still apply.
Phase reachability, such as an ethereal target being unreachable from none,
is distinct from the mundane-weapon immunity and is not removed by clearing
the RES_NONMAGIC mask.

====== Damage integration and diagnostics

The private damage_internal() interface now has an explicit physical_contact
argument, independent of its existing natural_contact ghoul/ghast-rider flag.
Only the documented contact entry points set it. Generic damage() does not
infer a weapon contact just because a spell has RES_MAGIC or physical damage.

For a positive hit, damage_internal() resolves one contact-aware or ordinary
response and applies it once with apply_resistance_result_to_damage(). Its
normal resistance wrapper remains available to unconverted callers. The
vulnerability arithmetic saturates at INT_MAX rather than overflowing;
normal damage ranges retain the previous arithmetic.

Phased ordinary miss paths also carry contact context. An impossible contact
is identified as immune even at zero damage so it does not trigger the old
zero-damage mob disarm/trip branch through an unreachable target. Ordinary
unphased misses retain their old routing. Positive-damage riders still require
positive damage. Existing XP, death, equipment and corpse processing is not
replaced, and attempts may still establish combat through existing handling.

mstat separates initial and live phases and now states that only supported
weapon/shield paths are connected. mset changes only the live phase; the next
supported contact reads that value. Changing phase does not stop combat,
recreate the NPC or clear its stored immunity. A fresh NPC is required after
reloading a changed prototype to obtain its new inherited mask.

====== Exclusions and acceptance checks

This does not add phase-aware spell targeting, spell status handling, ranged
ammunition, generic damage() callers, Target/trauma, Snap Neck, direct HP
subtraction or all legacy contact riders. Those paths keep their existing
mask-based rules. RES_NONMAGIC already participates in some nonweapon effect
masks, including Transfix and Howl; the new ghost mask also affects those
ordinary lookups. No magical-spell versus magical-weapon equivalence is implied.
A physical contact against a phased target lacking both source categories
defaults to nonmagical; an absent category cannot bypass the mundane barrier.
Automatic transitions, player phasing, fear, aging and possession remain later
work. An ethereal test NPC is not yet protected from every unconverted path.

Use fresh disposable ghost instances and compare plain, silver, cold-iron,
magical and magical-silver weapons. Verify inherited immunity 8192 and no
stored silver resistance. Repeat with explicit silver immunity and with a
matching vulnerability plus resistance. Test both attack directions for none
versus ethereal, and shared-side contacts between phased NPCs. Confirm an
individual RES_NONMAGIC XOR cancellation and the separate ghostphase none
case. Inspect both NPC instances and all masks before/after live phase edits.
Use an organic, head-bearing phased test NPC for finisher/status phase tests;
the default ghost is intentionally ineligible for biological knockout/severing.

===== How inherited fields are used

The resolved template contains ACT, AFF, body form, attack parts, resistance
masks, HP/damage/critical/haste modifiers, dimensions, size, language, special
names and the archetype XP adjustment. The presence of a value in a template
diagnostic is not proof that it is already applied to a live mobile.

ACT, AFF, body and resistance masks resolve when prototypes load. Each new
NPC receives its own copy; runtime checks read that live state.

Natural attack parts select an ordinary attack type when an NPC's attacking
weapon slot is empty. They do not add attacks, equipment or skill permissions.

The <<scribe-mobile-hp-modifier,HP modifier>> adjusts initial HP. The
<<scribe-mobile-damage-modifier,damage modifier>> adjusts NPC `one_hit()`
attacks. <<scribe-mobile-combat-modifiers,Critical and swiftness modifiers>>
set initial scores. <<scribe-mobile-dimensions,Dimensions>> and
<<scribe-mobile-language,language codes>> store raw metadata.
The <<scribe-weighted-specials,three special slots>> use weighted selection.

For the template scalar fields using `MOB_TEMPLATE_UNSET`, an archetype value
inherits when it is unset; otherwise it replaces the body-species value.
Literal zero is an explicit scalar value. If neither layer supplies a value,
the resolver returns zero. These sentinels are C-table conventions: do not
write `MOB_TEMPLATE_UNSET` in a Scribe source file. Use `hpmod inherit` or
`dammod inherit` for those scalars, and `critmod inherit` / `swiftmod inherit`
for score-point adjustments. The dimension fields also accept `inherit`.
`language` uses the same inheritance distinction. These scalar groups
have different meanings; language codes are not scores or bitmasks.

For template special names, `NULL` inherits, an empty string clears, and a
non-empty string replaces. Names resolve per slot; percentages inherit as a complete vector.
Legacy standalone `sp` remains a singleton override; extended `sp2`, `sp3`
and `spchance` use slot-aware records. `xp_mod` keeps its independent additive
rule, described in <<scribe-template-xp,Archetype XP>>.

[[scribe-mobile-undead]]
==== Undead mobile classification

`act undead` represents `ACT_UNDEAD` (`BIT_30`, decimal `1073741824`). It
classifies an NPC as undead; it does not automatically assign an alignment,
anatomy, mindlessness, spell immunity, or an entire skeleton/vampire behaviour
package. Supply those traits separately through the relevant flags and
archetype definition.

The common server test is `IS_UNDEAD(character)`. For NPCs it checks the live
`ACT_UNDEAD` flag. For PCs the currently supported case is
`SUBCLASS_VAMPIRE`; this work does not introduce a general `PLR_UNDEAD`
builder flag.

Use the same <<scribe-mobile-inheritance,XOR rule>> when an archetype already
supplies `ACT_UNDEAD`. `mstat` is the way to distinguish an inherited flag,
an individual cancellation and the actual live classification.

[source,text]
----
$mob
vn  7
nm  revenant watchman
sh  a revenant watchman
lo  A revenant watchman stands motionless beside the gate.
de
The watchman's ruined face turns slowly towards you.
~
lv  25
act undead sentinel
----

This example directly flags an otherwise untemplated mobile. It does not
select a new creature archetype or grant any implicit resistance package.

Object provenance uses the separate `ex undead` flag, documented under
<<scribe-object-undead,Undead objects and generated remains>>. Giving an
object that flag does not make its holder undead.

[[scribe-mobile-mindlessness]]
==== Mindlessness


`aff mindless` represents `AFF_MINDLESS`, `BIT_49`, decimal
`562949953421312`. It is a trait in the affected-by mask, independent of
intelligence scores, anatomy and undead classification. The skeleton
archetype supplies it as a default; other creatures can add or cancel it
through their individual `aff` masks.

[source,text]
----
aff mindless
----

The ordinary AFF inheritance rules apply. An untemplated individual can add
the bit directly. When a template already supplies it, repeating `mindless`
in the individual `aff` mask cancels it. Omission, `none`, or a zero input
mask leaves an inherited bit unchanged. No additional area-tail field is
introduced; the flag is exported in the existing affected-flags position.
Do not export an expanded effective mask as the individual mask.

===== Mind-dependent effects

The following existing routines reject a mindless target before applying
their mind-dependent effect:

[cols="<2,<5",options="header"]
|===
| Category | Routines covered
| Mental attacks
| Synaptic Blast, Inflict Pain, Mind Thrust, Psionic Blast, Psychic Crush,
and each otherwise eligible target of Ultrablast.
| Influence and cognitive effects
| Charm Person, Awe, Ego Whip, Feeblemind, Psychic Drain, Fear, Confusion,
and Possession.
| Cognitive enhancement
| Combat Mind also requires a mind to affect.
| Combat abilities
| Transfix and targeted Howl reject a mindless target. Aura of Fear cannot
prevent a mindless attacker's attack; that passive check is silent.
|===

Checks are in the individual effect routines, so direct calls by mobile
specials or item casting receive the same gate. The shared C predicate is
`is_mindless(character)`; `reject_mindless_target(actor, target)` adds a
failure message for an explicitly attempted effect. These helpers do not
perform a saving throw, consume a random roll, or mutate resistance masks.

Mindlessness does not grant `RES_PSYCHIC` immunity. It rejects the specific
mind-dependent effects listed above. Ballistic Attack is classified as
`RES_NONMAGIC | RES_BLUNT` and is not rejected by mindlessness. Its damage
therefore interacts with blunt resistance or vulnerability. Project Force,
Detonate and Disintegrate retain their normal handling. Do not
assume that every psionic ability requires a mind in its target.

Ordinary target selection, spell costs, lag and any surrounding retaliation
remain in place. Rejecting a mental effect is not a ceasefire or a refund.
Other creatures affected by an area spell retain their existing processing.
Domination's existing unconditional return is not removed or re-enabled.

===== Inspection, editing and boundaries

The existing `mstat` AFF layers show the named flag at template, individual,
prototype and live levels. Standard affect name formatting is also updated.
The bit does not fabricate `RES_CHARM` or `RES_PSYCHIC` in resistance rows.

[source,text]
----
mset <mobile> mindless on
mset <mobile> mindless off
----

These NPC-only live commands set or clear only the mindlessness bit. Repeating
`on` or `off` is idempotent. Invalid values change nothing. Prototype data,
other flags, other live copies, existing followers and future spawns remain
unchanged. The predicate itself reads a character's flag, including a player
flagged by other existing mechanisms; no player is flagged automatically.

Changing the trait does not retroactively remove existing effects or undo
possession, charms, equipment or follower relationships. It prevents the
listed future effects while present. No generic `affect_to_char()` or
`add_follower()` rejection is added: necromantic servants can still use the
existing follower/AFF_CHARM machinery without being susceptible to Charm
Person.

There is no duration associated with the directly stored trait bit. It is
not created as a timed spell affect. Existing whole-character resets or
explicit flag edits retain their normal authority over character state.
Mindlessness does not automatically remove a brain part, disable special
functions, reduce INT/WIS, grant poison/sleep/paralysis immunity, prevent all
movement or flight, or change speech permissions. Physiology and the
skeleton immunity package remain separate.


[[scribe-mobile-stench]]
==== Carrion stench

`aff stench` supplies `AFF_STENCH`, `BIT_50`, decimal `1125899906842624`,
to an NPC. The ghast archetype inherits this trait by default. A directly
stored trait has no timer and is independent of special-function weights.

[source,text]
----
aff stench
----

The existing individual AFF XOR rules apply. On a ghast, this same input
cancels its inherited stench rather than reinforcing it:

[source,text]
----
archetype ghast
aff stench
----

Do not repeat the flag on an ordinary ghast. Omitted or zero individual
AFF input preserves it. On an otherwise unflagged mobile it adds the trait.
There is no new optional area-tail field or archetype-specific source field.

===== Emission and exposure

The room is the range unit. Stench does not spread through exits or depend
on visibility, lighting, line of sight, or fighting status. Each combat
pulse checks living engine characters in the room, even outside combat.
This is a same-room gameplay approximation, not a measured ten-foot radius.

A source must be a non-deleted, physically interacting NPC with positive
HP and the live `AFF_STENCH` flag. A sleeping, held, dazed, waiting or charmed
source still emits the passive odor. An objectlike NPC can be an emitter
when deliberately given the trait. Non-corporeal or non-interacting sources
do not emit through this system. Loose corpse objects are not emitters.

Targets with `AFF_STENCH` are exempt. Inorganic, non-corporeal, objectlike,
non-interacting and dead targets are also excluded. Undead classification,
mindlessness and elven race alone do not grant protection. There is no
ally or safe-room exemption; the odor is environmental and does not itself
start combat, cause damage, consume mana, or assign a killer flag.

The first detected exposure uses the highest-level eligible emitter for one
`RES_POISON` resistance/save check. For players, existing Resist Toxin and
Bonus Exotic checks are applied before the generic save. A failed defense
applies `APPLY_HITROLL -2`; a successful defense applies a zero-modifier
record. Both records remember the result, preventing fresh saves every pulse.
Additional emitters do not stack penalties or cause extra saves while that
exposure record remains. A later, stronger emitter likewise does not reroll
an existing exposure.

The penalty changes ordinary attack accuracy through the existing hitroll
modifier. It does not apply poison damage, the Nausea spell, attribute or
saving-throw penalties, paralysis, or a general spell-failure chance.
The exposure record has no affect bits: affected targets never start
emitting odor merely because they inhaled it.

===== Recovery and inspection

The internal affect is named `stench exposure`. It has no useful cast action.
`mstat` and the detailed player `affects` display show the hitroll modifier
and the text `while exposed`, rather than a duration in game hours. A zero
modifier means the initial defense succeeded; it is not an attack penalty.

The exposure record is removed immediately when its target leaves a room.
It is removed on the next combat pulse if no eligible emitter remains, or
if the target becomes ineligible. Removal reverses only the stench's own
modifier and preserves unrelated affects and bonuses. It is safe to clear
an already-cleared record.

Emitter departure, destruction or live flag removal ends nearby exposure
at the next pulse when no other source remains. Exposure changes between
pulses are observed at the next check. Returning to an affected room allows
a new save. Explicitly stripping the exposure affect also allows a new check
on the next pulse; ordinary poison cures do not target this separate affect.

The source's AFF layers and the target's exposure record are separate:
`AFF_STENCH` means emission, whereas `stench exposure` records a successful
or failed defense. No new special invocation is counted by this passive
check. Stench does not change the stored experience modifier.

Live editing is NPC-only:

[source,text]
----
mset <mobile> stench on
mset <mobile> stench off
----

These set or clear only the live emitter flag. They do not toggle it on
repeated use, edit the prototype, alter other flags, or change future spawns.
Invalid settings change nothing. Nearby exposure is reconciled at the next
combat pulse. Removing or replacing `spec_ghast` does not remove this flag;
use the source AFF mask or this targeted command for an odorless ghast.


[[scribe-individual-resistances]]
==== Individual resistance fields


*`res` — Resistance XOR mask*

_Keyword list or combined non-negative decimal mask_

_Default: omitted; inherit without change_

Adds or cancels bits in the inherited resistance mask.

*`vuln` — Vulnerability XOR mask*

_Keyword list or combined non-negative decimal mask_

_Default: omitted; inherit without change_

Adds or cancels bits in the inherited vulnerability mask.

*`imm` — Immunity XOR mask*

_Keyword list or combined non-negative decimal mask_

_Default: omitted; inherit without change_

Adds or cancels bits in the inherited immunity mask.

Each field is resolved independently. A zero mask inherits that category; it
does not clear it. A mobile without an archetype has zero inherited masks,
so these fields can directly give it resistances, vulnerabilities or immunities.

Scribe accepts keywords separated by spaces, or one combined decimal number:

[source,text]
----
res cold sonic
vuln fire
imm poison paralysis
----

Use the <<scribe-resistance-flags,resistance keyword reference>> below.
`none` and `zero` are aliases for an empty mask. A blank, explicitly supplied
field is invalid. Numeric masks must contain only defined resistance bits.
There is no `RES_NONE` C macro; zero is the empty mask.

A compact expression such as `1|256` is server `.are`/`mset` syntax, not a
Scribe keyword list. For Scribe use `fire poison` or the combined number
`257`. Repeating the same Scribe field uses its last definition.

===== Generated area fields and placement

[cols="<1,<2,<4",options="header"]
|===
| Scribe field | Generated `.are` field | Meaning
| `res` | `MobResists` | Individual resistance XOR mask.
| `vuln` | `MobVulnerabilities` | Individual vulnerability XOR mask.
| `imm` | `MobImmunes` | Individual immunity XOR mask.
|===

The generated fields follow the ordinary mobile data, any mob programs,
the optional archetype/rank line and teacher entries. They may accompany the
optional `FStep...` fields, before the next mobile entry or `#0` terminator.
They do not use a tilde terminator.

[source,text]
----
< fire_elemental~ elite~
MobResists 2
MobVulnerabilities 1
MobImmunes 1
----

This is an *area-file tail*, not a Scribe source block. The values above add
cold resistance, add fire vulnerability, and cancel inherited fire immunity.
It assumes the selected template starts with fire immunity and no conflicting
cold resistance state.

The `.are` parser accepts a decimal mask or decimal values joined by `|`
without spaces. Values within that one mask are ORed together. Repeating an
area field replaces its earlier individual mask; it does not toggle the
inherited state a second time.

Negative numbers, unknown bits, overflow and malformed expressions are
rejected. For example, `4194304` is bit 22 and is undefined in this revision.

===== Moving a category between resistance states

Suppose the inherited template is immune to fire. This Scribe input changes
that category to vulnerability:

[source,text]
----
vuln fire
imm fire
----

The repeated fire bit in `imm` removes inherited immunity; the fire bit in
`vuln` adds vulnerability. Overlap between these *input* masks is intentional.
Only the fully resolved state must be free of contradictory categories.

Adding `vuln fire` alone leaves the inherited immunity active and creates a
conflicting effective definition. The boot diagnostic reports the conflict;
the established runtime resolver still gives immunity precedence.

Raw masks remain builder input. The server resolves a prototype once and
copies its effective masks into independent live instances. It does not
re-XOR the template on each attack. Live edits therefore affect only the
chosen instance, as described under <<scribe-mobile-diagnostics,inspection
and live editing>>.

[[scribe-individual-attack-parts]]
==== Individual attack-part masks


*`atk` — Attack-part XOR mask*

_Keyword list or combined non-negative decimal mask_

_Default: omitted; inherit without change_

An attack-part mask records natural offensive body features separately from
`bf` (general morphology). The server first resolves body-species and archetype
attack parts with XOR, then XORs the individual `atk` mask over that result.
The raw input, effective prototype and each live instance remain separate.

The accepted values are the existing `PART_*` combat group in `merc.h`, not
new low-order flags. In particular, these numbers must not be treated as
resistance values or converted through a 32-bit integer.

[cols="<2,<2,<2",options="header"]
|===
| Scribe keyword | C flag | Decimal bit
| `claws` | `PART_CLAWS` | 8589934592
| `fangs` | `PART_FANGS` | 17179869184
| `horns` | `PART_HORNS` | 34359738368
| `tusks` | `PART_TUSKS` | 68719476736
| `tail` | `PART_TAILATTACK` | 137438953472
| `sharp_scales` | `PART_SHARPSCALES` | 274877906944
| `beak` | `PART_BEAK` | 549755813888
| `haunch` | `PART_HAUNCH` | 1099511627776
| `hooves` | `PART_HOOVES` | 2199023255552
| `paws` | `PART_PAWS` | 4398046511104
| `forelegs` | `PART_FORELEGS` | 8796093022208
| `feathers` | `PART_FEATHERS` | 17592186044416
| `husk_shell` | `PART_HUSK_SHELL` | 35184372088832
| `none`, `zero` | Empty mask | 0
|===

Here `tail` means `PART_TAILATTACK`, not the general `PART_TAIL` morphology bit.
Other general body parts, negative `BODY_NO_*` flags and undefined bits are not
accepted in `atk`. Use `bf` for general positive body-part declarations.

[source,text]
----
atk claws fangs
----

Scribe writes the combined decimal value:

[source,text]
----
MobAttackParts 25769803776
----

Use the optional field in the mobile's final tail, after any mob programs,
archetype/rank line and teacher declarations. It can accompany `FStep...` and
`MobResists`/`MobVulnerabilities`/`MobImmunes`. Do not add a tilde terminator.
The server also accepts a compact numeric OR expression such as
`8589934592|17179869184`; Scribe source uses keywords or one combined number,
not that expression syntax.

Within one field, repeated parts are ORed together, not toggled. Repeating the
field itself uses its last value. An omitted field, `atk none` or `atk 0` leaves
the inherited mask unchanged; it does not erase inherited natural features.

For example, if the template supplies claws, `atk claws fangs` removes the
inherited claws and adds fangs. If the template supplies no attack parts,
the same input adds both. An untemplated mobile has an empty inherited mask.

===== Live inspection and editing

`mstat` adds an ATTACK PART group with Template, #MOBILES, XOR removed,
Prototype and Live rows. Cancelled inherited parts are also reported at load
time. A separate table validator rejects no source silently: it reports
undefined raw species/archetype attack bits, including bits that would cancel
out when the two layers are XORed. Malformed optional area masks stop loading
with a vnum-specific error.

[source,text]
----
mset filler attack_parts 17179869184
mset filler attack_parts 0
----

These NPC-only commands replace the entire live mask. Zero clears the live
mask. They do not modify the raw input, template, prototype, another live
instance or future spawns. The command uses decimal masks or compact `|`
expressions, not Scribe keywords. Unknown bits are rejected.

===== Behavioural boundary

The live `atk` mask supplies ordinary natural-attack types as described below.
It does not add attacks per round, create body-part equipment, grant skills
or specials, or alter player forms. A zero mask does not prevent fighting.
It also contributes declared physical parts to death-generated drops; see
<<scribe-death-parts,Death-generated body parts>>.

`bf` and `atk` remain separate. An attack-part declaration does not repair
missing anatomy or overwrite a body-form restriction. Eligibility is computed
from the current body form and relevant trauma flags without modifying the
configured attack-part mask.


[[scribe-death-parts]]
==== Death-generated body parts

At death, a creature that leaves a corpse can also drop one loose physical
part into the room. The random death-message roll gives a five-in-sixteen
opportunity to create a part; if at least one kind is eligible, one distinct
kind is chosen uniformly. This is not one roll per flag, and multiple-head
or multiple-limb flags do not create several objects on the same death.

Eligibility uses the live `bf` mask and, for NPCs, the physical PART features
in the live `atk` mask. It reads the already-resolved values, so inherited
parts count and cancelled declarations are removed. The legacy `HAS_HEAD`, `HAS_HEART`,
`HAS_ARMS`, `HAS_LEGS` and `HAS_TAIL` rules preserve ordinary body defaults
for old definitions without explicit PART flags. Removing only a positive
head, heart, arm or leg bit therefore does not remove its legacy default;
also set the corresponding negative BODY flag. Other kinds require an
explicit PART declaration. `no_corpse` prevents all random part drops.

A declared PART feature is eligible for death drops even when it is not a
currently usable natural attack. Feathers and shell therefore work, and
injury-related attack penalties do not erase the stored declarations.
This does not change combat's separate anatomy requirements or track exact
numbers of limbs already lost in combat.

| `head`, `many_heads` | Head
| `heart` | Heart
| `arms`, `many_arms` | Arm
| `two_legs`, `four_legs`, `many_legs` | Leg
| `tail`, `tail_attack`; also legacy `has_tail` | Tail
| `brains` | Brain
| `guts` | Bundle of entrails
| `hands` | Hand
| `feet` | Foot
| `fingers` | Finger
| `ear` | Ear
| `eye` | Eye
| `long_tongue` | Long tongue
| `eyestalks` | Eyestalk
| `tentacles` | Tentacle
| `fins` | Fin
| `wings` | Wing
| `scales`, `sharp_scales` | Patch of scales
| `claws` | Claw
| `fangs` | Fang
| `horns` | Horn
| `tusks` | Tusk
| `beak` | Beak
| `haunch` | Haunch
| `hooves` | Hoof
| `paws` | Paw
| `forelegs` | Foreleg
| `feathers` | Feather
| `husk_shell` | Shell fragment
|===

Equivalent features in `atk` contribute the same kinds. Duplicate declarations
across the two masks, or related quantity flags, do not give that kind extra
selection weight. Ordinary, undeclared bodies retain the legacy four
head/heart/arm/leg candidates.

Every generated piece has `body_part` and a short decay timer of four to
seven object-update ticks. A source classified as undead supplies the
`undead` extra flag, including a vampire player. All inorganic-source pieces
are inedible `trash`. Organic soft pieces use food objects; hard pieces such
as claws, fangs, horns, tusks, hooves, beaks, scales, feathers and shell are
trash. These drops are not automatically usable weapons or armour.

The existing head, heart, arm, leg and tail prototypes are retained. Other
kinds use the shared generic body-part prototype, with individual runtime
keywords and descriptions. No additional per-mobile source field is needed.
`mstat` lists `Death-part candidates` without making a random roll; `ostat`
inspects the resulting object's actual type, timer and extra flags.

[source,text]
----
bf no_head no_heart no_arms no_legs tentacles
----

With no inherited parts or additional attack parts, this creature has only
a tentacle in its candidate list. To prevent all loose parts, add `no_corpse`.
The corpse's object type and loot handling remain separate from random
part generation. No repeated corpse-decay generation or harvesting command
is implied.

[[scribe-natural-attacks]]
==== Ordinary NPC natural attacks


===== Selection and weapon precedence

For each ordinary NPC attack attempt, the server uses the weapon actually
occupying that attack's weapon slot. A wielded weapon, including an existing
`ITEM_BODY_PART` weapon, retains its own attack type and magical/nonmagical
classification. If the slot is occupied by another item, this new natural
fallback is not used.

When the slot is empty and the attack would otherwise receive its default
ordinary type, one usable configured attack part supplies that type. The
choice occurs before the existing to-hit roll: the attack can still miss.
The existing hit chance, damage calculation, defenses, attack scheduling,
death handling and immunity messaging remain in use.

Each eligible part is one equally selectable candidate. Horns and tusks
remain separate candidates even though both map to piercing. Selection is
not based on the victim's weaknesses. The resistance mask describes only the
chosen attack, not a union of all configured parts.

An empty mask, or a mask with no currently usable offensive parts, falls back
to the previous generic `hit`. This does not suppress combat; `ACT_NO_FIGHT`
and existing action restrictions remain separate. Adding more parts gives
more choices, not additional attacks per round.

Player attacks/forms and explicitly supplied primary attack identifiers are
unchanged. Skill-indexed attacks retain their skill definitions. Existing
secondary-weapon scheduling remains unchanged; no unarmed off-hand attack is
newly granted to an NPC.

===== Default attack mapping

These mappings use the existing ordinary attack vocabulary.

[cols="<2,<2,<2,<4",options="header"]
|===
| Attack part | Ordinary type | Physical category | Eligibility
| `claws` | `claw` | `RES_SLASH` | A usable arm or leg group.
| `fangs` | `bite` | `RES_PIERCE` | An existing head.
| `horns` | `pierce` | `RES_PIERCE` | An existing head.
| `tusks` | `pierce` | `RES_PIERCE` | An existing head.
| `tail` | `pound` | `RES_BLUNT` | An existing tail without tail trauma.
| `sharp_scales` | `rake` | `RES_SLASH` | The configured feature; no additional limb requirement.
| `beak` | `pierce` | `RES_PIERCE` | An existing head.
| `haunch` | `crush` | `RES_BLUNT` | Usable legs.
| `hooves` | `pound` | `RES_BLUNT` | Usable legs.
| `paws` | `pound` | `RES_BLUNT` | A usable arm or leg group.
| `forelegs` | `pound` | `RES_BLUNT` | Usable legs.
| `feathers` | Not selected | None | Retained data; no ordinary offensive action supplied.
| `husk_shell` | Not selected | None | Retained data; no ordinary offensive action supplied.
|===

These objectless attacks also carry `RES_NONMAGIC`. Being undead, having an
archetype, or carrying a magical item elsewhere does not make this selected
attack magical. Fangs do not automatically poison or drain; a tail attack
does not invoke the Tailwhip skill. Feathers and a shell grant no automatic
armour or reflected damage through this feature.

===== Anatomy and trauma

The filter uses DD4's existing `HAS_HEAD`, `HAS_ARMS`, `HAS_LEGS` and
`HAS_TAIL` tests. It preserves those macros' existing positive/negative body
flag interpretation; it does not reconcile contradictory body flags.

Usable arms require arms and the absence of `AFF_ARM_TRAUMA`. Usable legs
require legs and the absence of `AFF_LEG_TRAUMA`. Because `atk` does not
specify whether claws or paws belong to hands or feet, either usable limb
group is sufficient for those two features. Hooves, haunches and forelegs
require the leg group specifically.

A tail attack requires `BODY_HAS_TAIL` or `PART_TAIL` in the live body form
and no `AFF_TAIL_TRAUMA`. An `atk tail` declaration alone does not satisfy
that combat requirement. Head-based attacks require `HAS_HEAD`. Other
combat penalties remain separate. Death-part eligibility is a separate
read of the declared parts, not of the currently usable attacks.

Filtering never removes a bit from the live mask. Removing a relevant trauma
affect or repairing the live body form makes a still-configured feature
eligible again. A complete `mset attack_parts` assignment takes effect on the
next applicable ordinary attack without changing the prototype.

===== Inspection and verification

`mstat` retains the configured ATTACK PART layers and adds:

[cols="<2,<5",options="header"]
|===
| Row | Meaning
| `Eligible` | Configured offensive parts passing the current anatomical/trauma filter.
| `Inactive` | Other configured bits, including unsupported offensive mappings or anatomy/trauma exclusions.
|===

These rows describe eligibility independently of equipment. A weapon can
still take precedence over every eligible natural part. Inspecting a mobile
does not choose an attack or consume a combat random roll.

For a deterministic test, give a suitable live NPC only `fangs`, leave its
primary weapon slot empty, and give an ordinary target live piercing immunity.
Its successful bite rolls should produce the existing immunity-contact
message. Switch the attacker to eligible claws: piercing immunity alone must
not block the slashing claw attack. Test mixed masks, an equipped weapon,
anatomical exclusion and an empty mask separately.

No Scribe syntax changes are needed beyond the merged `atk` interface. DD
Builder should describe these behaviours without changing the stored/exported
raw mask, granting skill permissions or inventing extra attacks.

[[scribe-mobile-hp-modifier]]
==== HP modifier inheritance and overrides


*`hpmod` — Individual HP percentage adjustment*

_Signed decimal integer from -99 to 2147483647, or `inherit`_

_Default: omitted; inherit the resolved body-species/archetype value_

`hp_mod` is an adjustment to the normal generated HP, not a direct HP total.
The ordinary level-derived HP and rank multiplier are calculated first.
The HP adjustment is applied once to that result:

[source,text]
----
spawn HP = floor(normal level/rank HP * (100 + effective hp_mod) / 100)
----

The final spawn result is limited to at least one hit point and at most
`MOB_SPAWN_HP_LIMIT`, defined as `INT_MAX / 100` (21,474,836 with the current
32-bit `int`). The multiplication uses a 64-bit intermediate. The upper limit
leaves room for existing integer percentage calculations; it is a spawn-time
bound, not a universal cap on every subsequent scripted or live HP edit.

[cols="<2,<4,<2",options="header"]
|===
| Effective adjustment | Meaning | Result from base HP 1000
| `0` | No percentage change. | 1000
| `25` | Increase by 25 percent. | 1250
| `-25` | Reduce by 25 percent. | 750
| `100` | Increase by 100 percent. | 2000
| `-99` | Retain one percent, subject to minimum one HP. | 10
|===

Very large accepted positive values reach the spawn ceiling rather than
wrapping around. `-100` and lower numeric adjustments are rejected; a scalar
field cannot be used to create an initially dead mobile.

===== Scalar precedence

Unlike `act`, `aff`, `bf`, `res`, `vuln`, `imm` and `atk`, `hpmod` is not XORed.
A specified value replaces the inherited adjustment; adjustments from the
three layers are not summed or multiplied independently.

[source,text]
----
body species hp_mod
    -> archetype hp_mod, unless MOB_TEMPLATE_UNSET
    -> individual hpmod, unless omitted or inherit
    -> one adjustment to normal spawn HP
----

For the table layers, `MOB_TEMPLATE_UNSET` means inherit and zero is an
explicit neutral value. If neither table supplies a value, the resolved
adjustment is zero. For the individual layer:

[cols="<2,<4",options="header"]
|===
| Input | Result when the template supplies `+50`
| Omit `hpmod` | Inherit `+50`.
| `hpmod inherit` | Inherit `+50`.
| `hpmod 0` | Replace the inherited bonus with zero: normal HP.
| `hpmod 25` | Use `+25`, not `+75` and not two multipliers.
| `hpmod -25` | Use `-25`: 75 percent of normal HP.
|===

An untemplated mobile can use `hpmod`; its inherited adjustment is zero.
The goat archetype supplies a +20% adjustment unless individually replaced.

===== Scribe and area syntax

[source,text]
----
hpmod 25
----

Scribe emits:

[source,text]
----
MobHPMod 25
----

The alternative declarations `hpmod -25`, `hpmod 0` and `hpmod inherit` emit
the corresponding values. An omitted source field emits no area declaration.
Leading plus signs and decimal leading zeros are accepted and normalised.
Use one integer, not a numeric `|` expression, decimal fraction or percent
suffix. The keyword `inherit` is case-insensitive.

`MobHPMod` belongs in the same optional mobile tail as `MobAttackParts` and
the resistance declarations, after any mob programs, archetype/rank selection
and teacher entries. It has no tilde terminator. Repeated declarations use the
last value, including a final `inherit` which restores inheritance.

The source keyword is `hpmod`, the area keyword is `MobHPMod`, and the C
member is `hp_mod`. Use the separate `archetype` field to select a template.

===== Creation and runtime changes

The original individual scalar is preserved on the prototype separately from
its resolved value. Initialisation always starts from those inputs. Spawning
copies the resolved adjustment; it never interprets the already-resolved
number as a new layer.

During normal `create_mobile()` processing, the server records:

[cols="<2,<4",options="header"]
|===
| Snapshot | Meaning
| `spawn_base_hit` | Ordinary generated HP after the rank multiplier, before `hp_mod`.
| `spawn_hp_mod` | Effective percentage adjustment applied to this instance at creation.
| `spawn_max_hit` | Initial adjusted maximum, after the minimum/ceiling bounds.
|===

These snapshots exist for inspection. They are not recalculated by `mstat`,
healing, equipment changes, or combat. Current HP starts at the initial maximum.
Existing equipment and affect handling can then change the current maximum
without being multiplied again.

A script or summon routine can replace HP after creation. The recorded spawn
values remain unchanged by that later assignment. Existing `mset hp` edits
live HP; there is no `mset hpmod` command. New instances use their prototype
defaults, not another instance's live edits.

The HP adjustment is independent of XP, damage and combat-score adjustments.

===== Validation and builder integration

Raw species/archetype HP adjustments are checked during boot. An unset value
is permitted; an out-of-range numeric value is reported and stops loading.
Malformed `MobHPMod` input also stops loading with the mobile vnum in the error.
Scribe checks the same numeric bounds using exact integer arithmetic.

`mstat` adds HP modifier layers plus the three spawn snapshots and current HP.
Use the recorded spawn base for tests: two independently generated NPCs may
have different random base HP even when they use the same prototype.


[[scribe-mobile-damage-modifier]]
==== NPC attack damage modifier


*`dammod` — Individual NPC attack damage percentage adjustment*

_Signed decimal integer from -99 to 2147483647, or `inherit`_

_Default: omitted; inherit the resolved body-species/archetype value_

===== Scope and calculation

This implementation applies `dam_mod` once to NPC attacks resolved through
`one_hit()`. It includes ordinary weapon, natural and generic unarmed attacks,
and weapon manoeuvres which actually use that function. It does not classify
an ability by its name or assume that every physical skill follows this path.

The existing attack roll and attacker-side damage calculation run first,
including the existing flat damage roll and any skill multiplier inside
`one_hit()`. A successful attack's positive damage is then adjusted before
being passed to the existing resistance, critical-hit and target-defense
machinery:

[source,text]
----
attack damage = floor(calculated one_hit damage * (100 + live dam_mod) / 100)
----

At this stage, positive damage remains at least one. A zero or negative input
is not converted into a hit by the helper. Later immunity, mitigation, or a
successful defense can still prevent damage. A penalty is not immunity, and
an arbitrarily large bonus does not bypass immunity.

[cols="<2,<3,<2",options="header"]
|===
| Live adjustment | Meaning | Result from an input of 100
| `0` | No percentage adjustment. | 100
| `25` | Add 25 percent. | 125
| `-25` | Remove 25 percent. | 75
| `100` | Double this attack's calculated damage. | 200
| `-99` | Retain one percent, subject to minimum one. | 1
|===

The multiplication uses a 64-bit intermediate. The helper bounds its result to
`MOB_ATTACK_DAMAGE_LIMIT`, defined as `INT_MAX / 1000` (2,147,483 with the current
32-bit `int`), leaving headroom for later combat arithmetic. This is an early
arithmetic bound, not a replacement for the existing final `MAX_DAMAGE` rule.
The later pipeline can further reduce or modify the amount.

Player attacks are unchanged. Independent spells, breath weapons, direct-damage
skills such as Kick, damage-over-time events and reflected/module damage are
not newly multiplied by this field merely because an NPC is involved. Effects
which already derive an amount from a triggering attack can still reflect that
attack's adjusted amount; no second multiplier is applied to them.
Skill-specific and secondary-effect behavior otherwise remains separate.

The name in the tables remains `dam_mod`. For this implementation, read it as
an attack modifier with the explicit `one_hit()` scope above, not a universal
bonus to every harmful action. It grants no attacks, changes no skill-table
entries or resistance categories, and does not execute additional specials.

===== Scalar inheritance and input

The existing body-species and archetype `dam_mod` values are resolved using
`MOB_TEMPLATE_UNSET` to inherit. An individual supplied number replaces that
resolved value; it is not XORed, added, or independently compounded.

[cols="<2,<4",options="header"]
|===
| Individual input | Result when the template supplies `+50`
| Omit `dammod` | Inherit `+50`.
| `dammod inherit` | Inherit `+50`.
| `dammod 0` | Use zero: no percentage adjustment.
| `dammod 25` | Use `+25`, not `+75` or two multipliers.
| `dammod -25` | Use `-25`.
|===

An untemplated mobile inherits a zero damage adjustment and can override it.
The goat archetype supplies +20% damage for applicable attacks.

[source,text]
----
dammod 25
----

Scribe emits:

[source,text]
----
MobDamMod 25
----

The source name is `dammod`, the optional area keyword is `MobDamMod`, and the
C-table member is `dam_mod`. Place the area field in the optional mobile tail
with `MobHPMod`, attack parts and resistance declarations, after any mob
programs, archetype/rank line and teachers. It has no tilde terminator.

Omission emits no line. Explicit zero emits `MobDamMod 0`; it must not be lost
through a truth-value test. The keyword `inherit` is case-insensitive. A leading
plus and decimal leading zeros are accepted and normalised. Fractions, percent
suffixes, `|` expressions, and adjustments below -99 are invalid. Repeated
field declarations use their last value, including a final `inherit`.

Raw table values are validated at boot. An invalid adjustment stops loading
with a diagnostic. The individual parser similarly rejects invalid input
rather than silently supplying a different value.

===== Prototype, live state and diagnostics

The original individual value is stored separately from the resolved prototype
adjustment. `create_mobile()` copies the prototype value into the new live
NPC's `dam_mod`. Combat reads that live value; it does not re-resolve templates
or mutate the stored adjustment on each hit.

`mstat` adds an attack damage section with Template, #MOBILES, Prototype and
Live values. It also displays the helper's result for an illustrative input of
100, before target defenses and later combat adjustments. This sample is not
the last hit, a damage-per-round estimate, or a guarantee of the NPC's actual
damage. Inspection neither rolls a random attack nor changes the live value.

[source,text]
----
mset filler dammod 100
mset filler dammod 0
----

These NPC-only assignments replace the complete live percentage adjustment.
They do not modify the template, individual input, prototype, other instances,
or future spawns. The effect begins on the next applicable attack. The live
command accepts numbers only: `inherit` is an area/template concept and is
rejected here. A fresh instance receives the prototype value again.

`mset damroll` retains its existing meaning as a flat damage bonus. It is not
a synonym for `mset dammod`. Existing HP creation snapshots, HP modifiers, XP
calculation, critical/swiftness defaults, dimensions, language and special
execution are not changed by this addition.


[[scribe-mobile-combat-modifiers]]
==== Critical and swiftness defaults


*`critmod` — Individual critical-score adjustment*

*`swiftmod` — Individual swiftness-score adjustment*

_Signed decimal integer from -100 to 100, or `inherit`_

_Default: omitted; inherit the resolved body-species/archetype adjustment_

===== Units and initialisation

These fields add whole score points to the existing base score. They are not
percentage multipliers like `hpmod` or `dammod`:

[source,text]
----
initial critical score = 5 + resolved crit_mod
initial swiftness score = 5 + resolved haste_mod
----

The table field `haste_mod` is retained for compatibility with existing table
initialisers. It now supplies the swiftness score adjustment. It does not cast
the Haste spell, apply a Haste/Quicken affect, or guarantee an additional attack
independently of the existing swiftness check.

[cols="<2,<2,<4",options="header"]
|===
| Resolved adjustment | Initial score | Meaning
| `0` | 5 | Preserve the old base score.
| `20` | 25 | Add twenty score points, not twenty percent of five.
| `-5` | 0 | A zero score cannot beat a positive percentile roll.
| `-10` | -5 | Retain the full penalty before later equipment/effects.
| `100` | 105 | A score above the ordinary percentile range.
|===

Both adjustments are validated from -100 through 100. `MOB_TEMPLATE_UNSET`
is also allowed in the C table layers as their inheritance sentinel; it is
not an alternative numeric input in an area or Scribe source file. These
bounds do not change the larger allowed ranges for HP/damage adjustments.

No zero-to-one-hundred clamp is applied to the initial live scores. A negative
penalty must remain available for subsequent additive equipment changes:
base 5 plus `crit_mod = -10` yields -5; an item contributing +10 then yields 5,
and removing it returns the score to -5. Clamping the initial score to zero
would lose part of the penalty. This change does not redesign equipment code.

===== Scalar inheritance and syntax

The three template/individual layers choose one adjustment; they are not
added together or XORed. The base score is added only after that choice:

[source,text]
----
body species crit_mod / haste_mod
    -> archetype replacement unless MOB_TEMPLATE_UNSET
    -> individual replacement unless omitted / inherit
    -> add the chosen adjustment to base score 5 once during creation
----

For an inherited adjustment of +20:

[cols="<2,<3,<2",options="header"]
|===
| Individual input | Effective adjustment | Initial score
| Omitted or `inherit` | +20 | 25
| `0` | 0 | 5
| `10` | +10 | 15
| `-5` | -5 | 0
|===

Untemplated mobiles inherit a zero adjustment. The goat defaults are -10
critical and -2 swiftness points, producing scores -5 and 3. The fire-elemental
defaults produce scores 5 and 25 before individual overrides or equipment.

[source,text]
----
critmod 20
swiftmod 0
----

Scribe emits:

[source,text]
----
MobCritMod 20
MobSwiftMod 0
----

The server members are `crit_mod` and `haste_mod`; the source fields are
`critmod` and `swiftmod`; the generated fields are `MobCritMod` and
`MobSwiftMod`. These names are deliberately distinguished. Do not use
`haste_mod` as a Scribe keyword or `MobHasteMod` as an area keyword.

Place both optional area fields in the mobile tail with `MobHPMod`,
`MobDamMod`, attack parts and resistance declarations, after mob programs,
archetype/rank selection and teachers. No tilde terminator is used.
Repeated declarations use the last value. Omitting a source field emits no
line. Explicit zero emits a zero, not an omitted field. `inherit` is
case-insensitive; leading signs and decimal leading zeros are normalised.
Fractions, percent suffixes, numeric `|` expressions and out-of-range values
are rejected. Raw species and archetype values are checked even when a later
layer would replace them. Invalid template values or area inputs stop loading
with a diagnostic.

===== Existing combat semantics remain in use

NPC critical handling tests `number_percent() < ch->crit` in
`damage_internal()` and doubles damage when that branch succeeds. Its scope
is broader than the `one_hit()`-only `dammod` adjustment.

The existing NPC swiftness branch in `multi_hit()` similarly tests
`number_percent() < ch->swiftness` before its bonus `one_hit()` call. Initialising
a higher score increases the chance of that existing branch; it does not
create another scheduler or a new independent attack. Earlier exits, existing
status/action restrictions and other attack sources remain in effect.

Keep these as scores rather than presenting them as exact percent chances.
The existing strict `<` comparisons are not changed to `<=`. On a percentile
range of 1 through 100, a score of 25 accepts rolls 1 through 24. The random
number generator and player enhanced-skill/attribute calculations are unchanged.

Equipment and other consumers use the live `crit` and `swiftness` fields.
Swiftness also participates in existing movement and digging calculations.
HP, damage and XP adjustments remain independent.

===== Creation snapshots and live editing

The original individual adjustments and resolved prototype adjustments are
stored separately. Creation applies them once and records the applied
adjustments and initial scores. Later equipment, spells, scripts or immortal
edits can change live `crit` / `swiftness` without rewriting those snapshots.

`mstat` adds Critical score and Swiftness score groups showing the template,
original individual value, resolved prototype adjustment, base score, creation
adjustment, creation score and current live score. Inspection performs no
random roll and never reapplies the adjustment.

Existing live commands remain absolute score assignments:

[source,text]
----
mset filler crit 10
mset filler swiftness 0
----

These mean live scores 10 and 0, not +10 or +0 adjustments. They do not change
the template, prototype, snapshots, other live instances or future spawns.
There are no `mset critmod` or `mset swiftmod` commands.

The inherited legacy command limits remain unchanged: `mset crit` accepts
0 through 99, despite its existing error message saying 0 to 100;
`mset swiftness` accepts 0 through 100. Those live-command ranges differ from
the -100 to 100 adjustment fields and the possible -95 to 105 spawn scores.
No command accepts `inherit` for a live absolute score.

For testing, compare a fresh unmodified fire-elemental instance (scores 5/25)
with one using individual adjustments 20/0 (scores 25/5). Change a live score
with the existing commands, confirm snapshots are unchanged, then purge and
reload to confirm the prototype values return. Test zero and inherit separately.


[[scribe-mobile-dimensions]]
==== Dimension data and overrides

These fields store metadata. They do not define physical units or change gameplay calculations.

*`height`, `weight`, `size` — Individual raw dimension values*

_Decimal integer from 0 to 2147483647, or `inherit`_

_Default: omitted; inherit the resolved body-species/archetype value_

===== Meaning and limits of this data layer

These are absolute metadata values, not modifiers, percentages or bitmasks.
The existing template values are preserved exactly. The reviewed legacy table
initialisers do not specify measurement units or a categorical size scale:

[cols="<2,<1,<1,<1",options="header"]
|===
| Archetype | Raw height | Raw weight | Raw size
| `goat` | 1 | 30 | 100
| `fire_elemental` | 2 | 20 | 3
|===

No centimetre, metre, pound or kilogram unit is assigned to these values.
`size` is not a tiny/small/medium/large enumeration; 100 is a valid raw value.

For this metadata interface, zero means that no numeric dimension is
specified. It does not create a zero-sized or massless creature. An explicit
zero can replace an inherited nonzero value. If no layer supplies a dimension,
the existing scalar resolver returns zero.

The fields do not affect combat, carrying capacity, carried-item weight,
mount eligibility, corpse weight, room access, equipment fitting, movement or
natural-attack eligibility. `BODY_HUGE`, other body-form flags, and their
existing gameplay checks remain unchanged. Changing `size` does not add or
remove `BODY_HUGE`; changing `weight` does not edit inventory weight.

`APPLY_HEIGHT` and `APPLY_WEIGHT` equipment applies are inactive. Raw NPC
dimension fields do not activate them or change player dimensions.

===== Scalar precedence and syntax

Each field resolves independently:

[source,text]
----
body species value
    -> archetype replacement unless MOB_TEMPLATE_UNSET
    -> individual replacement unless omitted / inherit
    -> effective prototype value copied into each new NPC
----

There is no addition, scaling or XOR. For inherited weight 20:

[cols="<2,<3",options="header"]
|===
| Individual source input | Effective weight metadata
| Omitted | 20
| `weight inherit` | 20
| `weight 0` | 0, explicitly unspecified
| `weight 7` | 7, not 27
|===

Example Scribe source fields:

[source,text]
----
height 7
weight 0
size inherit
----

Generated optional area fields:

[source,text]
----
MobHeight 7
MobWeight 0
MobSize inherit
----

They occupy the existing optional mobile tail after mob programs,
archetype/rank selection and teacher entries. They can accompany the
resistance, attack-part and other scalar declarations. No tilde is used.
Repeated declarations use the last value, including a final `inherit`.

The source names `height`, `weight` and `size` apply to `$mob` blocks. They
do not replace the object `wg` field or object `ap` syntax. The C template
members retain their existing names; the generated keywords are `MobHeight`,
`MobWeight` and `MobSize`.

Omitted source fields emit no declaration. Explicit zero must be exported.
The `inherit` keyword is case-insensitive. A leading plus sign and decimal
leading zeros are accepted and normalised; numeric negative values, fractions,
unit suffixes and numeric `|` expressions are invalid. Numeric negative zero
normalises to zero. The C limit is `INT_MAX`; Scribe uses its current signed
32-bit counterpart, 2147483647.

Raw body-species and archetype values are validated before loading mobiles,
including values hidden by later overrides. `MOB_TEMPLATE_UNSET` is permitted
in C tables only; area/source input uses `inherit`. Invalid raw table or area
input stops loading with a diagnostic.

===== Live copies and immortal inspection

`mstat` adds Height, Weight and Size groups, each showing Template, #MOBILES,
Prototype and Live values. The older template-only line is explicitly labelled
as template data. No dimension calculation or random selection occurs during
inspection.

[source,text]
----
mset filler height 12
mset filler weight 40
mset filler size 100
----

These commands replace one absolute live NPC value. They do not accept
`inherit`, change a prototype, edit an area file, update other live instances,
or alter future spawns. A new instance receives its prototype values again.
Zero is accepted and clears that live metadata field to unspecified. Players
cannot be edited through these new handlers.

Dimensions are inspected with `mstat`, not added to player score or GMCP output.


[[scribe-mobile-language]]
==== Raw language-code data


*`language` — Individual raw language code*

_Decimal integer from 0 to 2147483647, or `inherit`_

_Default: omitted; inherit the resolved body-species/archetype value_

===== Meaning and boundaries

The existing table member is an integer. Its retained values are `1` for
`fire_elemental` and `3` for `goat`. This data layer preserves those codes;
it does not assign language names to them or treat them as indexes into a
new language-name table. Do not infer that code 1 means Common, or that code
3 identifies any particular named language.

For this interface, `0` means unspecified metadata. It does not mean mute,
unable to understand, unable to cast, or unable to communicate. A nonzero
code also does not grant speech or a language proficiency.

`CAN_SPEAK(ch)` depends on `BODY_NO_SPEECH`, not the language code. Changing
that code does not alter speech permissions, translation or comprehension.

The language code is an absolute scalar, not a percentage or bitmask. Scribe
validates syntax and numeric range; it does not use a dictionary of named
languages. A valid number does not imply a named language exists for it.

===== Inheritance and syntax

[source,text]
----
body species language
    -> archetype replacement unless MOB_TEMPLATE_UNSET
    -> individual replacement unless omitted / inherit
    -> effective prototype code copied into each new NPC
----

For the retained fire-elemental template code 1:

[cols="<2,<2,<4",options="header"]
|===
| Individual source | Prototype code | Meaning
| Omitted or `language inherit` | 1 | Keep the template code.
| `language 7` | 7 | Replace the code, not add seven to it.
| `language 0` | 0 | Explicitly clear the code to unspecified.
|===

Example:

[source,text]
----
language 7
----

Scribe emits:

[source,text]
----
MobLanguage 7
----

Place `MobLanguage` in the optional mobile tail after any mob programs,
archetype/rank selection and teacher entries, alongside the other scalar,
resistance, attack-part and footstep fields. No tilde terminator is used.
Repeated declarations use the last value, including a final `inherit`.

Omission emits no line. Explicit zero must be exported. `inherit` is
case-insensitive. Leading plus signs and decimal leading zeros are accepted
and normalised. Negative zero normalises to zero. Negative numeric values,
fractions, named languages, suffixes, numeric `|` expressions and integer
overflow are rejected. The C limit is `INT_MAX`; Scribe uses the current
signed 32-bit limit of 2147483647.

Both raw template layers are checked even when a later layer would override
them. C tables can use `MOB_TEMPLATE_UNSET`; source/area fields must use the
word `inherit` instead. Invalid template values or area declarations stop
loading with a diagnostic. An untemplated mobile begins with inherited code
zero and can also supply an individual code.

===== Inspection and live editing

`mstat` adds Language code layers with Template, #MOBILES, Prototype and
Live rows. The older template-only label becomes Template language code.
Inspection neither re-resolves the live NPC nor changes its speech flags.

[source,text]
----
mset filler language 42
mset filler language 0
----

These are absolute NPC-only live assignments. They do not accept `inherit`,
modify the prototype or source input, affect other instances, or change
future spawns. A new NPC receives the prototype code again. No new player,
Advanced Consider or GMCP language output is introduced.


[[scribe-weighted-specials]]
==== Three weighted special functions


===== Source fields and a working example

A mobile can have up to three configured special functions. The new source
fields supplement the existing `sp` field:

[cols="<2,<4,<3",options="header"]
|===
| Field | Meaning | Input
| `sp` | First slot, or legacy singleton selection when used alone | Registered name, `none`, `inherit`
| `sp2` | Second slot | Registered name, `none`, `inherit`
| `sp3` | Third slot | Registered name, `none`, `inherit`
| `spchance` | Complete selection-percentage vector | Three integers, `auto`, or `inherit`
|===

[source,text]
----
sp spec_breath_fire
sp2 spec_breath_frost
sp3 spec_poison
spchance 60 30 10
----

At each existing special opportunity, the dispatcher chooses one slot: rolls
1–60 select fire breath, 61–90 select frost breath, and 91–100 select poison.
These are mutually exclusive selections, not three independent firing rolls.
The selection is followed by that function's existing implementation.

A percentage is an integer from 0 to 100. Configurations containing functions
must total exactly 100. A named slot at 0% is retained for configuration but
is not selected and does not enable special-gated capabilities or contribute
to the weighted XP bonus. If the same routine is also present in another
positive-weight slot, that enabled occurrence still enables it.

An entirely empty set has three empty slots and 0/0/0. This is the sole
all-zero exception. Three *named* slots at 0/0/0 is invalid; clear the names
with `none` to disable the entire configuration.

===== Selection is not a promise of a visible action

A 0% slot is never selected. This does not rewrite another special's internals:
for example, an enabled `spec_breath_any` can still call a breath routine
internally even if that same routine occupies a separate 0% slot.

The chosen routine can still refuse to act because it is not fighting, has
no suitable target, fails an internal random roll, or fails another existing
condition. There is no retry with a different special after a FALSE return.
There is no pre-filtering and renormalising of percentages based on internal
eligibility. Consequently, a 60% selection weight need not produce a visible
fire breath on 60% of all ticks.

The existing `mobile_update()` cadence, charm/mount/rider checks and bot
branch remain the scheduling source. This change does not add a new
per-combat-round scheduler or call all three functions in sequence. A single
selected function can still perform whatever internal actions it already
performs; the wrapper does not redefine those routines.

The dispatcher does not consume an extra selection random number for a
single 100% choice. It stops the current update after a callback deletes or
moves its actor, even if that callback returned FALSE. Recursive dispatch on
the same actor is blocked. It never temporarily changes a mob's configured
identity to make an old single-pointer permission check pass.

===== Template and individual inheritance

The existing C-table names map directly to three ordinary slots:

[cols="<1,<2,<4",options="header"]
|===
| Slot | Existing C member | Meaning
| 1 | `spec_fun1` | First function
| 2 | `spec_fun2` | Second function
| 3 | `spec_boss` | Third function; *no new boss/world rank restriction*
|===

Name inheritance remains slot-by-slot: `NULL` inherits, `""` clears, and a
non-empty registered name replaces. Scribe/area inputs use `inherit` and
`none`, not C pointer constants.

A new final `spec_chance` member contains a three-integer vector in each
body-species/archetype definition. The vector is inherited or replaced as a
*whole*. Individual numeric components are not inherited separately, added,
or XORed. These valid C-table forms are:

[source,c]
----
MOB_SPECIAL_CHANCES_INHERIT
MOB_SPECIAL_CHANCES_AUTO
{ 60, 30, 10 }
----

The inheritance macro expands to three `MOB_TEMPLATE_UNSET` values. The auto
macro expands to three `MOB_SPECIAL_AUTO` values. A mixture of sentinels and
percentages is invalid. The probability member follows the existing fields.
The pinned tables use inheritance, auto and explicit distributions; inspect
the current entry rather than assuming that every archetype uses one policy.

In `mob_table`, the new field comes *after* the existing `xp_mod`. For example,
the final fields of an archetype can be:

[source,c]
----
"spec_cast_mage", "spec_breath_fire", "spec_poison",
5,                      /* independent additive xp_mod */
{ 60, 30, 10 }           /* selection percentages */
----

In `species_table`, the new vector follows the three special-name fields;
there is no species `xp_mod` field to insert.

If no layer supplies explicit percentages, the policy is `auto`. After the
final names are known, automatic allocation is 100 for one occupied slot,
50/50 for two, and 34/33/33 for three. Remainders go to earlier occupied slots.
Empty slots receive zero. This is a named automatic policy, not silent
normalisation of invalid explicit input.

An explicit vector must remain compatible with the final slot names. Clearing
a slot with a positive inherited percentage therefore also requires updating
the vector or selecting `auto`. A positive percentage on an empty slot is an
error. Changing only a name retains the inherited vector unless it is
explicitly replaced.

Multiple slots may name the same function. Their selection probabilities
add, but only one call is made per opportunity. This does not multiply that
function's permission grants or charge its full XP bonus several times.

===== Legacy `sp` compatibility and extended area records

A source containing only `sp <name>` continues to emit the legacy `M` record.
That record selects a singleton configuration at 100%, clearing other slots.
This preserves old area definitions even if their archetype later acquires
more functions. Standalone `sp none` clears all slots; standalone `sp inherit`
restores complete template inheritance. Omitting all special fields also
inherits the template.

Using any of `sp2`, `sp3`, or `spchance` switches that mobile to the extended
format. In this mode `sp` addresses only slot 1; omitted names inherit their
respective slots. To replace only slot 1 without clearing other inherited
slots, write:

[source,text]
----
sp spec_fido
spchance inherit
----

For the three-function example above, Scribe emits:

[source,text]
----
#SPECIALS
N 2700 1 spec_breath_fire
N 2700 2 spec_breath_frost
N 2700 3 spec_poison
P 2700 60 30 10
S
----

The example uses absolute vnum 2700; Scribe still adds the area's base vnum to
the mobile's relative `vn` as usual. These records belong in `#SPECIALS`,
not in the optional `#MOBILES` tail.

`N <vnum> <slot> <name>` addresses slots 1–3 and accepts a registered name,
`none`, or `inherit`. `P <vnum> <p1> <p2> <p3>` replaces the entire percentage
vector. `P <vnum> auto` and `P <vnum> inherit` select the corresponding policies.
The existing `M` record is retained for whole-set singleton/none/inherit
selection. There are no tilde terminators. Trailing end-of-line comments are
ignored. Repeated N/P records use the last declaration for that name/vector;
a later M record deliberately resets the whole individual configuration.

Scribe accepts lowercase `none`, `inherit`, and `auto`, and the exact
registered special names in its existing dictionary. A numeric `spchance`
requires exactly three nonnegative decimal integers, each at most 100.
Fractional values, signs, percent symbols, missing values and a fourth
percentage are rejected. The server repeats range/total validation and checks
the final names after inheritance; Scribe does not know the compiled templates.

The previous eight scalar inputs and exports are not replaced or regenerated
by this feature. In particular, `swiftmod`, `MobDamMod`, and `language` remain
in their existing parser/export paths.

===== Boot finalisation and live state

Original individual names and the original probability policy are retained
separately from the effective three-slot prototype. Final resolution runs
only after every area and `#SPECIALS` section has been read, before the first
area reset. It does not reapply XOR to existing prototype flags.

Each new NPC receives an independent copy of the effective set. Existing
code which deliberately assigns a single runtime function (for example bot
creation) uses a singleton setter, clearing other slots and setting the named
routine to 100%. The old singleton field is removed rather than left as a
second, conflicting source of truth.

All existing executable special-identity comparisons are migrated to
`mob_has_special()`; presence checks use `mob_has_specials()`. They inspect
all positive-weight slots. This matters for routines whose spells or skills
explicitly require particular NPC special identities. Slot 2 or 3 must not
silently fail those checks because only the former primary pointer was tested.

===== XP treatment

Each routine retains its old special-XP bonus. The combined prototype
contribution is the rounded weighted mean, because the scheduler selects one
routine rather than running all three:

[source,text]
----
weighted special bonus =
    floor((p1*bonus1 + p2*bonus2 + p3*bonus3 + 50) / 100)
----

For fire breath (+10) at 60%, frost breath (+10) at 30%, and poison (+5) at
10%, the result is +10 points after rounding 9.5. It is not +25 points.
A zero-weight slot contributes zero. An empty set contributes zero. A legacy
single function at 100% receives exactly its old bonus.

The existing area-reset assignment adds this special bonus in the same place
as before. The existing area/equipment contributions and separate archetype
`xp_mod` are still added once. A +5 archetype adjustment with the example
weighted bonus contributes +15 points in total before the other existing
contributions; it is not a second multiplier.

Live special edits do not recalculate the already stored `exp_modifier`.
The prototype diagnostic reports the contribution that ordinary area resets
use; it does not claim that an immortal-loaded or specially constructed NPC
has the same existing XP value as a reset-spawned one.

===== Immortal inspection and atomic editing

`mstat` shows the template names and probability policy, original individual
names and probability policy, effective prototype names/percentages, live
names/percentages, per-slot call counts, and prototype special-XP adjustment.
The older one-name summary reports the first enabled slot only; use the new
three-slot section for the full state.

Call counts record invocations, including callbacks which returned FALSE.
They measure selection, not successful attacks or spells. They start at zero
on creation and reset when a live configuration is replaced. Inspecting a
mobile neither rolls probabilities nor executes a special.

[source,text]
----
mset filler specials spec_breath_fire 60 spec_breath_frost 30 spec_poison 10
mset filler specials spec_breath_fire 100 none 0 none 0
mset filler specials none
mset filler specials inherit
mset filler spec spec_fido
----

The complete tuple is validated before changing the live set. Invalid names,
incorrect sums, negative percentages, positive empty slots, or a fourth pair
leave the existing live configuration untouched. The full live tuple accepts
only names/`none` and numeric percentages, not per-slot `inherit` or `auto`.
Whole-set `specials inherit` restores the effective prototype, including its
individual overrides. `specials none` clears all slots.

The legacy `spec <name>` command installs a singleton at 100%, and also
accepts whole-set `none` and `inherit`. These operations reset call counters,
not prototypes, other live instances, future spawns, area files, or stored XP.
They do not reverse effects that a routine has already caused.

===== Damage and status-effect behaviour

The attack/effect supplies a mask and the target supplies its resistance
state. Multiple matching categories produce *one* result for that damage or
status resolution:

[cols="<2,<5",options="header"]
|===
| Result | Behaviour in the resistance helper
| Immune | A matching immunity wins over resistance or vulnerability; positive damage becomes zero.
| Resistant | With no matching vulnerability or immunity, positive damage is halved, with a minimum of one point.
| Normal | No category matches, or the attack matches both resistance and vulnerability without matching immunity; the helper leaves damage unchanged.
| Vulnerable | With no matching resistance or immunity, positive damage becomes the original damage plus half that damage, rounded down.
|===

These percentages describe the resistance adjustment, not every later combat
modifier. A genuine miss enters with zero damage and remains a miss. An attack
which connects but is nullified by immunity receives a distinct immunity
message. Other mitigation systems can still affect the final damage.

For a combined attack such as `RES_FIRE | RES_MAGIC`, fire immunity or magic
immunity can negate the whole damage event. Resistance to magic and
vulnerability to fire cancel to normal. Being vulnerable to both categories
still applies the vulnerability adjustment only once, not twice.

Selected status-effect paths use `saves_resistance_effect()`. Immunity makes
that resistance-aware save succeed; resistance gives a five-level effective
caster penalty, and vulnerability a five-level effective caster bonus. This
corresponds to a nominal 20-percentage-point saving-throw shift away from
level/chance clamps, not an unconditional 20-point shift at every level.
The existing save limits and other saving-throw rules still apply.

A flag in `skill_table` does not by itself make every bespoke skill, rider,
room effect or direct resource change consult the resistance system. Check
the relevant implementation and test both damage and secondary effects.
The shared resolver uses resolved live masks for NPCs and the selected
<<scribe-pc-innate-resistances,derived innate traits>> for PCs. It does not
replace existing PC resistance skills, equipment or protective spells.
Innate PC traits never supply immunity.

===== Innate player resistances and vulnerabilities

The shared resistance resolver derives the following PC traits from the
character's current race, subclass and form. This is the complete selected
profile for this stage; other races and classes receive no new innate traits.
No profile supplies immunity.

[cols="<2,<3,<3",options="header"]
|===
| Source | Resistances | Vulnerabilities
| Elf, Drow, Wild-Elf | `sleep`, `charm` | None.
| Fae | None. | `cold_iron`, `silver`.
| Tiefling | None. | `cold_iron`.
| Troll | None. | `fire`, `acid`.
| Illithid | `psychic` | None.
| Duergar | `paralysis` | None.

| Vampire subclass | None. | `silver`, in every form.

|===

These traits are computed by `pc_innate_resists()` and

Racial traits remain in force through form changes. Werewolf/Vampire silver
weakness follows the subclass, not just wolf/direwolf/bat form. Demon-form
silver weakness requires both the Shapeshifter class and current demon form;
it disappears on leaving that form unless another source also supplies it.

Repeated weaknesses combine with bitwise OR, not XOR or repeated damage
multipliers. A Fae Vampire in demon form remains vulnerable to silver once.
An existing character receives its correct profile as soon as this server
code is running; the profile also follows later race/subclass/form changes.

====== Combat and saving throws

The existing damage helper applies one result per classified damage event:
resistance halves positive damage with a minimum of one; vulnerability adds
half the incoming damage, rounded down. A 100-point event becomes 50, 100
or 150 at this stage. Later mitigation and caps may change the final result.
Zero-damage misses remain zero.

Matching resistance and vulnerability retain the existing cancellation rule.
For example, a hypothetical event classified as both psychic and silver is
normal against an Illithid Vampire. No blanket magic or nonmagic resistance
has been added that could cancel the selected silver/cold-iron weaknesses.

Status effects already using `saves_resistance_effect()` retain one saving
throw. Resistance reduces effective casting level by five, with the existing
minimum level and saving-throw limits. This nominally improves the save by
20 percentage points away from those limits. It does not prevent ordinary
sleep, guarantee a successful save, or shorten effects after they succeed.

Sleep, Paralysis and the existing ghoul/ghast contact-paralysis save already
use this path. Charm Person's existing prohibition on PC targets is unchanged;
no new player-charming permission is introduced.

Transfix and targeted Howl use attack-success thresholds rather than spell
saving throws. Both now consult the shared resolver for PC and NPC targets;
see <<scribe-mental-status,Transfix, Howl and Confusion>>. Resistance halves
the winning outcomes of the existing roll. Vulnerability adds half, subject
to the existing ceiling; matching NPC immunity prevents success. There is
no second roll and no change to a successful effect's duration or penalties.
The previously implemented Transfix protection for PCs is preserved.

Confusion uses the resistance-aware saving throw for both PC and NPC targets.
This changes the chance of applying the psychic spell, not its strength or
duration on a failed save. Its existing player behaviour is preserved; NPC
masks are no longer bypassed.

Supported ordinary and named weapon/shield contacts already pass the actual
contact object's materials. Their existing shared damage path now uses PC
vulnerabilities as well. Decapitate, Assassinate's level-based threshold and
shield Hurl's daze threshold also consult these traits through their existing
material helper; do not apply another separate PC multiplier at those sites.

Fireshield retaliation is a separate direct-HP path. Its damage against a PC
attacker explicitly applies the innate fire response once, after the existing
Resist Heat adjustment. The NPC retaliation path and remaining Fireshield
processing are unchanged.

====== Category boundaries and existing mechanics

`paralysis` is not every effect using `AFF_HOLD`: a trap or binding does not
become paralysis merely because it prevents movement. Likewise, `psychic`
is not every spell, and sleep resistance is not immunity to normal sleep.
No additional fire/cold/poison/holy/drain traits have been added.

Existing PC resistance skills, item bonuses, buffs, target restrictions and
legacy creature-specific exceptions remain separate. This stage does not
retroactively remove all existing immunity-like abilities or target exclusions;
it adds no new PC immunity and ignores NPC-style `immunes` data on PCs.

A resistance bit still requires a classified damage or effect call. Beyond
the explicitly documented integrations, this stage does not normalise
every bespoke status, reflected-damage,
room-hazard or direct resource-loss path. Untyped HP subtraction and generic
`aggro_damage()` cannot infer fire, acid, psychic or weapon material. Effects
that intentionally bypass the shared resolver require an explicit later hook.

Weapon Stun now consults its full selected-object contact mask before its
success roll; see <<scribe-weapon-stun,Weapon Stun>>. This includes Duergar
paralysis resistance and the selected PC material vulnerabilities.
Tenketsu also resolves its paralysis after a damaging hit; see
<<scribe-tenketsu,Tenketsu: post-hit paralysis>>.
The exclusions for projectile ammunition, Target/trauma and other unclassified
effect riders remain. Ghost implementation is unchanged.

====== Builder and diagnostic behaviour

`res`, `vuln`, `imm`, `MobResists`, `MobVulnerabilities` and `MobImmunes` remain
NPC authoring fields. Scribe has no new PC fields or material keywords in this
stage. A mobile with a player-race value does not automatically receive this
PC profile: its NPC template, individual XOR values and live state remain
authoritative. NPC immunity and cancellation rules are unchanged.

For a PC, `mstat` prints the derived innate resistance and vulnerability masks
with category names and explicitly reports that innate immunities are none.
This report is not a total of every spell, equipment or learned defence.
The existing NPC `mstat` report remains unchanged.

[[scribe-mental-status]]
===== Transfix, Howl and Confusion

This stage connects three existing mental status paths to the shared
resistance system. It adds no skill-table category, player trait, immunity
flag, save-file field or Scribe keyword. NPCs use their resolved live masks;
PCs use their selected derived innate traits and receive no innate immunity.

[cols="<2,<3,<3",options="header"]
|===
| Effect | Existing categories | Resolution
| Transfix | `RES_CHARM`, `RES_NONMAGIC`, `RES_PSYCHIC`. | Adjust the existing learned/level success threshold for both PC and NPC targets.
| Targeted Howl | `RES_NONMAGIC`, `RES_PSYCHIC`, `RES_SONIC`. | Adjust the existing learned/level success threshold for both PC and NPC targets; reject a mindless target first.
| Confusion | `RES_MAGIC`, `RES_PSYCHIC`. | Use the existing resistance-aware saving throw for both PC and NPC targets.
|===

The complete effect mask supplies one response. Matching NPC immunity takes
priority. Otherwise, matching resistance and vulnerability cancel to normal;
several matching resistances or vulnerabilities do not stack.

These are not weapon contacts. The caster's equipment contributes no silver,
cold iron or magical-source category. The effect keeps its declared source
category, so an NPC's matching `non_magic` immunity also prevents Transfix or
Howl, and matching `magic` immunity prevents Confusion. No broader rewrite of
the meaning of those existing categories is introduced here.

====== Transfix and Howl: one existing success roll

Each retains its learned-skill and level formula, followed by the existing
base clamp to thresholds 5 through 95. `resistance_result_threshold()` then
adjusts that threshold once, using `get_resistance_result()` with the full
skill mask. Do not also apply the former PC-only Transfix reduction.

The comparison remains `number_percent() < chance`. A threshold of 41 gives
40 winning percentile outcomes. Normal response retains 41; resistance
produces 21 (20 outcomes); vulnerability produces 61 (60 outcomes); immunity
produces zero. Vulnerability remains limited by the upper threshold of 95
(94 winning outcomes). Do not reapply a lower minimum after adjustment.

No additional save, hit, damage multiplier or skill roll is introduced.
Successful Transfix and Howl retain their existing duration of 3, hitroll
penalty of -8, `AFF_HOLD`, and success-specific victim wait state. An immune
attempt cannot enter those success blocks. It follows the existing failed-
attempt path, which may initiate combat through the zero-damage call; this
is not a promise that an immune attempted attack has no combat consequences.

Existing user, form, target and PvP restrictions remain. In particular,
Howl remains player-operated and requires wolf or direwolf form; the early
NPC return remains before `pcdata` access. Transfix retains its existing
permitted-NPC-caller exception, sight checks and mindless-target rejection.

Targeted Howl now calls `reject_mindless_target()` after the ordinary safety
check and before its full skill action cost and success roll. It does not
apply a hold, victim wait state or failed-attempt damage call to that rejected
target. Its earlier two-pulse anti-spam cost remains. Howl with no target
continues to be its existing cosmetic action, and is not an area attack.

====== Confusion: one resistance-aware saving throw

Replace the PC/NPC conditional at the existing saving-throw site with one
call to `saves_resistance_effect(level, victim, skill_table[sn].res_type)`.
Do not keep the old save alongside it. Matching immunity rejects the effect
without a save roll. Otherwise, resistance lowers effective casting level
by five, vulnerability raises it by five, and the existing save helper uses
its existing bounds. Normal targets keep the original saving throw.

Mindless, object and already-confused target checks remain before that save.
A saved or immune target gets no new Confusion affects. On failure, the
existing duration, hitroll/Intelligence/Wisdom penalties, messages and
confusion behaviour remain unchanged. The original casting level still
sets those penalties and duration; the helper's adjusted level is only for
the save. Confusion casts no replacement spell and adds no damage event.

====== Player category boundaries and tests

Elven charm resistance protects Elf, Drow and Wild-Elf PCs against Transfix,
not Howl or Confusion. Illithid psychic resistance protects against all
three. Duergar paralysis resistance alone protects against none of them:
using `AFF_HOLD` does not make an effect paralysis. The words "bone-chilling"
in Howl's messages do not classify it as cold damage.

Fae, Tiefling, Werewolf/Vampire and demon-form material vulnerabilities do
not match these objectless effects. No character gains another resistance,
and player-owned NPCs continue to use NPC masks rather than their owner's
race or subclass traits.

Test a neutral NPC; NPCs with matching resistance, vulnerability, immunity
and mixed masks; Elf/Illithid/Duergar PCs; and a mindless target. For Transfix
or Howl with a normal base threshold of 41, compare rolls 20/21 and 60/61 at
the resistant/vulnerable boundaries. Verify that matching immunity produces
no successful hold or success-specific victim lag, and that a failed or
immune Confusion produces no new Confusion records. Existing innate player
profiles, material finishing-move rules, Stun, Tenketsu and ghost behaviour
are unchanged.

[[scribe-tenketsu]]
===== Tenketsu: post-hit paralysis

Tenketsu retains its existing `RES_BLUNT`, `RES_NONMAGIC` and `RES_PARALYSIS`
classification. It is an unarmed pressure-point attack. Silver, cold iron
and magic on unrelated equipment do not become categories of this attack.
No skill-table flag or new player resistance profile is added.

`tenketsu()` keeps the existing base/combo damage calculation and calls the
normal damage pipeline exactly once. It no longer applies the hold or
no-recall affects before damage is resolved.

After positive damage is applied, `damage_internal()` calls
`tenketsu_after_hit()` with the resistance result already computed for that
same hit. This does not calculate another damage multiplier or make another
attack. A failed skill roll that sends zero damage cannot trigger the hook.

The callback requires both characters to remain present in the same room,
not deleted or dead, and above zero HP. It rejects self-targeting, an already
held target, an immune result, and an invulnerable NPC. Misses, fully avoided
attacks, zero-damage outcomes and lethal impacts therefore do not apply a new
Tenketsu hold/no-recall pair. If retaliation has reduced the attacker to zero
HP or below, the callback does not apply paralysis either.

The effect cannot penalise the target's Dexterity before that same attack's
normal defences run. This ordering change intentionally removes the previous
possibility of applying paralysis through a defended or nullified strike.

[cols="<2,<3,<3",options="header"]
|===
| Resolved response | Categorised damage | Paralysis after an eligible damaging hit
| Normal | Existing normal damage. | Automatic, as before.
| Resistant | Existing half-damage rule, minimum one at the resistance stage. | 50% chance: percentile outcomes 1 through 50.
| Vulnerable | Existing +50% damage rule. | Automatic; the existing 100% follow-up cannot increase beyond certainty.
| Immune | Existing zero-damage rule. | No paralysis or no-recall affect.
|===

The damage response and secondary-effect response apply to different parts
of the attack. Damage is not scaled twice. The callback does not invoke
`saves_spell()`, `saves_resistance_effect()` or the learned-skill test again.
Only a resistant, otherwise eligible target requires the added percentile
roll. Normal and vulnerable targets retain automatic paralysis after a
successful damaging hit. This post-hit 100%/50% convention is the DD4 rule
for this integration, not a general new rule for all combat effects.

The full skill mask supplies one combined resistance result. Matching
resistance and vulnerability retain the existing cancellation rule, and
multiple matching resistances do not produce repeated chance reductions.
Duergar PCs qualify through their existing innate paralysis resistance.
Elven sleep/charm resistance and Illithid psychic resistance alone do not
match this attack. NPCs use their existing live masks, not player race
profiles. No new player immunity is introduced.

A successful effect retains `gsn_tenketsu`, duration `1 + level / 15`,
Dexterity penalty `-5` with `AFF_HOLD`, and movement penalty `-10 * level`
with `AFF_NO_RECALL`. The resistance branch either applies both effects or
neither. It does not shorten or weaken a successful paralysis, and an
already held target does not receive another pair.

Both direct Tenketsu and the existing combo route pass through `tenketsu()`.
Their learned-skill checks, action costs, target checks and combo arithmetic
remain unchanged. No global rewrite of other martial-arts effects, Target
trauma, spell effects, anatomy rules or ghost behaviour is part of this stage.

For tests, compare a neutral target, a Duergar PC and deliberately configured
resistant/immune/vulnerable NPCs. Check direct and combo use, zero-damage
failures, a lethal blow, existing holds, and both affect records. Equipping
silver/cold-iron items must not alter Tenketsu's categories.

===== Sonic and water categories

The added categories have specific, already-selected uses:

[cols="<2,<3,<4",options="header"]
|===
| Ability | Effect categories | Implementation qualification
| Sonic Blast | `RES_SONIC` and `RES_MAGIC`
| Sonic replaces the previous generic energy classification. The

[[scribe-template-xp]]
==== Archetype XP bonuses and penalties

A creature archetype can supply `xp_mod`, a signed adjustment in *percentage
points*. It is the final field of the server-side `mob_table` entry and is
carried into the resolved template. It is not an ordinary Scribe `$mob`
field, not an individual `.are` field, and not a body-species field in this
implementation.

[cols="<1,<4",options="header"]
|===
| `xp_mod` | Meaning
| `0` | No archetype adjustment. Use this rather than `MOB_TEMPLATE_UNSET`.
| `25` | Add 25 percentage points to the existing XP modifier.
| `-25` | Subtract 25 percentage points from the existing XP modifier.
|===

The effective percentage is calculated by `get_mob_exp_modifier()`:

[source,text]
----
effective XP percentage = existing stored modifier + archetype xp_mod

XP at this calculation stage = base XP * effective percentage / 100
----

The existing stored modifier includes whatever the normal creation/reset
path assigned, including area, special-function and equipment contributions.
The archetype adjustment is added to that same base percentage once. It is
not a second multiplier, and the special-function modifier is not added again.

[source,text]
----
Existing percentage    Archetype adjustment    Effective percentage
120                    +25                     145
120                    -25                      95
100                      0                     100
----

Negative effective percentages are clamped to zero. Later XP adjustments,
randomisation and existing minimum-reward rules still apply, so a very large
penalty or an area `xp` value of zero does not necessarily mean zero final XP.
Use the existing `act no_experience` flag for a mobile intended to award no
experience, allowing for its XOR meaning on a templated mobile.

The existing fame rule which halves fame below an XP modifier of 100 now
consults the effective percentage too. An archetype adjustment which crosses
that threshold can therefore change that existing fame reduction.

`mstat` shows the stored, archetype and effective contributions separately:

[source,text]
----
XP modifier: existing 120% + archetype +25 points = effective 145%
----

For reward testing, compare normally reset-spawned mobiles, not only `mload`
instances. Their stored area/special/equipment contributions can differ.
The template's other numerical modifiers are not substitutes for `xp_mod`.

==== Template diagnostics, validation and live editing

The server validates body-species names, archetype-to-species relationships,
special-function names and resistance definitions during startup. Typical
successful messages include:

[source,text]
----
[MOB TEMPLATE] Relationship validation complete: no issues found.
[MOB TEMPLATE] Attack-part validation complete: no issues found.
[MOB TEMPLATE] HP-modifier validation complete: no issues found.
[MOB TEMPLATE] Damage-modifier validation complete: no issues found.
[MOB TEMPLATE] Combat-score validation complete: no issues found.
[MOB TEMPLATE] Dimension validation complete: no issues found.
[MOB TEMPLATE] Language-code validation complete: no issues found.
[MOB TYPE] Resistance validation complete: no issues found.
----

Boot diagnostics validate the raw template values as well as resolved masks.
A successful validation does not test gameplay. Raw XOR masks can overlap
across categories when cancelling an inherited state; the resolved state
must still satisfy resistance-conflict checks.

For an individual flag cancellation, the load log includes the vnum, flag
group, bit, inherited archetype and the fact that `#MOBILES` removed it.
`mstat` exposes the same distinction through separate rows:

[cols="<2,<5",options="header"]
|===
| Row | Meaning
| Template | Body-species defaults after applying the archetype's XOR masks.
| #MOBILES | Original individual input mask, retained separately from the result.
| XOR removed | Bits present in both the inherited mask and the individual mask, excluding protected engine bits where applicable.
| Prototype | Effective initial values from which new NPCs are created.
| Live | Values on the particular NPC being inspected, including subsequent runtime changes.
|===

`mstat` shows ACT, AFF, BODY, resistance and attack-part layers. `Eligible`
and `Inactive` describe currently usable natural attacks. `Death-part
candidates` separately lists physical pieces eligible for random death drops.
Inspection does not create an object or consume a random roll. Template
labels describe inherited defaults, not necessarily the live state.

The HP section distinguishes inherited and individual adjustments, the
resolved prototype, recorded spawn values, and current HP. Inspection does
not recalculate HP.

The damage section includes a deterministic scaling sample. Critical and
swiftness sections show initial and live scores. Dimension and language
sections show template, individual, prototype and live values. These are
scalar diagnostics, not XOR removal reports.

Advanced Consider uses live body-form and resistance masks in its existing
archetype-information block. Its attack-part list also uses the live configured
mask. It is not the new filtered `Eligible` mask. This is not a promise that
Consider displays every new
field for every untemplated mobile.

===== Live resistance commands

[source,text]
----
mset <mobile> resists <mask>
mset <mobile> vulnerabilities <mask>
mset <mobile> immunes <mask>
----

These are immortal commands for NPCs only. The value is a complete replacement
mask, using decimal numbers or compact `|` expressions without spaces; it is
not a keyword list and is not XORed against the prototype.

[source,text]
----
mset filler resists 2
mset filler immunes 1|256
mset filler immunes 0
----

The last command clears the live immunity mask. It does not clear the
prototype, edit the source, or change any other copy of the mobile. A newly
loaded copy receives the prototype state again. These live changes are not
persisted back to the area definition.

Unknown bits and conflicting live categories are rejected. To move a fire
bit from immunity to vulnerability, first remove it from the live immunity
mask, retaining the other intended immunity bits, then replace the live
vulnerability mask. The command does not automatically edit the other two
categories for you.

===== Builder verification

Check the template, individual, prototype and live rows before testing
combat. Then test inherited defaults, one deliberate cancellation, an
ordinary untemplated mobile, and a temporary live change followed by a fresh
spawn. For an effect with secondary penalties, inspect both HP changes and
active affects. An immunity message alone is not evidence that every rider
was blocked.

When moving a source between editors, preserve the original individual
inputs rather than exporting a resolved inheritance preview.

The <<scribe-mobile-damage-modifier,attack damage modifier>> provides
a separate percentage-layer display, an illustrative pre-defense scaling sample,
and NPC-only `mset dammod`. These do not recalculate the recorded HP snapshots.

[[scribe-weapon-resistance]]
===== Ordinary weapon attack categories

For NPC attacks with an empty weapon slot, the
<<scribe-natural-attacks,natural-attack selector>> supplies the ordinary
attack type from `atk`. It does not alter equipped weapon objects.

For ordinary `TYPE_HIT`-based attacks, the weapon's `v3` attack type determines
its damage category:

[cols="<3,<2",options="header"]
|===
| `v3` keywords | Resistance category
| `hit`, `pound`, `crush`, `grep`, `scoop`, `mash` | `RES_BLUNT`
| `slice`, `slash`, `whip`, `claw`, `chop`, `rake`, `swipe`, `hack` | `RES_SLASH`
| `stab`, `bite`, `pierce`, `sting` | `RES_PIERCE`
| `blast` | `RES_ENERGY`
| `suction` | `RES_DRAIN`
|===

The source category is added separately. A weapon with `ex magic`
(`ITEM_MAGIC`) produces `RES_MAGIC` ordinary attacks. Other ordinary weapons
and generic unarmed attacks use `RES_NONMAGIC`. Having numerical `ap` bonuses
is not the test used here; the object magic flag is. Primary and secondary
weapons are classified using the actual weapon responsible for each hit.

`ex blessed` and `ex cursed` do not automatically change this ordinary attack
mask into holy or dark damage.

A blessed, non-cursed ITEM_WEAPON gains a separate anti-undead combat
bonus when the actual target satisfies `IS_UNDEAD()`: +2 effective
hitroll on ordinary `one_hit()` weapon attack rolls and +10 percent
positive weapon damage, with a minimum bonus of one point.

This bonus does not add `RES_HOLY`, does not set `ITEM_MAGIC`, and does
not itself bypass `RES_NONMAGIC`. Silver, cold iron, magical status and
ghost phase continue to resolve independently through their existing
contact rules.

If an object carries both `ITEM_BLESS` and `ITEM_CURSED`, it receives
no anti-undead blessing bonus. The cursed flag does not otherwise gain
a new undead benefit.

Only the actual attacking ITEM_WEAPON contributes the bonus. A blessed
weapon elsewhere in inventory or in the other hand does not bless an
unrelated strike. ITEM_BODY_PART objects and shields do not receive this
weapon bonus.

Named weapon attacks already routed through `damage_from_object()` use
the selected source weapon for the damage bonus. Percentage/chance-based
finishing or status rolls such as Decapitate and Hurl are not granted
extra success percentage merely because the weapon is blessed.

A special skill's damage may use its fixed `skill_table`
mask instead of this ordinary-weapon classification, even while the character
is wielding a magical weapon.

See <<scribe-resistance-flags,Resistance category reference>> for the combined
mask rule. Immunity which nullifies a connected ordinary hit has a distinct
combat message; it is not reported as a genuine miss.

[[scribe-cold-iron]]
===== Cold iron

Cold iron uses the existing object-extra and resistance systems:

[cols="<2,<2,<2",options="header"]
|===
| Source field | C flag | Decimal bit
| Object `ex cold_iron` | `ITEM_COLD_IRON` (`BIT_32`) | `4294967296`
| Mobile `res cold_iron` | `RES_COLD_IRON` (`BIT_22`) | `4194304`
| Mobile `vuln cold_iron` | `RES_COLD_IRON` (`BIT_22`) | `4194304`
| Mobile `imm cold_iron` | `RES_COLD_IRON` (`BIT_22`) | `4194304`
|===

The same keyword has different bit values in these separate namespaces.
Cold iron is not `RES_COLD` (freezing), and does not use an AFF flag.
Object names and descriptive material text do not automatically set the tag.
The tag may be stored on any object. Ordinary strikes check actual weapons;
supported shield attacks check the actual shield.

For example:

[source,text]
----
$obj
vn 1
nm iron dagger
sh a cold-iron dagger
lo A cold-iron dagger lies here.
ty weapon
v3 stab
we take wield
wg 2
ex cold_iron
----

Use `ex cold_iron magic` for a weapon carrying both properties. The material
flag does not grant magic by itself and does not bypass nonmagical immunity.

===== Attack classification and resolution

An ordinary primary or secondary melee weapon strike adds `RES_COLD_IRON`
when the actual attacking, non-deleted ITEM_WEAPON has `ITEM_COLD_IRON`.
It retains its physical damage category and its magic/nonmagic source category.
A nonmagical cold-iron dagger therefore supplies:

[source,c]
----
RES_PIERCE | RES_NONMAGIC | RES_COLD_IRON
----

The complete mask goes through the existing resistance resolver once.
A matching immunity nullifies the damage. With no matching immunity, a
matching resistance and vulnerability cancel to normal; resistance alone
halves positive damage (minimum one), and vulnerability alone adds half the
original damage, rounded down. Several matching vulnerabilities do not stack.
For an otherwise normal 100-point hit at this stage, the possible results are
0 (immune), 50 (resistant), 100 (normal) and 150 (vulnerable).

Cold-iron vulnerability is consequently +50%, not a separate doubled-damage
rule. Normal defenses and subsequent combat modifiers remain in effect.
A nullified connected hit uses the existing immunity message, not a miss.

Ordinary TYPE_HIT-based weapon strikes and the documented
<<scribe-object-contact,named object-contact attacks>> obtain cold-iron
classification from their actual contact object. Carrying or wearing a
cold-iron item does not give unrelated attacks its material.
Other effect paths may explicitly supply RES_COLD_IRON when designed to
do so; the category is not restricted to ghasts.

Body-species, archetype and individual resistance fields remain NPC data.
Combat also consults the selected <<scribe-pc-innate-resistances,innate PC
traits>>. Existing player resistance skills and effects retain their separate
handling; NPC authoring masks are not copied onto player characters.

===== Inheritance and live editing

The ghast archetype supplies `vuln cold_iron` as a template default. Do not
repeat it on an ordinary individual ghast: individual masks are XOR inputs.

A neutral-to-cold-iron ghast cancels its inherited vulnerability:

[source,text]
----
archetype ghast
vuln cold_iron
----

A cold-iron-resistant ghast cancels vulnerability and adds resistance:

[source,text]
----
archetype ghast
vuln cold_iron
res cold_iron
----

A cold-iron-immune ghast instead uses:

[source,text]
----
archetype ghast
vuln cold_iron
imm cold_iron
----

Putting the same effective category in more than one response mask is invalid.
On a template without inherited cold-iron properties, any one of `res`, `vuln`
or `imm` can add the corresponding response normally.

The existing live commands use absolute masks, not XOR. To change a default
ghast from vulnerable to resistant, first clear that vulnerability, then set
resistance. Preserve any unrelated bits in both masks:

[source,text]
----
mset <mobile> vulnerabilities 0
mset <mobile> resists 4194304
----

These values are for a default ghast with no other vulnerability or resistance
bits. To change to immunity, clear the resistance and preserve sleep/charm:

[source,text]
----
mset <mobile> resists 0
mset <mobile> immunes 4197376
----

`4197376` combines cold iron with the ghast's existing sleep/charm mask `3072`.
`mstat` names cold_iron in the relevant resistance layers. `ostat` and the
ordinary identification path name cold_iron as an object extra flag. The
existing `oset extra` command replaces an entire extra-flags mask: preserve
unrelated flags when editing a real object. No special material mset field is
required, and changing `spec_ghast` or stench does not change these masks.

[[scribe-silver]]
===== Silver

`ex silver` sets `ITEM_SILVER` (`BIT_33`, decimal `8589934592`).
Use it for silver or silvered objects. Names and descriptions do not set
the flag automatically, and the flag does not grant `ITEM_MAGIC`.

`res silver`, `vuln silver` and `imm silver` use `RES_SILVER`
(`BIT_23`, decimal `8388608`). These are mobile resistance fields, in a
different flag namespace from object extras.

For ordinary primary and secondary weapon strikes, a non-deleted
`ITEM_WEAPON` carrying `ITEM_SILVER` adds `RES_SILVER` to the attack's
existing damage and magic/nonmagic categories.

For example, a mundane silver dagger supplies
`RES_PIERCE | RES_NONMAGIC | RES_SILVER`. A magical silver dagger supplies
`RES_PIERCE | RES_MAGIC | RES_SILVER`.

The complete mask is resolved once using the existing resistance rules.
Multiple matching vulnerabilities or resistances do not stack.
Silver does not automatically bypass nonmagical immunity.

Ordinary weapon strikes and the documented
<<scribe-object-contact,named object-contact attacks>> obtain silver
classification from their actual contact object. Other skills and spells
do not acquire it merely because the attacker carries or wears silver.

Identification describes the silver property. Object inspection names
the silver extra flag, and mobile inspection names silver resistance
categories.

Existing individual XOR inheritance and absolute live-mset rules remain
unchanged. Those stored masks remain NPC-only; selected innate player
resistances and vulnerabilities are derived separately at runtime.

Silver tagging by itself grants no universal immunity bypass.
The <<scribe-ghost-contact,ghost contact rules>> provide a conditional
exception for the existing mundane-weapon barrier. Automatic
materialisation and spell-phase rules remain separate work.

[[scribe-object-contact]]
===== Named weapon and shield contacts

The following attacks use their actual weapon's ITEM_MAGIC,
ITEM_SILVER and ITEM_COLD_IRON properties:

* weapon backstab and its double-backstab repetition;
* circle and second circle;
* thrust, joust and riposte;
* counterbalance strikes and armed whirlwind;
* weapon Hurl and Decapitate.

<<scribe-weapon-stun,Weapon Stun>> also uses the selected weapon's contact
categories, but adjusts its status-effect success roll rather than adding
another damage event.

Joust uses the selected lance. Hurl uses the selected hurled object.
Decapitate uses a qualifying primary vorpal, or the off-hand vorpal when
the primary weapon does not qualify.

Natural/body-part variants retain their existing skill categories and
do not borrow material from unrelated equipment.

A named attack keeps its explicitly declared damage kind. Where none is
declared, a weapon supplies its attack kind and a shield supplies blunt.
ITEM_MAGIC determines the single magic/nonmagic source category.
Silver and cold iron are additional material categories.

Damage resolves the complete mask once. Matching immunity wins.
Otherwise, matching resistance and vulnerability cancel. Several
matching vulnerabilities or resistances do not stack.

====== Shield attacks

Smash obtains contact categories from the equipped shield, never the
primary weapon. Its existing base-damage calculation is preserved.
Matching contact immunity prevents the Smash-imposed victim lag.

A huge NPC permitted to Smash without a shield receives no item-material
categories. Existing separate off-hand follow-up strikes retain their
own ordinary weapon classification.

Shield Hurl uses the selected equipped shield. Material responses modify
its daze success chance, not its duration. Nonweapon objects outside the
shield slot are not eligible for this branch.

[[scribe-weapon-stun]]
====== Weapon Stun: materials and resistance

`do_stun()` selects a qualifying, non-deleted blunt weapon from the primary
slot first, or from the off-hand slot when the primary object does not qualify.
It does not combine the materials of two equipped objects. The existing
`is_blunt_weapon()` eligibility test is retained.

For an ordinary weapon, Stun retains its declared `RES_BLUNT` and
`RES_PARALYSIS` categories. The actual selected weapon supplies exactly one
of `RES_MAGIC` or `RES_NONMAGIC`, plus any `RES_SILVER` and `RES_COLD_IRON`
material tags. The category remains blunt even when the qualifying weapon's
normal attack is described differently: this preserves the Stun skill's own
classification.

A qualifying `ITEM_BODY_PART` object may still pass the existing equipment
eligibility test, but does not supply item material or item magic to the
knockout. That version uses the skill's existing blunt, nonmagical and
paralysis categories. No objectless version of the command is added.

[cols="<3,<4",options="header"]
|===
| Selected source | Stun contact categories
| Plain blunt weapon | `RES_BLUNT`, `RES_PARALYSIS`, `RES_NONMAGIC`.
| Mundane silver blunt weapon | `RES_BLUNT`, `RES_PARALYSIS`, `RES_NONMAGIC`, `RES_SILVER`.
| Magical cold-iron blunt weapon | `RES_BLUNT`, `RES_PARALYSIS`, `RES_MAGIC`, `RES_COLD_IRON`.
| Qualifying body-part object | Skill defaults only: `RES_BLUNT`, `RES_PARALYSIS`, `RES_NONMAGIC`.
|===

The initial learned-skill/level threshold is clamped to 5 through 95 as before.
The full contact mask then produces one resistance result, used to adjust
that existing success roll. No additional saving throw is introduced.

[cols="<2,<4",options="header"]
|===
| Effective response | Effect on the existing success chance
| Normal | Unchanged.
| Resistant | Halve the winning percentile outcomes, rounded down.
| Vulnerable | Add half the winning percentile outcomes, rounded down, retaining the existing upper threshold of 95.
| Immune, or invulnerable NPC | The knockout cannot succeed. No success affect, forced sleep or victim lag is applied.
|===

The roll remains `number_percent() < chance`. Thus a threshold of 41 means
40 winning outcomes; resistance changes it to 21 (20 outcomes), vulnerability
to 61 (60 outcomes). The upper threshold of 95 means at most 94 winning
outcomes. No minimum of five is re-applied after the resistance adjustment.

Resistance and vulnerability matching different categories of the same
attempt cancel to normal under the existing rule. For example, a silver
bludgeon against a Duergar Vampire matches paralysis resistance and silver
vulnerability, producing the normal success chance. Multiple material tags
or repeated innate weaknesses do not cause multiple multipliers. NPC
immunity takes priority over matching resistance and vulnerability.

This is distinct from the material-only chance scaling for Decapitate,
Assassinate and shield Hurl. Those three retain their previous semantics;
they share only the threshold arithmetic helper with Stun.

Stun remains player-operated: its early NPC-caller return is retained before
any `pcdata` access. Its existing target restrictions, head and size checks,
Gaia's Warning interaction, clan-guard exclusion and attacker action costs
remain. Inorganic NPCs are now excluded from a biological knockout.
Contact reachability is phase-aware; the existing single chance roll uses
that full resolved contact response. Failed or immune attempts use the
existing zero-damage failure path
rather than inventing positive damage. A successful attempt retains its
existing affect duration, forced-sleep behaviour and victim lag.

The result still uses `AFF_SLEEP`, but the skill is classified as paralysis,
not magical sleep. Elven `RES_SLEEP` alone therefore does not reduce a
physical Stun attempt; Duergar `RES_PARALYSIS` does. No new player immunity,
racial trait, skill-table flag, save-file field or Scribe keyword is added.

====== Finishing and status chances

Decapitate, Assassinate's level-based proc, and shield Hurl use one
material-based chance adjustment:

* immune: impossible;
* resistant: half the chance, rounded down;
* normal: unchanged;
* vulnerable: add half the chance, rounded down.

Matching material resistance and vulnerability cancel; immunity wins.
The existing upper thresholds are retained, and no lower minimum is
reapplied after the material adjustment.

The code preserves the existing strict-less-than percentile convention.
For example, a threshold of 21 permits 20 winning percentile outcomes.
Material resistance reduces those to 10; vulnerability increases them
to 30, subject to the existing ceiling.

Other matching contact immunity also prevents these effects, even when
it is not material immunity. Physical-type resistance or vulnerability
does not itself scale their percentage chance in this stage.

Assassinate retains its separate backstab and learned-assassinate checks.
Only its level-based proc is adjusted. Unkillable NPCs cannot be
assassinated. Immune Decapitate attempts cannot create a severed head
through the success branch. Decapitate now also excludes NPCs that
are both inorganic and no-corpse, avoiding fabricated severed heads for
the default ghost. Corpse-producing inorganic targets retain their
existing eligibility. These are NPC-only physiology checks.

====== Scope

Existing NPC live resistance masks and XOR authoring rules are unchanged.
The same contact and finishing-chance paths now also consult the selected
<<scribe-pc-innate-resistances,innate player traits>>. Player immunity is not
introduced, and duplicate silver weaknesses do not stack.

Weapon Stun is covered by its dedicated status-success integration above.
This stage does not extend Shoot, Snap Shot, Knife Toss, turret payloads,
Target/trauma, bleeding ticks or spells with object-material classification.
Other bespoke status-effect paths are not automatically rewritten.
The <<scribe-ghost-contact,ghost contact rules>> now govern these
supported physical paths. Automatic materialisation remains separate.

`holy_water` is liquid index 16. It has the ordinary hydration values of
water, but drinking it has an additional undead interaction in the server.
A living drinker receives the normal liquid effects only. A character for
which `IS_UNDEAD()` is true takes holy damage equal to one quarter of current
maximum hit points, with a minimum base of 10, through the normal DD4 damage
pipeline. The explicit damage category is `RES_HOLY`; resistance,
vulnerability and immunity to holy damage therefore apply once.

Drinking holy water from a fountain does not consume the fountain. Drinking
from a drink container consumes the ordinary rolled number of draughts before
the holy-water damage is resolved.

Holy water participates in the general liquid-splash command:

[source,text]
----
splash <container> <target>
----

`splash` is not specific to holy water. Any current liquid in a carried
`ITEM_DRINK_CON` can be splashed at another character.

A valid splash consumes up to five units of the liquid, retains the
container, costs one combat pulse of wait state, and identifies the actual
liquid in its messages.

Most ordinary liquids have no intrinsic mechanical splash effect. Water,
beer, wine, blood, salt water and the other existing liquids therefore only
produce the generic splash action unless another property of the container,
such as poison, supplies an effect.

Liquid-specific mechanics are resolved separately after the generic
delivery action. This allows later liquids to gain contact effects without
duplicating container, quantity, target and message handling.

Holy water has a special splash interaction against a target satisfying
`IS_UNDEAD()`. That combination is hostile and therefore passes through
`is_safe()` before any liquid is consumed. Holy water splashed on a living
target is otherwise an ordinary splash.

Against an undead target, holy-water base damage is the smaller of one
eighth of the target's maximum HP and four times the attacker's level,
with a minimum base value of 10. The damage is resolved exactly once as
`RES_HOLY`.

Holy resistance, vulnerability and immunity therefore apply normally.
The attack does not gain `RES_MAGIC`, silver, cold-iron or weapon-material
categories. Ghost phase does not prevent this supernatural holy effect.

A non-zero drink-container `value[3]` marks the contained liquid as poisoned.
When that liquid is splashed onto a suitable living, organic target, it attempts
to apply the normal poison affect. This is `RES_POISON` contact, not magical
poison, and does not add `RES_MAGIC`.

Inorganic creatures and object-like NPCs cannot be poisoned this way. Existing
poison immunity, resistance and vulnerability apply through the shared
resistance machinery. Player `Resist Toxin` and `Bonus Exotic` retain their
normal protection.

Poison and the liquid's own effect are independent. Poisoned holy water can
therefore attempt to poison an eligible organic undead target and also apply
the normal holy-water effect.

Apart from holy water and poison, current liquids have no combat, status or
environmental splash effect.

Room fountains cannot be used directly by `splash`. Fill a carried drink
container first.

Future splash effects should be added to the liquid-specific resolver
rather than by adding liquid-specific branches throughout `do_splash()`.

[[scribe-object-undead]]
==== Undead objects, corpses, remains and body parts

`ex undead` represents the object extra flag `ITEM_UNDEAD` (`BIT_31`, decimal
`2147483648`). It marks undead nature or undead provenance and may be applied
to *any* object type, including flavour items. It is not a new object type.

[source,text]
----
$obj
vn  8
nm  relic black bone
sh  a black bone relic
lo  A black bone relic lies here.
ty  treasure
wg  1
we  take
ex  undead
----

This does not animate the object, give it creature resistances, make its
holder undead, or turn a treasure into a corpse. A downstream spell or skill
must explicitly interpret the flag for it to affect that mechanic.

===== Automatic provenance on death-generated objects

When the dying character satisfies `IS_UNDEAD()`, the death-generation paths
add `ITEM_UNDEAD` to the corpse/remains object and generated body-part objects.
This includes NPC corpses, PC corpses (including vampire PCs), objectlike
mobile remains and the generated fragments/body parts appropriate to the
source's anatomy.

[cols="<2,<5",options="header"]
|===
| Existing object kind | Interaction with the provenance flag
| `ITEM_CORPSE_NPC` | An undead NPC's generated corpse is tagged.
| `ITEM_CORPSE_PC` | An undead PC's generated corpse is tagged; currently the common PC undead classification is vampire.
| `ITEM_REMAINS` | An undead objectlike mobile's generated remains are tagged.
| Generated body-part or fragment objects | Receive the tag from the undead source even when their object type is not a corpse type.
| Existing carried equipment and loot | Do not become undead merely because their owner died or because they are placed inside a tagged corpse.
|===

`ACT_OBJECT` (`act objectlike`) selects the objectlike remains path.
`BODY_INORGANIC` is a separate anatomical property and is not, by itself, the
switch from an NPC corpse to `ITEM_REMAINS`. Existing body-form tests also
affect which death descriptions and body fragments are generated.

`BODY_NO_CORPSE` suppresses corpse production. There is then no corpse/remains
container to tag, and dropped belongings retain their own flags. The
classification is captured when an object is generated; it is not reconstructed
later from a character which no longer exists.

===== Visibility and immortal inspection

Identification reveals the object's undead extra flag. Ordinary room and
inventory descriptions do not gain an automatic visible `(Undead)` marker
from this addition. `ostat` displays the extra flag for immortal inspection.
`oset` retains its existing whole-mask extra-flags interface; this change does
not add a new text-based toggle command.

The `undead` object flag records provenance. Do not assume that merely
setting it changes healing, permits animation, or supplies a combat effect.

=== 10. Object sets [[scribe-object-sets]]

Object sets are groups of related wearable objects that grant extra bonuses when enough pieces are worn together. Define the objects normally using `$obj` blocks, then define the set itself with an `$objset` block.

*Block header:* `$objset` or `$objectset`

*`vn` — Vnum*

_Number: 0 or higher_

The relative vnum of the object set. Scribe adds the area base vnum when writing the final #OBJECT_SETS section.

*`nm` — Name / keywords*

_Line of text_

The identifying name or keywords for the set. This is written as the set keyword string.

*`de` — Description*

_Multi-line text block_

The description of the object set. Terminate the block with a single tilde.

*`ob` — Set member object*

_Number: 0 or higher_

The relative vnum of an object belonging to this set. Use one ob line per set item. Scribe writes up to five members. Missing members are written as 0.

*`bt` — Bonus threshold*

_Number: 0 or higher_

Defines how many worn set pieces are required for the corresponding bonus tier. Use one bt line per possible bonus. Scribe writes up to five thresholds. Missing thresholds are written as 0.

*`ap` — Apply effect*

_Line of text_

Defines a bonus applied by the set. Use the same apply keywords as normal object ap fields.

Important: set bonuses are applied in reverse order by the game, so put the strongest bonus first.

The below example writes an `#OBJECT_SETS` entry with two set members. When enough pieces are worn, the set grants the listed apply bonus.

[source, text]
----
$objset
vn      2
nm      uncommon crow
de
The Smithy's Set of the Crow.
~
ob      4
ob      5
bt      2
bt      2
ap      fly -1
----

lock    closed and locked
----

The reset will only be used if the relevant exit has been defined and that exit is a door.

[source, text]
----
E.g.    e   2
    elo door
    eds close
----

Unless otherwise desired (e.g. one-way doors), use the same door reset in both rooms sharing a door for consistency.

*`am` — Room ambient sound file path*

_Line of text_

Relative path to a room-specific ambient sound file. This overrides area and sector ambience.

*`av` — Room ambient volume*

_Number: 0 to 100_

Volume for the room ambient loop. Defaults to 25 if am is set and av is omitted.

*`mu` — Room music file path*

_Line of text_

Relative path to room-specific music. The path must contain no spaces and must begin with music/. This replaces the area music while the player remains in the room.

[source, text]
----
E.g.    mu    music/room/submerged_temple.mp3
----

*`mv` — Room music volume*

_Number: 0 to 100_

Volume for the room music layer. Defaults to 25 if mu is set and mv is omitted.

=== 12. Mobile resets [[scribe-mobile-resets]]

A _reset_ refers to an action performed by the MUD to manipulate and update the world's areas. Mobile resets determine how mobiles are loaded into your area: what rooms they appear in, how many may appear and what objects they are wearing or carrying. The $*addmob* block is used to describe a single mobile reset. You may have as many $*addmob* blocks as you like in your area. You do not need to have any mobile resets for your area to be valid. You may use any particular rooms and mobs as many times as you wish.

*Block header:* `$addmob` or `$addmobile`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `mb`
| mobile vnum
| number
| `rm`
| room vnum
| number
| `num`
| maximum mobile number
| number
| `inv`
| item in inventory
| number
| `*`
| equip item
| number
|===

`*` See below for list of _equip_ fields.

*`mb` — Mobile vnum*

_Number: 0 or higher_

The relative vnum of the mobile you wish to load. A mob using this vnum must be defined otherwise Scribe will indicate an error.

*`rm` — Room vnum*

_Number: 0 or higher_

The relative number of the room you wish to load the mobile into. A room using this vnum must also be defined otherwise an error will result.

You can add as many `rm` fields as you like to a single $*addmob* block, and identical mobiles carrying and wearing all equipment specified will be loaded into each room (up until the limit specified by the `num` field).

*`num` — Maximum mobile number*

_Number: 1 or higher_

_Default: 1_

The maximum number of mobiles with this vnum that can be loaded into the world (all areas) at any one time.

*`inv` — Item in inventory*

_Number: 0 or higher_

The relative vnum of any object you wish the mob to carry. An object using this must be defined otherwise an error will result. You do not have to include any `inv` fields in your reset; you may give a reset as many `inv` fields as you like.

*`*` — Equip an item*

_Number: 0 or higher_

Equip an object on the mob. The following format is used:

_<position> <relative vnum>_

_Position_ is any of the following:

[source, text]
----
light   light source
finger1
finger2
neck1
neck2
body
on body
head
legs
feet
hands
arms
shield
about   about body
waist
wrist1
wrist2
wield   primary weapon
dual    secondary weapon
ranged  ranged weapon (lance, bow)
hold    held in hand
float   orbiting head
pouch   belt pouch
----

You may equip as many items as you wish; if you indicate the same position more than once, the last instance defined will be used.

*Examples*

_Load a single naked mob to a room:_

[source, text]
----
$addmob
mb  1
rm  3
----

_Load a naked mob to rooms 30, 32 and 33 (relative vnums); keep adding a mobile to these rooms every time the area resets until there are 6 mobs in the MUD:_

[source, text]
----
$addmob
mb  4
rm  30
rm  32
rm  33
num 6
----

_Load and equip a mob:_

[source, text]
----
$addmob
rm  3
mb  3
wield   7
inv 6
shield  9
body    8
inv 5
inv 5
----

=== 13. Object resets [[scribe-object-resets]]

Object resets determine how objects other than those given to mobiles are loaded into your area: objects that appear on the ground in rooms, and objects that are placed inside other objects. The *$addobj* block is used to describe a single object reset. You may have as many *$addobj* blocks as you like in your area. You do not need to have any object resets for your area to be valid. You may use any particular rooms and objects as many times as you wish.

*Block header:* `$addobj` or `$addobject`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `ob`
| object vnum
| number
| `rm`
| room vnum
| number
| `lv`
| level of object
| number
| `con`
| container object vnum
| number
|===

*`ob` — object vnum*

_Number: 0 or higher_

The relative vnum of the object you wish to load.

*`rm` — Room vnum*

_Number: 0 or higher_

The relative number of a room you wish to load the object into. A room using this vnum must also be defined otherwise an error will result.

*`lv` — Level of object*

_Number: 0 or higher_

The level you wish the object to be. *Only applies if the object is reset to the ground and NOT to a mob or container*.

*`con` — Container vnum*

_Number: 0 or higher_

The relative number of a container object you wish to place the item in. A container object with this vnum must be defined for the reset to be valid.

Only one of each kind of object may occupy any single container. The object is loaded to the most recently loaded container with the specified vnum. For best results, only load one of each container object into your area.

You need to have at least one `rm` or one `con` fields for the *$addobj* block to be valid.

*Examples*

[source, text]
----
$addobj
ob  4
rm  12

$addobj
ob  2
rm  6
rm  7
con 12
----

=== 14. Games [[scribe-games]]

You can allow mobiles to host gambling games in the MUD.

*Block header:* `$game`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `mb`
| mobile vnum
| number
| `gm`
| game name
| text
| `br`
| bankroll
| number
| `mw`
| max wait time
| number
| `ch`
| cheat value
| number
|===

*`mb` — Mobile vnum*

_Number:1 or higher_

Number of the mobile in charge of the game (dealer or croupier, for example)

*`gm` — Name of game*

_Line of text_

The name of the game. Current games available are

[source, text]
----
ult     Upper-Lower-Triple, a dice game
highdice    High dice, a dice game
seven       Seven, a dice game
----

*`br` — Bankroll*

_Number: 0 or higher_

the amount of gold that the mob running the game has when it is loaded. When the bankroll goes below zero, the mob shuts down its game. Currently games can only be conducted with gold pieces.

*`mw` — Max wait time*

_Number: 0 or higher_
_Default: 8_

The number of PULSE_MOBILEs the croupier will wait for each person to make a decision for interactive games (currently unimplemented).

*`ch` — Cheat value*

_Numbe: 0 or higher_

Whether the mobile running the game will cheat or not. If the cheat value is non-zero, he will cheat.

`mb`, `gm`, `br`, and `ch` values are required for a $game block to be valid.

*Example*

[source, text]
----
$game
mb  3001
gm  ult
br  50000
mw    24
ch    0
----

=== 15. Helps [[scribe-helps]]

You can define help file entries in your area using the *$help* block. You don't have to include any *$help* blocks in your area for it to be valid.

*Block header:* `$help`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `he`
| Help text
| Multi-line text block
| `lv`
| Level restriction
| number
|===

*`he` — Help text*

_Multi-line text block_

Define the help entry keywords and body text using the `he` field:

[source, text]
----
he  <keywords or phrases>
<help text>
~
----

The _keywords or phrases_ string is automatically capitalised by Scribe.

[source, text]
----
E.g.    he  fly levitate
This is the text displayed whenever the
commands HELP FLY or HELP LEVITATE
are entered.
~

he  'aura of fear'
This is the text displayed whenever the
command HELP 'AURA OF FEAR' is issued.
~
----

*`lv` — Level restriction*

_Number: -1 or higher_

The minimum level a character has to be in order to access the help entry. `0` is used for general help entries. Use `–1` if you want the help entry keyword header to be hidden.

=== 16. Shops [[scribe-shops]]

Mobiles can be made to run shops: the inventory of the shop is the inventory of the mobile. So long as the mobile is alive, players can attempt to buy and sell items from the shop.

*Block header:* `$shop`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `vn`
| Vnum of shopkeeper
| number
| `t1`
| Traded item type 1
| keyword
| `t2`
| Traded item type 2
| keyword
| `t3`
| Traded item type 3
| keyword
| `t4`
| Traded item type 4
| keyword
| `t5`
| Traded item type 5
| keyword
| `ps`
| Profit-sell
| number
| `pb`
| Profit-buy
| number
| `oh`
| Opening hour
| number
| `ch`
| Closing hour
| number
|===

*`vn` — Vnum of shopkeeper*

_Number: 0 or higher_

The relative vnum of the mobile that will run the shop.

*`t1-t5` — Traded item types*

_Keyword_

The item types that the shopkeeper will be prepared to buy from players. You may indicate up to five types; you don’t have to specify any types for the shop to be valid. Use the same keywords used to define item types.

[source, text]
----
E.g.    t1  weapon
t2  armour
----

*`ps` — Profit-sell*

_Number: 0 or higher_

The percentage markdown on items sold to the shopkeeper. `100` is the intrinsic value of the item, `75` is a 25% markdown, etc. This value should be at most 100%.

*`pb` — Profit-buy*

_Number: 0 or higher_

The percentage mark-up on items bought from the shopkeeper. `100` is the intrinsic value of the item, `150` is a 50% mark-up, etc. This value should be at least 100%.

*`oh ch` — Opening and closing hours*

_Number: 0 - 23_

The times when the store opens and closes (`0` = midnight).

*Example*

[source, text]
----
$shop
vn  0
t1  wand
t2  staff
t3  potion
t4  scroll
oh  7
ch  18
ps  85
pb  120
----

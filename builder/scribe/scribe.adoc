=== 1. Introduction [[scribe-introduction]]

_DD Area Scribe_ or _Scribe_ is a tool for producing formatted area files for the Dragons Domain Envy-style MUD. DD area files retain the Envy MUD format, with changes to the `#AREA` header information and the addition of new variables and flag values to other sections.

Scribe is a script that reads a simplified text source file containing all area information, validates the information, and if no serious errors are found, outputs a formatted area file. Scribe is written in Perl and is run from the command line (see Section 2).

Scribe was written as an alternative to writing area files by hand or by using the existing Windows tool _MZF_. The advantages and disadvantages of each of these systems might be summarised:

==== Writing areas by hand

Laborious; lots of redundant variables to include. Unsafe; no error or format checking.

==== Using the MZF tool

Easy to use; convenient and simple user interface. Format and variable checking provides some safety. Buggy; contains known bugs and bizarre behaviours. Incompatible with DD; MZF does not contain DD's special flags and values; output requires hand-editing. Win16/32 executable only.

==== Using the Scribe tool

Fairly laborious; all data hand written, although in a friendly, human-readable format. Safe; variable checking and correct formatting. Compatible; contains all DD special variables and flags. Requires Perl 5 for compilation.

Scribe meets writing areas by hand and using MZF midway, providing full DD-server compatibility and error checking, but not including a simple to use graphical interface.

=== 2. Usage [[scribe-usage]]

Producing an area file with Scribe involves the following steps:

==== 1. Source file is written

The area source file contains all of the relevant information to be included in the final, correctly formatted area file. It is a text file with a simple, human-readable format that is easy to edit. Information can be added to the source file in any order.

==== 2. Scribe is used to check the source file and write the area

Scribe is used to process the area source file. It reads through the source file checking for obvious formatting errors and then validates this information, filling in any missing variables where it can. If there are serious errors then Scribe will indicate where they occur in the source file and then exit. If there are no serious errors, then the area is formatted and written to file.

Scribe is a Perl script that is run from the command:

`scribe.pl` _<source file> <destination file>_

For example,

[source, text]
----
scribe.pl kahsis.src kahsis.are
----

Area files traditionally have the `.are` extension. Both source and destination files must be indicated for the script to run. Scribe will create a backup copy of any existing destination file.

=== 3. What's Perl? [[scribe-perl]]

If you are not able to run Perl but would like to use this script to produce your areas, you can write your source files and send them to one of the DD Immortals, who will test the file and inform you of any errors.

=== 4. Producing source files [[scribe-source-files]]

The area source file consists of discrete blocks of data that each define area information (area name, author, etc), one mob (mobile, creature), one room, one object, one mobile reset, one object reset, one shop or one help file entry. Some reset information (e.g. shutting doors and mob special functions) are included in the above blocks. Blocks may occur in any order within the source file.

A *block* consists of a *header* indicating the type of data it defines, followed by a list of *field* and *value* pairs. Fields are short keywords representing room, object, mobile or area variables. A block is terminated by the start of another block or the end of the source file.

*Headers* are single words preceded by a dollar sign `$` and occupy one line. Field keywords and values are separated at least one space or tab (one tab is nice). Field/value pairs occupy one line unless they define multiple-line text blocks, in which case they are terminated by a line containing a single tilde `~`. You should not terminate single line strings of text with a tilde: these will be automatically added by Scribe.

Blocks have the following format:

[source, text]
----
$header
field1          value1
multiple_line_field
<lines of text>
~
field2          value2
...
fieldN          valueN
----

For example, the following block defines the name, short name, long name, description, sex, affect flags, vnum, level and act flags variables for a mobile:

[source, text]
----
$mob
nm  octopus
sh  an octopus
lo  An octopus crawls along the coral.
de
The octopus' slimy body is purple with bright red blotches.
It crawls over the coral, its tentacles writhing horribly.
~
sx  female
aff hide sneak
vn  1
lv  5
act scavenger wimpy stay_area
----

(Field/value pairs for each type of block are discussed in detail in Section 5 onwards.)

Field/value pairs can be arranged in any order within the block. Multiple definition of the same field can be made, although only the last instance will be used. The dollar sign `$` at the beginning of a line indicates the beginning of a new block, so should be avoided.

Your source file will consist of a series of blocks of any type in any order. Use your favourite text editor to produce the source file. All text before the first block header is ignored, so you can add comments if you wish. Your source file must contain an *$area* block in order to be compiled without error.

Source file format:

[source, text]
----
Any number of comments at the start of the file.
$area   <area header information>
$...    <mobile, room, object, etc blocks as desired>
----

You may add comments at any point in your area file by prefixing them with a non-alphanumeric symbol that is not a dollar sign `$`, e.g. `#`, `;` or whatever symbol you prefer.

[source, text]
----
. This is a comment
# So is this
; The line below is a header
$mob
. This is a comment within a $mob block
----

==== Note

Make sure that you hard-wrap lines of text in multi-line text blocks to under 80 columns, i.e. supply a carriage-return at the end of every line. Make sure your text editor isn't soft-wrapping your text!

=== 5. Area header and base vnum definition [[scribe-area-header]]

The *area header* block defines the `#AREA` section of the final area file. It describes the name and author of the area, and character access information. One definition is required, or your source file will produce errors.

==== Note on Vnums

_Vnums_, or _virtual numbers_, are the unique identification numbers for the mobiles, rooms and objects in your area. No blocks of the same type (mobs versus rooms versus objects) may share the same vnum; blocks of different types may share a particular vnum. Vnums are indicated as relative numbers in the area source file (usually beginning at zero).

Scribe uses _relative vnums_: the vnums used in the source file are numbered from 0 upwards. A base vnum is defined in the area header block and is used to calculate absolute vnums from the relative values:

[.text-center]
`Final vnum in area file = base vnum + relative vnum`

If you have been allocated a range of vnums from the DD Immortals for use in your area (e.g. 2600-2799), use the lowest vnum as your base (2600), and number your mobs, rooms and objects from zero upwards. If you haven't been given a range of vnums, you should still number mobs, rooms and objects from zero up, and just use any value for your base value. The use of a base value allows you to easily renumber your area if necessary, e.g. when you are finally given some to use by those lazy Imms.

If you need to use vnums for rooms, mobiles or objects that are not defined in the same source file (i.e. are defined in other areas), you need to use temporary holding values and manually edit the formatted area file produced by Scribe.

*Header:* `$area`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `au`
| author
| text
| `ti`
| title
| text
| `ls`
| lower level suggested
| number
| `us`
| upper level suggested
| number
| `le`
| lower level enforced
| number
| `ue`
| upper level enforced
| number
| `bv`
| base vnum
| number
|===

*`au` — Author*

_Line of text_

The person or people responsible for writing the area.

*`ti` — Title*

_Line of text_

The name of the area. Don't make it too long (25 characters maximum).

*`ls us` — Suggested level range*

_Number: 0 or higher_

The suggested level range for travelling to your area, as shown in the online _AREAS_ command. Use these values to indicate what level of character would profit from visiting your area; don't use them to indicate the lowest and highest level mobs (1, 100 is fairly unhelpful).

*`le ue` — Enforced level range*

_Number: 0 or higher_

The level range for permitted entry to your area. Characters outside this range may not access the area and get the ‘God prevents you from entering there’ message when they try.

Note: only the lower level limit is currently enforced.

*`bv` — Base vnum*

_Number: 0 or higher_

The base value used to calculate absolute vnums from relative vnums. Note that if your area links to other areas in the MUD and you want to be able to have these links active while you build, it may be best to set this to 0 and use absolute vnums in your .src file, for convenience’s sake.

*Example*

[source, text]
----
$area
ti  The Planet Vulcan
au  Mr Spock
ls  75
us  90
le  0
ue  100
bv  2600
----

=== 6. Recall header [[scribe-recall-header]]

The *recall header* block defines the `#RECALL` section of the final area file. It provides the author with an opportunity to override the default recall room location for a player who is adventuring in the area.

*Header:* `$recall`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `rl`
| recall location
| number
|===

*`rl` — Recall location*

_Number: vnum of a room in the MUD_

The vnum of a room a character in this area should recall to by default. Does not have to be in the current area. If the character has multiple recalls available and is using a non-default one, they will recall there, and not to the #RECALL location.

*Example*

[source, text]
----
$recall
rl  27347
----

_Line of text_

Flags that produce area-wide effects. They include:

[source, text]
----
school  area is a MUD SCHOOL (new character

----

----

*`xp` — experience modifier*

_Number: 0 or higher_

An area-wide contribution to the mobile XP percentage. `100` is the neutral
area value, `50` is half and `200` is double at this percentage stage when no
other contributions alter the total. Normal resets also include the existing
special-function and equipment adjustments; the creature archetype's
`xp_mod` is added to that same percentage rather than multiplied separately.
See <<scribe-template-xp,Archetype XP bonuses and penalties>> for the combined
calculation and the existing minimum-reward qualification.

[source, text]
----
E.g.    xp  125
----

*`rm` — reset message*

_Line of text_

A custom reset message for the area (seen by players and imms in an area when it resets, or by an imm using the ‘reset’ command).

[source, text]
----
E.g.    rm  Water swirls through the ruins.
----

*`rs` — area reset sound file path*

_Line of text_

An optional replacement for the default one-shot notification sound played when the area reset message is shown. The path is relative to the MUD audio directory, must contain no spaces, and should normally begin with notify/.

If this field is omitted, the default reset sound is: notify/area_reset.mp3

[source, text]
----
E.g.    rs notify/area/swamp_reset.mp3
----

*`rv` — area reset sound volume*

_Number: 0 to 100_

Source volume for the area reset notification sound. A value of 0 disables the reset sound for this area. Values from 1 to 100 override the default source volume. If this field is omitted, the default volume of 60 is used. The rv field may be used without rs to change the volume of the default reset sound. The final volume is scaled by the player's master and notification volume settings.

[source, text]
----
E.g.    rv 55
----

*`am` — area ambient sound file path*

_Line of text_

Relative path to an ambient sound file to use for atmospheric sound for the area. This will play throughout the area on loop unless a room sound file exists.

[source, text]
----
E.g.    am ambient/area/crypt.mp3

----

*`av` — area ambient volume*

_Number: 0 to 100_

Volume setting for ambient loop. Will be scaled by player master volume level.

[source, text]
----
E.g.    av 25
----

*`mu` — area music sound file path*

_Line of text_

Relative path to a music sound file to use for background music for the area. This will play throughout the area on loop unless a room music file exists, and independently of the ambient sound layer.

[source, text]
----
E.g.    mu music/area/crypt.mp3

----

*`mv` — area music volume*

_Number: 0 to 100_

Volume setting for the area music loop. It is scaled by the player's master and music volume settings.

[source, text]
----
E.g.    mv 25
----

*Example*

[source, text]
----
$special
af hidden no_teleport
xp 125
rm Water swirls through the ruins.
rs notify/area/ruins_reset.mp3
rv 55
am ambient/area/crypt.mp3
av 25
mu music/area/crypt.mp3
mv 20
----

[[scribe-mobile-inheritance]]
==== Body species, creature archetypes and individual mobile flags

A *body species* describes a broad physical form, such as `humanoid`,
`elemental` or `farm_mammal`. A *creature archetype* is a more specific entry
in the server's `mob_table`, such as `goat` or `fire_elemental`, which refers
to one body species. A particular `#MOBILES` entry supplies the individual
mobile's descriptions, level, flags and other area-authored values.

For the ACT, AFF and body-form flags already supported by Scribe, the server
resolves the layers in this order:

[source,text]
----
body-species defaults XOR creature-archetype masks
    = inherited template

inherited template XOR original individual #MOBILES mask
    = effective prototype flags

copy prototype flags when an NPC is created
    = initial live flags
----

Runtime spells, equipment, resets and immortal commands can subsequently
change the live instance. They do not repeatedly reapply XOR to that instance.
The original individual masks are retained separately from the prototype's
effective values.

===== Adding and removing inherited flags

For one flag, the individual mask has the following meaning:

[cols="<1,<1,<1,<3",options="header"]
|===
| Inherited bit | Individual bit | Effective bit | Result
| Off | Off | Off | Leave the flag absent.
| Off | On | On | Add the flag.
| On | Off | On | Keep the inherited flag.
| On | On | Off | Cancel the inherited flag.
|===

`none`, `zero`, `0`, or omission of an existing flag field means an empty
*individual* mask. On a templated mobile, that inherits the corresponding
template unchanged; it does not clear all inherited flags. On an untemplated
mobile, the inherited mask is zero, so the existing ordinary flag behaviour
is preserved.

Example: suppose an archetype supplies `ACT_UNDEAD`. Its individual Scribe
field `act undead` cancels that classification. The same field gives an
untemplated mobile the undead classification. The meaning depends on the
selected template, not on the flag word alone.

[source,text]
----
# Keep an inherited undead flag and add sentinel:
act sentinel

# Cancel an inherited undead flag and add sentinel:
act undead sentinel
----

These lines illustrate the individual mask only. The archetype must also be
selected in the generated area entry as described below. They do not define
or select a skeleton archetype by themselves.

Within a single field, flags form one mask. Repeating a word within the field
is not another inheritance layer. Repeating the same source field replaces
its earlier definition; it is not an additional XOR operation. The server
logs bits cancelled at the template-to-individual boundary, rather than
requiring builders to discover those cancellations through combat.

===== Protected engine flags

`ACT_IS_NPC` is always enabled on an NPC prototype. It cannot be cancelled
through inheritance. `AFF_CHARM` is always removed from the initial prototype:
charm is a runtime relationship, not a safe way to create a pre-charmed mobile
by listing `aff charmed`. Scribe can recognise the word, but recognising it
does not override this server restriction.

===== Body-form masks and migration

The body-form mask contains both `BODY_*` restrictions and positive `PART_*`
flags. They are independent bits. To remove an inherited heart represented by
`PART_HEART`, cancel that bit and add `BODY_NO_HEART` where the intended
anatomy requires it. Adding a negative flag does not automatically remove a
positive part flag, and removing a positive part flag does not necessarily
satisfy the engine's negative-flag anatomy tests.

The Scribe `bf` keyword list remains the list documented below; template
support does not automatically add every `PART_*` C constant as a Scribe
keyword. A combined non-negative decimal mask can be used for supported bits
whose textual names are not in Scribe. Consult `merc.h` for their values.

When moving an existing mobile onto a template, inspect its old individual
flags before regenerating the area. Duplicated defaults now mean cancellation.
For example, the elemental template supplies `BODY_NO_ARMS` and
`BODY_NO_LEGS`. An old individual body mask of `12` (4 + 8) cancels both;
changing that individual mask to `0` retains the inherited restrictions.

Do not put the final expanded flags back into `act`, `aff`, or `bf` on export.
Doing so can cancel the very defaults the editor intended to preserve.

[[scribe-template-selection]]
===== Selecting an archetype: `.are` syntax versus Scribe syntax

The server reads an optional mob-spec/rank line in a mobile's `.are` entry:

[source,text]
----
< fire_elemental~ elite~
----

The first string selects the creature archetype; the second selects the rank.
The archetype in turn names its body species. Template definitions are
server-side C tables and require a server rebuild when changed.

The verified Scribe script does *not* provide a source field for choosing a
creature archetype. Its `sp` field chooses a special function, and `rnk`
chooses a rank. For a non-default rank, Scribe currently emits a line such as:

[source,text]
----
< reserved~ elite~
----

A workflow using Scribe must therefore preserve or apply the desired archetype
in the generated `.are` file after generation, replacing that `reserved`
selection when necessary. Do not put the literal `< ...~ ...~` line into a
Scribe `$mob` source block and expect it to be recognised. Regenerating the
area can overwrite a hand-edited archetype selection.

The resistance and attack-part field additions do not add a source-level
archetype selector. DD Builder integration must preserve this distinction too.

===== Template fields which are not yet live defaults

The resolved template contains ACT, AFF, body form, attack parts, resistance
masks, HP/damage/critical/haste modifiers, dimensions, size, language, special
names and the archetype XP adjustment. The presence of a value in a template
diagnostic is not proof that it is already applied to a live mobile.

In the verified baseline, ACT/AFF/body and resistance masks are resolved at
prototype loading and copied into live NPCs; resistance calculations read the
live masks; and `xp_mod` is used by the XP helper.

Step 4C3a adds prototype/live storage and individual overrides for attack parts.
This does not yet connect those parts to automatic attack selection, damage
calculation, equipment creation or new skill permissions. The remaining template
scalar defaults still require live application. Special-function names are
resolved and validated without automatically activating all three slots.

For the template scalar fields using `MOB_TEMPLATE_UNSET`, an archetype value
inherits when it is unset; otherwise it replaces the body-species value.
Literal zero is an explicit scalar value. If neither layer supplies a value,
the resolver returns zero. This is a C-table convention, not new Scribe input
syntax.

For template special names, `NULL` means inherit, an empty string explicitly
clears an inherited name, and a non-empty string replaces it. The existing
single active `sp` special remains the builder-facing mechanism until active
special inheritance is implemented. `xp_mod` has its own zero-based additive
rule, described in <<scribe-template-xp,Archetype XP>>.

==== Mobile source fields

*`nm` — Name (keywords)*

_Line of text_

The keywords that can be used to indicate the mob.

[source, text]
----
E.g.    nm  wraith hazy shadow
----

*`sh` — Short description*

_Line of text_

The short name of the mob, used whenever an action is performed involving the mob. Don't capitalise any leading ‘a’, ‘the’, ‘an’, etc: the DD server does automatically where necessary.

[source, text]
----
E.g.    sh  an alligator
sh  the Gatekeeper
sh  Mycroft
----

*`lo` — Long description*

_Line of text_

The description of the mob as it appears in room after the _LOOK_ command is issued. Capitalise the initial letter and don't make the description too long if the mob will have many affect flag labels like _(White Aura)_ and _(Flaming)_. Remember full stops etc.

[source, text]
----
E.g.    lo  A snake lurks in the grass.
----

*`de` — Description*

_Multiple-line text block_

[[scribe-mobile-undead]]
==== Undead mobile classification

`act undead` represents `ACT_UNDEAD` (`BIT_30`, decimal `1073741824`). It
classifies an NPC as undead; it does not automatically assign an alignment,
anatomy, mindlessness, spell immunity, or an entire skeleton/vampire behaviour
package. Supply those traits separately through the relevant flags and
archetype definition.

The common server test is `IS_UNDEAD(character)`. For NPCs it checks the live
`ACT_UNDEAD` flag. For PCs the currently supported case is
`SUBCLASS_VAMPIRE`; this work does not introduce a general `PLR_UNDEAD`
builder flag.

Use the same <<scribe-mobile-inheritance,XOR rule>> when an archetype already
supplies `ACT_UNDEAD`. `mstat` is the way to distinguish an inherited flag,
an individual cancellation and the actual live classification.

[source,text]
----
$mob
vn  7
nm  revenant watchman
sh  a revenant watchman
lo  A revenant watchman stands motionless beside the gate.
de
The watchman's ruined face turns slowly towards you.
~
lv  25
act undead sentinel
----

This example directly flags an otherwise untemplated mobile. It does not
select a new creature archetype or grant any implicit resistance package.

Object provenance uses the separate `ex undead` flag, documented under
<<scribe-object-undead,Undead objects and generated remains>>. Giving an
object that flag does not make its holder undead.

[[scribe-individual-resistances]]
==== Individual resistance fields

These fields were merged in PR #708 and are present in the verified baseline.
Use a server and Scribe script containing those changes; see
<<scribe-documentation-status,Documentation status>>.

*`res` — Resistance XOR mask*

_Keyword list or combined non-negative decimal mask_

_Default: omitted; inherit without change_

Adds or cancels bits in the inherited resistance mask.

*`vuln` — Vulnerability XOR mask*

_Keyword list or combined non-negative decimal mask_

_Default: omitted; inherit without change_

Adds or cancels bits in the inherited vulnerability mask.

*`imm` — Immunity XOR mask*

_Keyword list or combined non-negative decimal mask_

_Default: omitted; inherit without change_

Adds or cancels bits in the inherited immunity mask.

Each field is resolved independently. A zero mask inherits that category; it
does not clear it. A mobile without an archetype has zero inherited masks,
so these fields can directly give it resistances, vulnerabilities or immunities.

Scribe accepts keywords separated by spaces, or one combined decimal number:

[source,text]
----
res cold sonic
vuln fire
imm poison paralysis
----

Use the <<scribe-resistance-flags,resistance keyword reference>> below.
`none` and `zero` are aliases for an empty mask. A blank, explicitly supplied
field is invalid. Numeric masks must contain only defined resistance bits.
There is no `RES_NONE` C macro; zero is the empty mask.

A compact expression such as `1|256` is server `.are`/`mset` syntax, not a
Scribe keyword list. For Scribe use `fire poison` or the combined number
`257`. Repeating the same Scribe field uses its last definition.

===== Generated area fields and placement

[cols="<1,<2,<4",options="header"]
|===
| Scribe field | Generated `.are` field | Meaning
| `res` | `MobResists` | Individual resistance XOR mask.
| `vuln` | `MobVulnerabilities` | Individual vulnerability XOR mask.
| `imm` | `MobImmunes` | Individual immunity XOR mask.
|===

The generated fields follow the ordinary mobile data, any mob programs,
the optional archetype/rank line and teacher entries. They may accompany the
optional `FStep...` fields, before the next mobile entry or `#0` terminator.
They do not use a tilde terminator.

[source,text]
----
< fire_elemental~ elite~
MobResists 2
MobVulnerabilities 1
MobImmunes 1
----

This is an *area-file tail*, not a Scribe source block. The values above add
cold resistance, add fire vulnerability, and cancel inherited fire immunity.
It assumes the selected template starts with fire immunity and no conflicting
cold resistance state.

The `.are` parser accepts a decimal mask or decimal values joined by `|`
without spaces. Values within that one mask are ORed together. Repeating an
area field replaces its earlier individual mask; it does not toggle the
inherited state a second time.

Negative numbers, unknown bits, overflow and malformed expressions are
rejected. For example, `4194304` is bit 22 and is undefined in this revision.

===== Moving a category between resistance states

Suppose the inherited template is immune to fire. This Scribe input changes
that category to vulnerability:

[source,text]
----
vuln fire
imm fire
----

The repeated fire bit in `imm` removes inherited immunity; the fire bit in
`vuln` adds vulnerability. Overlap between these *input* masks is intentional.
Only the fully resolved state must be free of contradictory categories.

Adding `vuln fire` alone leaves the inherited immunity active and creates a
conflicting effective definition. The boot diagnostic reports the conflict;
the established runtime resolver still gives immunity precedence.

Raw masks remain builder input. The server resolves a prototype once and
copies its effective masks into independent live instances. It does not
re-XOR the template on each attack. Live edits therefore affect only the
chosen instance, as described under <<scribe-mobile-diagnostics,inspection
and live editing>>.

[[scribe-individual-attack-parts]]
==== Individual attack-part masks — Step 4C3a

IMPORTANT: This section accompanies the Step 4C3a code changes. It is not a
claim that those changes were present in PR #709. Install the server and
Scribe additions before using `atk` or `MobAttackParts`.

*`atk` — Attack-part XOR mask*

_Keyword list or combined non-negative decimal mask_

_Default: omitted; inherit without change_

An attack-part mask records natural offensive body features separately from
`bf` (general morphology). The server first resolves body-species and archetype
attack parts with XOR, then XORs the individual `atk` mask over that result.
The raw input, effective prototype and each live instance remain separate.

The accepted values are the existing `PART_*` combat group in `merc.h`, not
new low-order flags. In particular, these numbers must not be treated as
resistance values or converted through a 32-bit integer.

[cols="<2,<2,<2",options="header"]
|===
| Scribe keyword | C flag | Decimal bit
| `claws` | `PART_CLAWS` | 8589934592
| `fangs` | `PART_FANGS` | 17179869184
| `horns` | `PART_HORNS` | 34359738368
| `tusks` | `PART_TUSKS` | 68719476736
| `tail` | `PART_TAILATTACK` | 137438953472
| `sharp_scales` | `PART_SHARPSCALES` | 274877906944
| `beak` | `PART_BEAK` | 549755813888
| `haunch` | `PART_HAUNCH` | 1099511627776
| `hooves` | `PART_HOOVES` | 2199023255552
| `paws` | `PART_PAWS` | 4398046511104
| `forelegs` | `PART_FORELEGS` | 8796093022208
| `feathers` | `PART_FEATHERS` | 17592186044416
| `husk_shell` | `PART_HUSK_SHELL` | 35184372088832
| `none`, `zero` | Empty mask | 0
|===

Here `tail` means `PART_TAILATTACK`, not the general `PART_TAIL` morphology bit.
Other general body parts, negative `BODY_NO_*` flags and undefined bits are not
accepted in `atk`. This step does not expand the separate `bf` keyword list.

[source,text]
----
atk claws fangs
----

Scribe writes the combined decimal value:

[source,text]
----
MobAttackParts 25769803776
----

Use the optional field in the mobile's final tail, after any mob programs,
archetype/rank line and teacher declarations. It can accompany `FStep...` and
`MobResists`/`MobVulnerabilities`/`MobImmunes`. Do not add a tilde terminator.
The server also accepts a compact numeric OR expression such as
`8589934592|17179869184`; Scribe source uses keywords or one combined number,
not that expression syntax.

Within one field, repeated parts are ORed together, not toggled. Repeating the
field itself uses its last value. An omitted field, `atk none` or `atk 0` leaves
the inherited mask unchanged; it does not erase inherited natural features.

For example, if the template supplies claws, `atk claws fangs` removes the
inherited claws and adds fangs. If the template supplies no attack parts,
the same input adds both. An untemplated mobile has an empty inherited mask.

===== Live inspection and editing

`mstat` adds an ATTACK PART group with Template, #MOBILES, XOR removed,
Prototype and Live rows. Cancelled inherited parts are also reported at load
time. A separate table validator rejects no source silently: it reports
undefined raw species/archetype attack bits, including bits that would cancel
out when the two layers are XORed. Malformed optional area masks stop loading
with a vnum-specific error.

[source,text]
----
mset filler attack_parts 17179869184
mset filler attack_parts 0
----

These NPC-only commands replace the entire live mask. Zero clears the live
mask. They do not modify the raw input, template, prototype, another live
instance or future spawns. The command uses decimal masks or compact `|`
expressions, not Scribe keywords. Unknown bits are rejected.

===== Behavioural boundary

Step 4C3a provides the input, resolution, live storage and inspection/editing
mechanics. It does not select new natural attacks, add attacks per round,
create body-part equipment, grant a poison or breath special, change player
forms, or replace the existing combat skills. A zero live attack-part mask
also does not prevent the creature from fighting with its existing combat
mechanics. Wiring natural attack selection to these data is a separate chunk.

`bf` and `atk` are not automatically ORed together. An attack-part declaration
does not silently repair missing anatomy or override a body-form restriction.
Subsequent combat consumers must apply their own anatomical and trauma checks.

DD Builder must expose the same `atk` values and preserve the raw individual
mask. Display inherited and effective values separately. Export `MobAttackParts`
without pre-expanding the template; do not use the effective mask as the next
individual input.

===== Damage and status-effect behaviour

The attack/effect supplies a mask and the target supplies its resistance
state. Multiple matching categories produce *one* result for that damage or
status resolution:

[cols="<2,<5",options="header"]
|===
| Result | Behaviour in the resistance helper
| Immune | A matching immunity wins over resistance or vulnerability; positive damage becomes zero.
| Resistant | With no matching vulnerability or immunity, positive damage is halved, with a minimum of one point.
| Normal | No category matches, or the attack matches both resistance and vulnerability without matching immunity; the helper leaves damage unchanged.
| Vulnerable | With no matching resistance or immunity, positive damage becomes the original damage plus half that damage, rounded down.
|===

These percentages describe the resistance adjustment, not every later combat
modifier. A genuine miss enters with zero damage and remains a miss. An attack
which connects but is nullified by immunity receives a distinct immunity
message. Other mitigation systems can still affect the final damage.

For a combined attack such as `RES_FIRE | RES_MAGIC`, fire immunity or magic
immunity can negate the whole damage event. Resistance to magic and
vulnerability to fire cancel to normal. Being vulnerable to both categories
still applies the vulnerability adjustment only once, not twice.

Selected status-effect paths use `saves_resistance_effect()`. Immunity makes
that resistance-aware save succeed; resistance gives a five-level effective
caster penalty, and vulnerability a five-level effective caster bonus. This
corresponds to a nominal 20-percentage-point saving-throw shift away from
level/chance clamps, not an unconditional 20-point shift at every level.
The existing save limits and other saving-throw rules still apply.

A flag in `skill_table` does not by itself make every bespoke skill, rider,
room effect or direct resource change consult the resistance system. Check
the relevant implementation and test both damage and secondary effects.
The generic NPC system also does not replace existing PC resistance skills
and spells, even when the PC is a vampire.

[[scribe-sonic-water]]
===== Sonic and water categories

The added categories have specific, already-selected uses:

[cols="<2,<3,<4",options="header"]
|===
| Ability | Effect categories | Implementation qualification
| Sonic Blast | `RES_SONIC` and `RES_MAGIC`
| Sonic replaces the previous generic energy classification. The supplied
immunity guard also blocks its secondary nausea, confusion and ongoing effect.
| Bubble Jet | `RES_BLUNT`, `RES_NONMAGIC` and `RES_WATER`
| Water is added without removing impact/source categories. Its immunity guard
also blocks the subsequent disorientation effects.
| Flood | `RES_BLUNT`, `RES_MAGIC` and `RES_WATER`
| The water classification is metadata for this implementation stage. Flood
changes the room; the flag does not automatically prevent flooding or drowning.
|===

Water resistance is not underwater breathing, cold resistance or acid
resistance. Sonic resistance is not a blanket counter to every spell with a
spoken word, chant or vocal casting component. Additional ability
classifications require deliberate changes and, where necessary, additional
runtime checks. Earlier candidate suggestions for other abilities are not
newly enabled rules in this manual.

[[scribe-template-xp]]
==== Archetype XP bonuses and penalties

A creature archetype can supply `xp_mod`, a signed adjustment in *percentage
points*. It is the final field of the server-side `mob_table` entry and is
carried into the resolved template. It is not an ordinary Scribe `$mob`
field, not an individual `.are` field, and not a body-species field in this
implementation.

[cols="<1,<4",options="header"]
|===
| `xp_mod` | Meaning
| `0` | No archetype adjustment. Use this rather than `MOB_TEMPLATE_UNSET`.
| `25` | Add 25 percentage points to the existing XP modifier.
| `-25` | Subtract 25 percentage points from the existing XP modifier.
|===

The effective percentage is calculated by `get_mob_exp_modifier()`:

[source,text]
----
effective XP percentage = existing stored modifier + archetype xp_mod

XP at this calculation stage = base XP * effective percentage / 100
----

The existing stored modifier includes whatever the normal creation/reset
path assigned, including area, special-function and equipment contributions.
The archetype adjustment is added to that same base percentage once. It is
not a second multiplier, and the special-function modifier is not added again.

[source,text]
----
Existing percentage    Archetype adjustment    Effective percentage
120                    +25                     145
120                    -25                      95
100                      0                     100
----

Negative effective percentages are clamped to zero. Later XP adjustments,
randomisation and existing minimum-reward rules still apply, so a very large
penalty or an area `xp` value of zero does not necessarily mean zero final XP.
Use the existing `act no_experience` flag for a mobile intended to award no
experience, allowing for its XOR meaning on a templated mobile.

The existing fame rule which halves fame below an XP modifier of 100 now
consults the effective percentage too. An archetype adjustment which crosses
that threshold can therefore change that existing fame reduction.

`mstat` shows the stored, archetype and effective contributions separately:

[source,text]
----
XP modifier: existing 120% + archetype +25 points = effective 145%
----

For reward testing, compare normally reset-spawned mobiles, not only `mload`
instances. Their stored area/special/equipment contributions can differ.
The template's other numerical modifiers are not substitutes for `xp_mod`.

[[scribe-mobile-diagnostics]]
==== Template diagnostics, validation and live editing

The server validates body-species names, archetype-to-species relationships,
special-function names and resistance definitions during startup. Typical
successful messages include:

[source,text]
----
[MOB TEMPLATE] Relationship validation complete: no issues found.
[MOB TYPE] Resistance validation complete: no issues found.
----

These messages report the checks performed by those validators, not a full
gameplay test. Unknown bits must be checked on raw template layers as well
as resolved masks: identical invalid bits could otherwise cancel through XOR.
Raw archetype XOR masks are not checked for overlap as though they were an
already-resolved creature state.

For an individual flag cancellation, the load log includes the vnum, flag
group, bit, inherited archetype and the fact that `#MOBILES` removed it.
`mstat` exposes the same distinction through separate rows:

[cols="<2,<5",options="header"]
|===
| Row | Meaning
| Template | Body-species defaults after applying the archetype's XOR masks.
| #MOBILES | Original individual input mask, retained separately from the result.
| XOR removed | Bits present in both the inherited mask and the individual mask, excluding protected engine bits where applicable.
| Prototype | Effective initial values from which new NPCs are created.
| Live | Values on the particular NPC being inspected, including subsequent runtime changes.
|===

ACT, AFF, BODY, RESISTANCE, VULNERABILITY and IMMUNITY layers are implemented
in the verified baseline, along with separate prototype/live resistance-validity
results. Step 4C3a adds ATTACK PART layers. Labels beginning with `Template`
describe the inherited layer, not the final NPC state.

Advanced Consider uses live body-form and resistance masks in its existing
archetype-information block. Step 4C3a changes that block's attack-part list to
use the live mask too. This is not a promise that Consider displays every new
field for every untemplated mobile.

===== Live resistance commands

[source,text]
----
mset <mobile> resists <mask>
mset <mobile> vulnerabilities <mask>
mset <mobile> immunes <mask>
----

These are immortal commands for NPCs only. The value is a complete replacement
mask, using decimal numbers or compact `|` expressions without spaces; it is
not a keyword list and is not XORed against the prototype.

[source,text]
----
mset filler resists 2
mset filler immunes 1|256
mset filler immunes 0
----

The last command clears the live immunity mask. It does not clear the
prototype, edit the source, or change any other copy of the mobile. A newly
loaded copy receives the prototype state again. These live changes are not
persisted back to the area definition.

Unknown bits and conflicting live categories are rejected. To move a fire
bit from immunity to vulnerability, first remove it from the live immunity
mask, retaining the other intended immunity bits, then replace the live
vulnerability mask. The command does not automatically edit the other two
categories for you.

===== Builder verification

Check the template, individual, prototype and live rows before testing
combat. Then test inherited defaults, one deliberate cancellation, an
ordinary untemplated mobile, and a temporary live change followed by a fresh
spawn. For an effect with secondary penalties, inspect both HP changes and
active affects. An immunity message alone is not evidence that every rider
was blocked.

Scribe, the server parser and any DD Builder exporter must agree on the
input format. DD Builder must preserve raw individual masks, offer inherited
and effective values separately, and defer cross-category overlap decisions
until the masks have been resolved. The sonic/water categories and signed
archetype XP adjustment also need corresponding editor support; this manual
does not claim that a separate DD Builder implementation has already shipped.

===== Ordinary weapon attack categories

For ordinary `TYPE_HIT`-based attacks, the weapon's `v3` attack type determines
its damage category:

[cols="<3,<2",options="header"]

| `v3` keywords | Resistance category
| `hit`, `pound`, `crush`, `grep`, `scoop`, `mash` | `RES_BLUNT`
| `slice`, `slash`, `whip`, `claw`, `chop`, `rake`, `swipe`, `hack` | `RES_SLASH`

(`ITEM_MAGIC`) produces `RES_MAGIC` ordinary attacks. Other ordinary weapons

weapons are classified using the actual weapon responsible for each hit.

mask into holy or dark damage. The planned blessed/cursed anti-undead rules
are separate work. A special skill's damage may use its fixed `skill_table`
mask instead of this ordinary-weapon classification, even while the character
is wielding a magical weapon.

See <<scribe-resistance-flags,Resistance category reference>> for the combined
mask rule. Immunity which nullifies a connected ordinary hit has a distinct
combat message; it is not reported as a genuine miss.

[[scribe-object-undead]]
==== Undead objects, corpses, remains and body parts

`ex undead` represents the object extra flag `ITEM_UNDEAD` (`BIT_31`, decimal
`2147483648`). It marks undead nature or undead provenance and may be applied
to *any* object type, including flavour items. It is not a new object type.

[source,text]
----
$obj
vn  8
nm  relic black bone
sh  a black bone relic
lo  A black bone relic lies here.
ty  treasure
wg  1
we  take
ex  undead
----

This does not animate the object, give it creature resistances, make its
holder undead, or turn a treasure into a corpse. A downstream spell or skill
must explicitly interpret the flag for it to affect that mechanic.

===== Automatic provenance on death-generated objects

When the dying character satisfies `IS_UNDEAD()`, the death-generation paths
add `ITEM_UNDEAD` to the corpse/remains object and generated body-part objects.
This includes NPC corpses, PC corpses (including vampire PCs), objectlike
mobile remains and the generated fragments/body parts appropriate to the
source's anatomy.

[cols="<2,<5",options="header"]
|===
| Existing object kind | Interaction with the provenance flag
| `ITEM_CORPSE_NPC` | An undead NPC's generated corpse is tagged.
| `ITEM_CORPSE_PC` | An undead PC's generated corpse is tagged; currently the common PC undead classification is vampire.
| `ITEM_REMAINS` | An undead objectlike mobile's generated remains are tagged.
| Generated body-part or fragment objects | Receive the tag from the undead source even when their object type is not a corpse type.
| Existing carried equipment and loot | Do not become undead merely because their owner died or because they are placed inside a tagged corpse.
|===

`ACT_OBJECT` (`act objectlike`) selects the objectlike remains path.
`BODY_INORGANIC` is a separate anatomical property and is not, by itself, the
switch from an NPC corpse to `ITEM_REMAINS`. Existing body-form tests also
affect which death descriptions and body fragments are generated.

`BODY_NO_CORPSE` suppresses corpse production. There is then no corpse/remains
container to tag, and dropped belongings retain their own flags. The
classification is captured when an object is generated; it is not reconstructed
later from a character which no longer exists.

===== Visibility and immortal inspection

Identification reveals the object's undead extra flag. Ordinary room and
inventory descriptions do not gain an automatic visible `(Undead)` marker
from this addition. `ostat` displays the extra flag for immortal inspection.
`oset` retains its existing whole-mask extra-flags interface; this change does
not add a new text-based toggle command.

The proposed Detect Undead display, corpse-feeding restrictions, soul checks,
Animate Dead recycling rules, healing inversions, holy-water attacks and Turn
Undead behaviour are not automatically enabled by adding the provenance flag.
They require their own subsequent implementation. An object with `ex undead`
can therefore be authored now without implying those future mechanics exist.

=== 10. Object sets [[scribe-object-sets]]

Object sets are groups of related wearable objects that grant extra bonuses when enough pieces are worn together. Define the objects normally using `$obj` blocks, then define the set itself with an `$objset` block.

*Block header:* `$objset` or `$objectset`

*`vn` — Vnum*

_Number: 0 or higher_

The relative vnum of the object set. Scribe adds the area base vnum when writing the final #OBJECT_SETS section.

*`nm` — Name / keywords*

_Line of text_

The identifying name or keywords for the set. This is written as the set keyword string.

*`de` — Description*

_Multi-line text block_

The description of the object set. Terminate the block with a single tilde.

*`ob` — Set member object*

_Number: 0 or higher_

The relative vnum of an object belonging to this set. Use one ob line per set item. Scribe writes up to five members. Missing members are written as 0.

*`bt` — Bonus threshold*

_Number: 0 or higher_

Defines how many worn set pieces are required for the corresponding bonus tier. Use one bt line per possible bonus. Scribe writes up to five thresholds. Missing thresholds are written as 0.

*`ap` — Apply effect*

_Line of text_

Defines a bonus applied by the set. Use the same apply keywords as normal object ap fields.

Important: set bonuses are applied in reverse order by the game, so put the strongest bonus first.

The below example writes an `#OBJECT_SETS` entry with two set members. When enough pieces are worn, the set grants the listed apply bonus.

[source, text]
----
$objset
vn      2
nm      uncommon crow
de
The Smithy's Set of the Crow.
~
ob      4
ob      5
bt      2
bt      2
ap      fly -1
----

=== 11. Rooms [[scribe-rooms]]

Rooms are distinct locations within your area, and need not be rooms in a literal sense (inside space with walls, ceiling, floor and doors). They are defined in the `#ROOMS` section of the final area file. You don't have to define any rooms in your area for it to be valid, although you'll probably want rooms if you want people to adventure in your area! Rooms are individually defined in single blocks. === 12. Mobile resets [[scribe-mobile-resets]]

A _reset_ refers to an action performed by the MUD to manipulate and update the world's areas. Mobile resets determine how mobiles are loaded into your area: what rooms they appear in, how many may appear and what objects they are wearing or carrying. The $*addmob* block is used to describe a single mobile reset. You may have as many $*addmob* blocks as you like in your area. You do not need to have any mobile resets for your area to be valid. You may use any particular rooms and mobs as many times as you wish.

*Block header:* `$addmob` or `$addmobile`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `mb`
| mobile vnum
| number
| `rm`
| room vnum
| number
| `num`
| maximum mobile number
| number
| `inv`
| item in inventory
| number
| `*`
| equip item
| number
|===

`*` See below for list of _equip_ fields.

*`mb` — Mobile vnum*

_Number: 0 or higher_

The relative vnum of the mobile you wish to load. A mob using this vnum must be defined otherwise Scribe will indicate an error.

*`rm` — Room vnum*

_Number: 0 or higher_

The relative number of the room you wish to load the mobile into. A room using this vnum must also be defined otherwise an error will result.

You can add as many `rm` fields as you like to a single $*addmob* block, and identical mobiles carrying and wearing all equipment specified will be loaded into each room (up until the limit specified by the `num` field).

*`num` — Maximum mobile number*

_Number: 1 or higher_

_Default: 1_

The maximum number of mobiles with this vnum that can be loaded into the world (all areas) at any one time.

*`inv` — Item in inventory*

_Number: 0 or higher_

The relative vnum of any object you wish the mob to carry. An object using this must be defined otherwise an error will result. You do not have to include any `inv` fields in your reset; you may give a reset as many `inv` fields as you like.

_Number: 0 or higher_

Equip an object on the mob. The following format is used:

_<position> <relative vnum>_

_Position_ is any of the following:

[source, text]
----
light   light source
finger1
finger2
neck1
neck2
body
on body
head
legs
feet
hands
arms
shield
about   about body
waist
wrist1
wrist2
wield   primary weapon
dual    secondary weapon
ranged  ranged weapon (lance, bow)
hold    held in hand
float   orbiting head
pouch   belt pouch
----

You may equip as many items as you wish; if you indicate the same position more than once, the last instance defined will be used.

*Examples*

_Load a single naked mob to a room:_

[source, text]
----
$addmob
mb  1
rm  3
----

_Load a naked mob to rooms 30, 32 and 33 (relative vnums); keep adding a mobile to these rooms every time the area resets until there are 6 mobs in the MUD:_

[source, text]
----
$addmob
mb  4
rm  30
rm  32
rm  33
num 6
----

_Load and equip a mob:_

[source, text]
----
$addmob
rm  3
mb  3
wield   7
inv 6
shield  9
body    8
inv 5
inv 5
----

=== 13. Object resets [[scribe-object-resets]]

Object resets determine how objects other than those given to mobiles are loaded into your area: objects that appear on the ground in rooms, and objects that are placed inside other objects. The *$addobj* block is used to describe a single object reset. You may have as many *$addobj* blocks as you like in your area. You do not need to have any object resets for your area to be valid. You may use any particular rooms and objects as many times as you wish.

*Block header:* `$addobj` or `$addobject`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `ob`
| object vnum
| number
| `rm`
| room vnum
| number
| `lv`
| level of object
| number
| `con`
| container object vnum
| number
|===

*`ob` — object vnum*

_Number: 0 or higher_

The relative vnum of the object you wish to load.

*`rm` — Room vnum*

_Number: 0 or higher_

The relative number of a room you wish to load the object into. A room using this vnum must also be defined otherwise an error will result.

*`lv` — Level of object*

_Number: 0 or higher_

The level you wish the object to be. *Only applies if the object is reset to the ground and NOT to a mob or container*.

*`con` — Container vnum*

_Number: 0 or higher_

The relative number of a container object you wish to place the item in. A container object with this vnum must be defined for the reset to be valid.

Only one of each kind of object may occupy any single container. The object is loaded to the most recently loaded container with the specified vnum. For best results, only load one of each container object into your area.

You need to have at least one `rm` or one `con` fields for the *$addobj* block to be valid.

*Examples*

[source, text]
----
$addobj
ob  4
rm  12

$addobj
ob  2
rm  6
rm  7
con 12
----

=== 14. Games [[scribe-games]]

You can allow mobiles to host gambling games in the MUD.

*Block header:* `$game`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `mb`
| mobile vnum
| number
| `gm`
| game name
| text
| `br`
| bankroll
| number
| `mw`
| max wait time
| number
| `ch`
| cheat value
| number
|===

*`mb` — Mobile vnum*

_Number:1 or higher_

Number of the mobile in charge of the game (dealer or croupier, for example)

*`gm` — Name of game*

_Line of text_

The name of the game. Current games available are

[source, text]
----
ult     Upper-Lower-Triple, a dice game
highdice    High dice, a dice game
seven       Seven, a dice game
----

*`br` — Bankroll*

_Number: 0 or higher_

the amount of gold that the mob running the game has when it is loaded. When the bankroll goes below zero, the mob shuts down its game. Currently games can only be conducted with gold pieces.

*`mw` — Max wait time*

_Number: 0 or higher_
_Default: 8_

The number of PULSE_MOBILEs the croupier will wait for each person to make a decision for interactive games (currently unimplemented).

*`ch` — Cheat value*

_Numbe: 0 or higher_

Whether the mobile running the game will cheat or not. If the cheat value is non-zero, he will cheat.

`mb`, `gm`, `br`, and `ch` values are required for a $game block to be valid.

*Example*

[source, text]
----
$game
mb  3001
gm  ult
br  50000
mw    24
ch    0
----

=== 15. Helps [[scribe-helps]]

You can define help file entries in your area using the *$help* block. You don't have to include any *$help* blocks in your area for it to be valid.

*Block header:* `$help`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `he`
| Help text
| Multi-line text block
| `lv`
| Level restriction
| number
|===

*`he` — Help text*

_Multi-line text block_

Define the help entry keywords and body text using the `he` field:

[source, text]
----
he  <keywords or phrases>
<help text>
~
----

The _keywords or phrases_ string is automatically capitalised by Scribe.

[source, text]
----
E.g.    he  fly levitate
This is the text displayed whenever the
commands HELP FLY or HELP LEVITATE
are entered.
~

he  'aura of fear'
This is the text displayed whenever the
command HELP 'AURA OF FEAR' is issued.
~
----

*`lv` — Level restriction*

_Number: -1 or higher_

The minimum level a character has to be in order to access the help entry. `0` is used for general help entries. Use `–1` if you want the help entry keyword header to be hidden.

=== 16. Shops [[scribe-shops]]

Mobiles can be made to run shops: the inventory of the shop is the inventory of the mobile. So long as the mobile is alive, players can attempt to buy and sell items from the shop.

*Block header:* `$shop`

.Fields
[cols="1,3,2",options="header"]
|===
| Field | Description | Type
| `vn`
| Vnum of shopkeeper
| number
| `t1`
| Traded item type 1
| keyword
| `t2`
| Traded item type 2
| keyword
| `t3`
| Traded item type 3
| keyword
| `t4`
| Traded item type 4
| keyword
| `t5`
| Traded item type 5
| keyword
| `ps`
| Profit-sell
| number
| `pb`
| Profit-buy
| number
| `oh`
| Opening hour
| number
| `ch`
| Closing hour
| number
|===

*`vn` — Vnum of shopkeeper*

_Number: 0 or higher_

The relative vnum of the mobile that will run the shop.

*`t1-t5` — Traded item types*

_Keyword_

The item types that the shopkeeper will be prepared to buy from players. You may indicate up to five types; you don’t have to specify any types for the shop to be valid. Use the same keywords used to define item types.

[source, text]
----
E.g.    t1  weapon
t2  armour
----

*`ps` — Profit-sell*

_Number: 0 or higher_

The percentage markdown on items sold to the shopkeeper. `100` is the intrinsic value of the item, `75` is a 25% markdown, etc. This value should be at most 100%.

*`pb` — Profit-buy*

_Number: 0 or higher_

The percentage mark-up on items bought from the shopkeeper. `100` is the intrinsic value of the item, `150` is a 50% mark-up, etc. This value should be at least 100%.

*`oh ch` — Opening and closing hours*

_Number: 0 - 23_

The times when the store opens and closes (`0` = midnight).

*Example*

[source, text]
----
$shop
vn  0
t1  wand
t2  staff
t3  potion
t4  scroll
oh  7
ch  18
ps  85
pb  120
----
